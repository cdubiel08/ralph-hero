## Overview

Single-issue plan for GH-1271 (Feature D of the Unified Agent System epic). Plugs three non-issue event sources into the GitHub Projects V2 board so the Director (Feature B) can route them to the right team:

1. **Cloud Monitoring → board**: a Pub/Sub subscriber normalizes alert payloads into `watcher-auto`-labeled draft issues.
2. **Langfuse → board**: `ralph-debug-collate` is promoted from on-demand to a non-interactive scheduled run that lives inside the Watcher heartbeat (Feature C).
3. **Dream-loop → board**: `scripts/dream/reflect.py` gains a post-cluster classifier step that, when a cluster exceeds a size threshold AND its raw memories share `tool_use_error` or `verdict: BLOCKED` signals, emits a `process-improvement` draft issue.

Plus a small Director taxonomy patch that upgrades the `watcher-auto` and `process-improvement` rows in `event-classes.md` from "placeholder, producer ships in Feature D" to live entries pointing at this feature's producers.

| Phase | Title | Estimate |
|-------|-------|----------|
| 1 | Cloud Monitoring → board: Pub/Sub subscriber | S |
| 2 | Langfuse → board: scheduled debug-collate inside Watcher heartbeat | XS |
| 3 | Dream-loop → board: cluster classifier in reflect.py | S |
| 4 | Director taxonomy patch: promote placeholder rows to live producers | XS |

**Why single-issue**: GH-1271 is sized **S** in the epic and is a single GitHub issue. The four phases above are the four atomics enumerated in the parent plan-of-plans for Feature D. They share a producer/consumer contract (all four feed labeled issues onto the same board, all four are read by Director), so they belong together in one plan document and one PR.

## Shared Constraints

Inherited verbatim from the parent plan-of-plans (`thoughts/shared/plans/2026-05-16-GH-1267-unified-agent-system-epic.md` § Shared Constraints). The points that bite hardest in this feature:

1. **No new runtime layers.** The Cloud Monitoring → board bridge MUST terminate in a `create_issue` call against the existing GitHub Projects V2 board via the `mcp__plugin_ralph-hero_ralph-github__ralph_hero__create_issue` MCP tool (or, for draft-issue mode, `create_draft_issue`). No message broker, no separate orchestration daemon, no new database. The Pub/Sub subscriber's only output is GitHub issue creation. If a Cloud Run deployment is chosen, it is a stateless job whose sole side-effect is the MCP call (or a `gh issue create` shell-out as fallback for the launchd path).

2. **Skill / agent surface conventions.** This feature adds **no new skills and no new subagents**. It edits one existing Python file (`scripts/dream/reflect.py`), one existing taxonomy doc (`plugin/ralph-hero/skills/director/event-classes.md`), one existing skill body (`plugin/ralph-hero/skills/watch/SKILL.md` — heartbeat step), and one new infrastructure directory (`plugin/ralph-hero/scripts/monitoring-bridge/` with subscriber + launchd template). No `SKILL.md` or `agents/*.md` files are created.

3. **iOS-friendly artifacts.** Every issue created by a producer in this feature MUST be a `## Result` shape that fits one mobile screen — title, one-paragraph summary, a `## Source` block (alert URL, Langfuse trace URL, or cluster id), and a `## Suggested Team` line. Long payloads (full alert JSON, full Langfuse error trace, full cluster memory bodies) go in a collapsed `<details>` block at the bottom so iOS readers see the summary first.

4. **Remote-trigger contract.** The producers in this feature emit labels that Director's taxonomy already recognizes (`watcher-auto`, `process-improvement`). No new `trigger:<team>` labels are introduced here. Director ticks consume the labels per its own rules; this feature is producer-side only.

5. **Outcome recording is automatic.** This feature is on the **ingestion** side of the loop (events → board). The outcome-recorder wrapper that closes the loop on the read side is Feature E (GH-1272). Producers in this feature do not call `knowledge_record_outcome` themselves — they file issues, the downstream team handlers (Watch, Caretake, etc.) record outcomes when they act on those issues.

6. **Verification tooling.** Discovered from the repo:
   - Python (dream-loop changes): `cd scripts/dream && uv run pytest`, `cd scripts/dream && uv run ruff check .`
   - TypeScript (no plugin code changes expected, but lint/typecheck must still pass): `cd plugin/ralph-hero/mcp-server && npm run build && npm test`
   - Cloud Monitoring subscriber: shell smoke script at `plugin/ralph-hero/scripts/monitoring-bridge/smoke.sh` asserting (i) the subscriber script parses and runs `--dry-run` cleanly against a fixture payload, (ii) the dry-run output enumerates the issue title/labels/body it would file
   - Taxonomy doc: visual diff and `grep -E '^\| \`watcher-auto\`' plugin/ralph-hero/skills/director/event-classes.md` returns the live (non-placeholder) row

7. **Atomicity.** Every phase below is XS or S. The Pub/Sub subscriber is the largest unit; its `S` sizing comes from the choice between launchd-scheduled pull (preferred for parity with `dream-loop`) vs. Cloud Run job (preferred for Cloud-native ops). The plan picks **launchd-scheduled pull** as the default because it keeps the producer side of the loop on the same machine as the dream-loop and avoids a new Cloud Run deployment; the Cloud Run path is documented as an optional follow-up in "What We're NOT Doing."

8. **No OpenClaw runtime.** Repeated for emphasis. The subscriber is a single Python script that calls one MCP tool; the reflect.py classifier is ~50 LOC; the heartbeat patch is a one-step addition to an existing skill body; the taxonomy patch is a two-line edit. There is no new platform.

Feature-specific additions (not in the parent plan):

9. **Cloud Monitoring payload normalization is deterministic.** The subscriber MUST NOT call an LLM. It maps Pub/Sub message fields → GitHub issue fields via a fixed schema (alert policy id → `<!-- gcp-policy: ... -->` marker, condition name → issue title, alert URL → `## Source` link). This is the same marker shape that `gcp-incident-triage` already keys off (per the Watcher plan, Phase 4 task 4.2). Keeping the marker stable means the Director → Watch handoff Just Works without coordination.

10. **The dream-loop cluster classifier is a post-cluster pure-Python step.** It runs AFTER `cluster_memories()` returns and BEFORE `synthesize_reflection()` is called per cluster. It reads only the fields already on `RawMemoryRow` and emits a separate side-effect (an MCP issue-creation call); it MUST NOT mutate the clusters or the reflection-writing path. A failing classifier (e.g. unreachable MCP) MUST log a warning and continue — the reflection pipeline keeps running.

## Current State Analysis

**Cloud Monitoring side.** GCP alert policies are terraform-managed (per `gcp-incident-triage` skill notes). The `gcp-incident-triage` skill reads from a Pub/Sub topic that Cloud Monitoring already publishes to. There is currently **no automated translation** from those Pub/Sub messages to GitHub issues — a human runs `gcp-incident-triage` manually (or via `/loop 30m`), and the skill is what creates the issues. Feature D moves that translation to a non-interactive subscriber so issues land on the board even when no human is at the terminal. The subscriber is **not** a replacement for `gcp-incident-triage` — the skill keeps doing its delta/dedup analysis; the subscriber just ensures the issues exist for the skill to analyze.

**Langfuse side.** `plugin/ralph-hero/skills/ralph-debug-collate/SKILL.md` already implements the dry-run → confirm → file workflow. The `ralph_hero__collate_debug` MCP tool gates on `RALPH_DEBUG=true`. The skill is interactive — Step 4 requires a human "yes" before mutating GitHub. Feature D promotes it to a non-interactive scheduled run by adding a `--auto-confirm` flag (read by the skill body's Step 4) and registering a heartbeat step that invokes the skill with that flag. The promotion lives **inside Feature C's Watcher heartbeat** (`plugin/ralph-hero/skills/watch/SKILL.md`'s heartbeat path), not as a standalone schedule — the Watcher already runs every 15 min, so adding one step to its heartbeat is cheaper than a separate cron.

**Dream-loop side.** `scripts/dream/reflect.py` clusters raw memories via UMAP+HDBSCAN at lines 274–333 (`cluster_memories()`). The clusters then flow through `synthesize_reflection()` (line 446) and `write_reflection()` (line 599). The classifier inserts between cluster_memories and synthesize_reflection: for each cluster, it scans the raw memories' `content` (or a dedicated `signals` field if present) for `tool_use_error` and `verdict: BLOCKED` markers, and if a cluster's size exceeds a threshold AND a fraction of its memories carry one of those signals, it emits a `process-improvement` issue via the MCP `create_issue` tool. The reflection then synthesizes normally — the classifier is additive, not replacement.

**Director taxonomy side.** Per the Director plan (Feature B, GH-1269), `event-classes.md` ships with placeholder rows for `watcher-auto` and `process-improvement`:

> any state + `watcher-auto` → watchers (placeholder, producer ships in Feature D)
> any state + `process-improvement` → caretakers (placeholder, producer ships in Feature D)

Feature D's taxonomy patch removes the "(placeholder, producer ships in Feature D)" annotation and adds a `## Producers` subsection at the bottom of `event-classes.md` documenting which producer ships each label (with file paths to the subscriber + reflect.py classifier).

## Desired End State

After this feature ships:

- A synthetic Cloud Monitoring alert delivered to the configured Pub/Sub subscription results in a `watcher-auto`-labeled draft issue on the GitHub Projects V2 board within one launchd cycle (default 5 min).
- The Watcher heartbeat (Feature C) includes a step that invokes `ralph-debug-collate --auto-confirm --since 24h --min-occurrences 3` and files any Langfuse error groupings as `debug-auto`-labeled issues without human confirmation.
- A dream-loop run (`dream-now` or `uv run reflect.py --since 24h`) that encounters a cluster of size ≥ threshold whose raw memories contain ≥ 30 % `tool_use_error` or `verdict: BLOCKED` signals files a `process-improvement` draft issue describing the cluster theme (plus a `<details>` block with the source ids).
- `plugin/ralph-hero/skills/director/event-classes.md` no longer carries placeholder annotations for `watcher-auto` and `process-improvement`; it has a `## Producers` section enumerating producer file paths and trigger conditions.

- `plugin/ralph-hero/scripts/monitoring-bridge/smoke.sh` passes (dry-run subscriber against a fixture payload).
- The Director skill, run on a board that contains a freshly-filed `watcher-auto` issue, classifies and dispatches Watch without any taxonomy edits.

## What We're NOT Doing

- **Building a Cloud Run job for the Pub/Sub subscriber.** The plan picks launchd-scheduled pull. A Cloud Run deployment is a valid follow-up if multi-machine reliability becomes a concern, but it adds a new runtime layer (Cloud Run) and a new deployment path. Out of scope for this feature.
- **Editing `gcp-incident-triage`'s body or its marker conventions.** The subscriber emits the same `<!-- gcp-policy: ... -->` marker shape that `gcp-incident-triage` already keys off. If the marker shape needs to change, that's a separate issue.
- **Editing `ralph-debug-collate`'s preflight or dry-run logic.** Only adding `--auto-confirm` and threading it into Step 4 of the existing skill body. The dry-run, the Langfuse health check, and the issue-shape are unchanged.
- **Reclustering raw memories.** The classifier piggybacks on `cluster_memories()`'s output. It does not introduce a new clustering pass or change the UMAP/HDBSCAN parameters.
- **Adding new taxonomy rows beyond what Director's `event-classes.md` already enumerates.** The Director plan (Task 1.1) already includes rows for `watcher-auto` and `process-improvement`; this feature only upgrades them from placeholder to live.
- **Writing the outcome-recorder.** Feature E (GH-1272) ships that. This feature is producer-side only.
- **Cloud Monitoring alert policy creation or terraform changes.** Those policies are already terraform-managed; this feature reads from an existing topic.
- **Adding push notifications (ntfy) when issues are filed.** Feature H (GH-1275) ships the ntfy wiring. The producers in this feature emit issues silently; iOS users discover them via the next `cos` summary or the GitHub mobile app.

## Implementation Approach

The plan is a single PR with four phases. Phases 1, 3, and 4 are independent and could be parallelized by an orchestrator; Phase 2 depends on Phase 4 (the heartbeat step references the taxonomy doc for label conventions). Phase 4 is the smallest and is sequenced last so the taxonomy doc reflects the producers as they actually ship.

Dependency-wise, this feature consumes:
- The Watcher heartbeat path from GH-1270 (Feature C) — Phase 2 patches `plugin/ralph-hero/skills/watch/SKILL.md`'s heartbeat step.
- The Director taxonomy doc from GH-1269 (Feature B) — Phase 4 patches `plugin/ralph-hero/skills/director/event-classes.md`.

Both files are produced by sibling features earlier in Wave 2. This feature is Wave 3 and lands after both.
