How GitHub rate limits work in ralph-hero/mcp-server

TL;DR — A proactive in-process limiter sits in front of every GraphQL call: it reads each response's rateLimit field, warns at 100 points remaining, and blocks for up to 60s when ≤ 50. Secondary 403s with retry-after are caught and retried transparently. Primary 429s and every REST call have no retry path at all.

Where GitHub traffic enters

Two paths reach api.github.com. GraphQL goes through Octokit's @octokit/graphql client, constructed in github-client.ts:109–119 with an injected auth header and no throttling plugin. REST goes through a raw fetch() wrapper named restPost() at github-client.ts:363–392. Only the GraphQL path runs through the limiter wrapper executeGraphQL<T>() at line 142.

★
The split matters. Anything routed through executeGraphQL() — almost every issue/project read and write — gets the limiter. Anything that bypasses it (view creation, a few REST-only endpoints) hits GitHub naked.

The in-process limiter

One file, ~90 lines: src/lib/rate-limiter.ts. The RateLimiter class tracks remaining and resetAt, updated from each GraphQL response.

1 · Pre-request check rate-limiter.ts:43–67

Every call to executeGraphQL() first runs checkBeforeRequest(). If remaining ≤ 50 (the block threshold), it sleeps until reset — capped at 60 seconds regardless of what GitHub's reset window says. If remaining ≤ 100 (the warn threshold), it logs but doesn't block.

Thresholds are constructor options that could be wired to env vars but currently aren't — index.ts instantiates the class with the hard-coded defaults (100, 50).

2 · Auto-injected rateLimit fragment github-client.ts:149–164

Before every non-mutation query goes out, the wrapper checks whether the query contains a rateLimit { remaining cost resetAt } selection. If not, it splices one in via a regex against the leading query { token. The response is parsed and pushed into the limiter so its state stays current without any explicit call by tool code.

★
The regex only matches unnamed queries. A query GetIssue($id: ID!) { ... } won't receive auto-injection. If named queries exist anywhere in the codebase, the limiter silently goes stale for them.

Retry on secondary rate limit

When Octokit raises a 403 carrying a retry-after header, the wrapper catches it, parses the header as seconds, sleeps, and recursively re-invokes executeGraphQL(). The caller sees only the eventual success or a final throw.

// github-client.ts:227–238 (paraphrased)
} catch (err) {
  if (err.status === 403 && err.response?.headers?.['retry-after']) {
    const waitMs = parseInt(err.response.headers['retry-after'], 10) * 1000;
    await sleep(waitMs);
    return executeGraphQL(query, vars);  // recursive — no max-attempts
  }
  throw err;
}

No exponential backoff. No retry budget. One secondary-limit storm in succession could stack recursive frames.

What the caller sees

Tool handlers don't see the limiter at all on the happy path. On failures they see the rethrown error and wrap it via toolError() — the LLM receives the GitHub message verbatim in the MCP response body.

  • 403 + retry-after (secondary rate limit): retried once transparently; success returns, failure rethrows.
  • 429 (primary rate limit): not handled. Thrown straight through to the caller, surfaced to the LLM as a tool error.
  • Any REST call hitting 429 or 403: thrown immediately by restPost(). No retry, no log.
  • Network / 5xx: logged to OpenTelemetry span and console, rethrown unchanged.

Configurable knobs

Almost none. Everything that could be tunable is hard-coded:

  • Warn / block thresholds — constructor options, never wired to env (rate-limiter.ts:25–27).
  • 60-second sleep cap — literal in checkBeforeRequest() (rate-limiter.ts:53).
  • Fragment injection regex — literal at github-client.ts:154.

No CLI flags, no env vars, no config file. The shape of the limiter is the shape you get.

Test coverage

Three rate-limit tests live in __tests__/github-client.test.ts:

  • Lines 332–357 — verifies rate-limit state is read from a successful response.
  • Lines 385–408 — verifies the 403 + retry-after path retries once and returns the second call's result.
  • Lines 410–426 — verifies that 500-class errors are rethrown without retry.

Gaps & gotchas

  • No 429 handling. Octokit can raise a primary 429 if the limiter's view of remaining is stale or wrong. The code only retries 403. A 429 propagates as a hard error.
  • REST is unprotected. View creation and any other REST-only path inherits zero retry logic. One transient 403 ends the operation.
  • Named GraphQL queries skip auto-injection. The regex only catches anonymous query { form. Named queries get no rate-limit fragment, the limiter's state stops updating for them, and the next pre-check uses stale numbers.
  • 60-second cap is arbitrary. If GitHub returns retry-after: 3600 during a long outage, the limiter sleeps 60s and tries again immediately — the cap protects against indefinite hangs but throws away the server's advice.
  • Recursive retry has no ceiling. Successive secondary-limit responses stack recursive executeGraphQL() frames. No maxAttempts, no exponential backoff.
Does the limiter share state across MCP server processes?
No — it's in-process. Each tool invocation that spawns the server gets a fresh limiter that starts with the first GraphQL response's quota numbers.
What happens at server cold-start before any response has been seen?
The limiter initializes with no state, so checkBeforeRequest() on the very first call is a no-op — the first request always goes out unchecked. The response then seeds the limiter for everything after.
Would adding octokit-plugin-throttling duplicate work?
Partially. The plugin handles both 403 and 429, and adds exponential backoff — both gaps in the current code. The in-process pre-check would still be additive (the plugin reacts; the pre-check anticipates).
