Postgres vs DynamoDB for the event-log store

PROMPT Compare Postgres vs DynamoDB for our event-log store and recommend one.

01Postgres (append-only table, partitioned by month)

One table keyed on (aggregate_id, sequence_no), range-partitioned by event_time, written through a managed RDS / Aurora primary.

Pro
Con
Ad-hoc SQL over the event stream — debugging is SELECT
Single-primary write ceiling; one node carries every INSERT
Transactional appends; the optimistic-concurrency check is one row constraint
Vacuum, bloat, and partition maintenance become real jobs past ~1 TB
Existing team SQL muscle and tooling apply on day one
Multi-region active-active is a project, not a feature
Projections / read models can live in the same database, joined to source events
Replay throughput is bounded by sequential scan speed of one node
Write ceiling: ~20k/s (Aurora) Read latency: 1–5 ms p50 Ops cost: medium $/GB-month: ~$0.10 (gp3)

02DynamoDB (partition by aggregate, sort by sequence)

Partition key aggregate_id, sort key sequence_no; GSI on event_time for chronological replay; on-demand capacity.

Pro
Con
Horizontal write scaling is the default — no ceiling within a single table
Access patterns are baked into the schema; new query shapes mean new GSIs
Single-digit-ms reads on the partition + sort key at any scale
No joins, no ad-hoc SQL; every debug session pulls items into a script
Conditional writes give per-aggregate optimistic concurrency for free
Hot partitions on a popular aggregate throttle the whole partition's throughput
Streams + Lambda give a zero-ops projection pipeline
On-demand cost climbs fast at sustained high RPS; provisioned needs forecasting
Write ceiling: none (per partition: 1000 WCU/s) Read latency: 2–10 ms p50 Ops cost: low $/GB-month: ~$0.25

Recommendation

Go with approach 02, DynamoDB. Event logs are the workload DynamoDB was shaped for: high-volume appends, partition-key-driven reads (aggregate_id), and a Streams-based projection path that doesn't require us to operate a Kafka or build CDC. The schema constraint — access patterns up front — is fine because event-sourced reads are almost always "give me all events for aggregate X" or "give me events since timestamp Y", both of which the partition + sort layout serves natively.

Switch to 01 (Postgres) if (a) sustained write throughput will stay under ~5k events/s for the foreseeable future, (b) the team needs ad-hoc SQL over the event stream for debugging or audit, or (c) projections must transactionally read from the same store as the source events. The moment writes blow past a single Aurora primary or a multi-region active-active requirement lands, the migration cost dwarfs the schema-design discomfort of going to DynamoDB now.
