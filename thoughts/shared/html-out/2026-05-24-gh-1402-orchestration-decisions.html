Orchestration-gap decisions for GH-1402

TL;DR — Most of the proposed gaps already exist as functionality; the rest become four small extensions to GH-1402 plus a triage self-containment hook. Final shape: per-verb --auto alias (Option A), heartbeat status posts default to --dry-run, triage drops KEEP for explicit ROUTE-TO-<queue> transitions, no new ScheduleWakeup hook (existing autopilot pair covers it), and caretake --auto (triage) is hook-enforced to never dispatch Skill() to other verbs. All folded into GH-1402 (now 7 phases, was 5; 10 new files, 13 modified).
★
The biggest surprise of the brainstorm: /ralph:hero --mode auto already does exactly what the user proposed in "drive the orchestrator, not the verb." The user had been running /loop /ralph:caretake (a heartbeat fan-out) when they wanted /loop /ralph:hero --mode auto (an event-driven director loop). The gap was discovery, not implementation.

1. --auto flag scope: per-verb alias picked

DECISION --auto on any loop-suitable verb is a per-verb alias for that verb's most autonomous mode — not a universal director-routed dispatcher.
WHY Preserves verb semantics; /ralph:hero --mode auto stays the canonical "drive across all teams" path; smaller change (no new routing logic, just a per-verb alias table). The verb you typed still scopes the action.
REJECTED Option B — universal director-routed: --auto on any verb would ignore the verb and classify the top of next_actions via director. Would let /ralph:caretake --auto end up running an impl, which surprises and breaks the verb taxonomy.

2. Heartbeat status posts default to dry-run picked

DECISION When /ralph:catch-up --mode report is invoked via --loop, default to --dry-run; print to stdout and end with a literal > hint: to actually post this status update, re-run with --post line.
WHY Today, a daily cron would generate 365 GitHub status updates per year — each one persistent and visible on the project's status feed. The composed body is still useful as stdout; posting should be explicit opt-in via --post or RALPH_CATCH_UP_HEARTBEAT_POST=true. Non-loop invocations preserve today's post-by-default behavior.
REJECTED Status quo — silently posting every tick generates noise faster than humans can read it.

3. Triage palette: remove KEEP, add ROUTE-TO-<queue> picked

DECISION Drop KEEP as a verdict. New palette: CLOSE · SPLIT · RE-ESTIMATE · ROUTE-TO-Research Needed · ROUTE-TO-Ready for Plan · ROUTE-TO-In Progress · HUMAN. Every triage call produces forward motion or escalates to "Human Needed."
WHY Today's KEEP applies a ralph-triage label that excludes the issue from re-pick, so KEEP'd items sit dormant in Backlog until manual label removal. Replacing it with explicit routing means triage always produces a state transition or asks for help — no more "decided + not acted-on" purgatory.
REJECTED TTL on KEEP'd items (e.g., re-pick after 14 days) — just re-creates the original triage problem after N days without adding information. Block-reason hint label — overlaps with the simpler ROUTE-TO solution.

4. No new ScheduleWakeup hook picked

DECISION Do not add a new hook for ScheduleWakeup overwrite-cancel semantics. The existing autopilot-wakeup-clear.sh + autopilot-stop-gate.sh pair already deterministically guards the only path where an inner skill could leak a ScheduleWakeup call.
WHY The generalized --loop flag wraps skills via Skill("loop", ...) — /loop owns wakeup management, inner skills don't call ScheduleWakeup themselves. The autopilot case (where inner skills could leak) is already hook-enforced. Adding more hooks would duplicate enforcement and tighten coupling for no real safety gain.
REJECTED New PreToolUse:ScheduleWakeup hook with per-turn counter — was my initial suggestion; user pushed back rightly that the existing hooks already cover the autopilot case deterministically, and other --loop wraps don't need it because /loop handles wakeup itself.
→
Belt-and-suspenders: ralph/CLAUDE.md Phase-4 doc update states the rule explicitly so future skill authors don't reintroduce direct ScheduleWakeup calls from inside --loop-wrapped skill bodies.

5. Consolidation: iterate GH-1402, no new doc picked

DECISION Iterate the existing GH-1402 plan in place with two new phases (6 + 7) and inline updates to Phases 3 + 4. No companion design doc.
WHY The GH-1402 plan was drafted today, is in status: draft, and already contains full prior-work + state analysis for the --loop flag. Adding three phases is iteration, not a fork. "Compress to one doc" means one source of truth, not multiple cross-referenced specs.
REJECTED Write a new thoughts/shared/research/2026-05-24-orchestration-gap-design.md spec that supersedes GH-1402 — creates a second doc that has to stay in sync with the plan. Net cost > net benefit.

6. Triage self-containment: hook-enforced picked

DECISION caretake --auto (= --mode triage) does not dispatch any Skill() calls. Enforced deterministically by a new triage-no-skill-dispatch.sh PreToolUse hook (matcher: Skill, gated on RALPH_SUBCOMMAND=triage).
WHY Triage's contract: assess ONE Backlog issue, route it via state transition. Downstream work happens between loop ticks — if triage routes to "Ready for Plan," the next tick of /loop /ralph:plan --auto picks it up. Within-tick cascading would break loop discipline, undermine the per-verb --auto contract, and make iterations unpredictable. Hook over prose because deterministic enforcement matches the same principle that ruled out a new wakeup-cancel hook in Decision 4 — when the contract is bright-line, code it.
REJECTED Allowlist with some Skills permitted (e.g., Skill("ralph:caretake", args="--mode split #NNN") for inline splitting). Today's design already defers split via the needs-split label and a separate --mode split picker tick — no need to break loop discipline for it.
→
Hook scope is narrow: blocks Skill() only. Agent() sub-agent dispatches (codebase-locator for assessment) and MCP tool calls (save_issue, add_dependency) pass through — those are triage's core work.

7. catch-up refuses --auto picked

DECISION /ralph:catch-up --auto refuses with a one-line message. Already in Phase 6's refusal-targets list alongside form and setup.
WHY --auto means "drive work forward autonomously." catch-up composes-and-observes rather than drives. Users who want a status-update heartbeat type --mode report --loop explicitly. If a caller (e.g., another skill) invokes catch-up, it must understand the contract — there is no autonomous catch-up surface.
REJECTED Alias --auto to --mode report for muscle-memory parity across loop-suitable verbs. User explicitly chose semantic purity over parity.
