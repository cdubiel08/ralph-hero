Loop agents for ralph: how many, what they own, when they fire

Prompt Design easy-to-create agents that run in loops within the ralph-hero plugin ecosystem. Starting concepts: a board agent (context across plan files, issues, hygiene), a delivery agent (CI / comments / reviews / CD, PR stacking), and a work agent (picks epics and issues off the backlog). Explore granularity (2 vs 3 vs 5 agents), boundaries, trigger/dispatch cadence, and how to make new agents cheap to create and configure.
TLDR: In ralph v2 terms an "agent" is a lane: a deterministic selector, one skill, a cadence, a bounded write lane, and a model tier. Split lanes where signal source, write lane, cadence, and permission set all four differ at once — that test yields exactly three lanes, and they map onto the board's own state machine: work owns In Progress (exists, never enabled), deliver owns In Review (the biggest gap — merge-pr.sh's exit-75 retry contract was designed for a caller loop nobody built), and tend owns Backlog shape plus the Done→effective audit. Ship each lane as a capability with a stable contract (typed selector, exit codes, one skill) plus a malleable example loop script — never a prescribed harness. Enforcement already lives at the mutation path, so the scripting stays the user's. Step zero is not new code: switch on the loop that already exists.

Ground truth: what already exists, what is missing

The three starting concepts land very differently against the current tree. One is built, one is half-built as deterministic code, and one is a genuine void.

Work lane
Built, never enabled
tick.sh + board next + /ralph:work are complete; waystone grades ralph-tick-loop at rung 1, "built-but-never-enabled", baseline 0 ticks/day (ladder.yaml:34-41, charter W4).
Board hygiene, layer 0
Already code
state-guard.yml event lane + 15-min doctor --fix cron + weekly doctor --strict. The deterministic part of the "board agent" is shipped — only the judgment tier is missing.
Delivery
Nothing
No re-review nudges, no thread replies, no re-attest on new head, no CI retry, no stack retarget. merge-pr.sh:39-48 defines PASS/WARN/PENDING(75)/FAIL explicitly "for loop-runners" — none exists.
Scheduler contract
Transport-agnostic, prompt-hardcoded
The v2 record says the contract is only "invoke one work session per tick" and calls tick.sh "a convenience, not the architecture." This design keeps it that way: new lanes ship as contracts plus example scripts users copy and own — never a harness ralph runs for you.

Three architectural facts constrain everything below:

  • Projects V2 emits no usable webhook — field-level truth is only observable by polling, which is why state-guard.yml is a two-lane event-plus-reconciler design. Any board-watching agent inherits the reconciler shape.
  • The claim protocol's safety margin assumes one flock-serialized scheduler per machine (Projects V2 has no compare-and-swap; races are made visible and refused, not impossible). Adding schedulers carelessly erodes a stated design assumption.
  • The rework edge already exists. MACHINE at board.ts:41-48 allows In Review → In Progress and In Progress → Backlog, so a delivery lane can demote a PR that needs semantic rework without any state-machine change (two legal hops, same precedent as the deliberately multi-hop parent-check).
§ The v2 design record's funnel test governs this whole exercise: "a proposed addition that is not a state mutation, an invariant, or doctor belongs to the model's judgment." Applied here: lane eligibility is a typed selector (code), lane invariants are board.ts guards and doctor checks (code), lane judgment is one SKILL.md (prose). Nothing else gets to exist.

Recommendation

Go with approach 02 — three lanes partitioned by board state, shipped as capabilities plus example scripts (below), never a prescribed harness. The decision rule that produces it is the one worth keeping: split where signal source, write lane, cadence, and permission set all differ simultaneously. Work (backlog + code, claims, 15-min, full dev rights), deliver (checks + reviews + attestations, PR/branch + In Review transitions, ~10-min, push/merge rights), and tend (board + thoughts + live tree, issue metadata only, hours, zero code rights) each pass all four. The five-way split divides lanes that share signals; the two-way merge fuses lanes that share nothing but shape.

Conditions that change the answer: if token budget is the binding constraint, run approach 01 with the steward on a slow cadence — it is strictly better than nothing and upgrade-compatible with 02 (the steward skill forks into deliver/tend later). If a future lane candidate passes the four-dimension test (a plausible one: a release/effective lane once deploy lanes exist per waystone W5), add it as a fourth lane — the test, not the count, is the design.

Boundaries and handoffs

The state machine is the only boundary object, and state transitions are the only handoff channel. No agent-to-agent messaging, no shared scratch state: the v2 rule that "the board is the control channel; nothing parses transcript output" extends unchanged to multiple lanes.

Lane ownership follows the item's current state. The dashed rust path is the delivery lane's rework demotion — two hops already legal in MACHINE (board.ts:41-48), landing the issue back in Backlog where board next re-surfaces it by priority. No state-machine change required.

Contested call: who handles CHANGES_REQUESTED and review threads?deliver vs work

Deliver owns mechanical remediation; work owns semantic rework. Mechanical = rebase onto main, conflict resolution that preserves both sides' intent, lint/format fixes, CI retry, re-running attest-pr.sh after a new head, posting @coderabbitai review after fixes (standing permission exists; spend deliberately — each nudge costs a rate-limit unit), and replying in-thread where the answer is already in the diff or the issue. Unresolved GraphQL review threads are the ground-truth work list — deliver replies in-thread, never dismisses a finding by timestamp.

Semantic = anything a reviewer would call a design decision. Deliver demotes: In Review → In Progress → Backlog (both hops legal), posts one findings comment summarizing every unresolved thread, and releases. board next re-surfaces the issue by priority; the next work tick claims it fresh with the findings in the issue history. This deliberately reuses the claim protocol instead of inventing a deliver→work channel.

Contested call: who owns branch topology and stacking?deliver

Deliver owns PR shape end-to-end: splitting an oversized PR, maintaining stacks (git rebase --update-refs), and — critically — retargeting dependent PRs before merging a stack base, because merge-pr.sh merges with --delete-branch and GitHub closes (not retargets) a dependent PR whose base disappears. That known hazard becomes a deliver-lane checklist item rather than a human memory. Work creates PRs in the simplest correct shape; it never manages stacks.

Contested call: who creates issues, and who may close them?tend arbitrates

Any lane may board create (work rule 4 already requires it for deferred findings). Tend owns dedup and formation: merging duplicates, wiring --parent/board dep, and grepping the live tree before trusting an issue body — the repo's documented failure mode is stale backlog items whose deliverables already landed or whose target architecture was deleted by a cutover. Tend never closes-as-stale unilaterally: it proposes via Human Needed with evidence, because close/cancel is the one hygiene action with real blast radius.

Triggers and cadence

Four constraints decide this, and they point at one hybrid rather than a menu:

  • Board signals can only be polled. Projects V2 has no field webhook — the 15-min reconciler in state-guard.yml is the proven pattern, not a compromise.
  • Model lanes must run locally. Cloud routines can't load ralph plugins; launchd/cron driving a local runner (the existing install-loop.sh transport) is the realistic host. GitHub Actions stays what it is: the deterministic corrective wall, never a model lane.
  • Cheap idle-exit is what makes polling affordable. tick.sh:75-79 queries the selector and exits before spawning anything when empty. Elevate this from an implementation detail to the lane contract: every lane MUST have a deterministic selector whose empty result costs an API call, not a model session.
  • Async review state needs settle time. Reviewer/CI state read mid-flight produces false "stuck" verdicts; deliver's selector acts only on signals older than a settle window (~3 min).

Continuous daemons and in-session wake-up loops are rejected outright — v2 killed exactly that ceremony (sentinel manifests, ScheduleWakeup discipline) and recorded a silent-loop-death failure under it. The scheduler owns cadence; every lane run is one mortal process judged by board state, not exit codes.

Capabilities and examples: making agents cheap to create

Scripts are examples; contracts are doctrine. The doctrine line is the mutation path: everything ralph must enforce already lives beneath any script a user could write — claim/scope/state gates in board.ts, merge gates in merge-pr.sh, the corrective wall in Actions. That is precisely why the loop layer can be soft. A shipped lane.sh harness with a lanes registry in .ralph.json would promote a convenience into prescribed choreography — the v1 mistake in shell form. The v2 record already states the right posture: tick.sh is "a convenience, not the architecture," and any command that invokes one session per tick is an equally first-class drive. Users perform their own scripting; ralph makes that scripting easy and safe to write.

So per lane, the plugin ships exactly two kinds of things:

  • Capabilities with hardened contracts — the parts worth typing, versioning, and testing: selectors (board next --json today; board deliver-queue --json and board tend-queue --json as board.ts additions for the board-derived halves of eligibility), the grep-parseable MERGE GATE PASS/PENDING/FAIL + exit 0/1/75 contract, claim/TTL semantics, and readiness willing to read a heartbeat or outcomes file wherever a user's script declares one.
  • One example loop script per lane — a reference composition to copy and rewrite, owned by the user the moment it's copied, the same way host repos own their merge flow. Ralph never executes it for you.
# deliver-loop.sh — EXAMPLE composition. Copy it, rewrite it, own it.
# The stable part is the contracts it leans on, not this script:
#   board list --state 'In Review' --json      typed selector (board.ts)
#   scripts/merge-pr.sh → exit 0 / 1 / 75      gate contract, grep-parseable
#   claim TTL + release                        enforced in board.ts, beneath this script
grep -q '^autopilot.deliver=true' "$HOME/.ralph/config" || exit 0   # fail-closed opt-in — keep this
[ -n "$ANTHROPIC_API_KEY" ] && [ "$RALPH_ALLOW_API_BILLING" != true ] && exit 3  # billing guard — keep this
exec 9>"$HOME/.ralph/spawn.lock"; flock -n 9 || exit 0    # share ONE spawn lock across your loops
date +%s > "$HOME/.ralph/deliver.heartbeat"
ID=$(./deliver-queue.sh) || exit 0                         # idle-exit: empty queue spawns no model
timeout 15m claude -p --model sonnet "/ralph:deliver $ID"
echo "$(date -u +%FT%TZ) deliver GH-$ID rc=$? checked=$N acted=$M" >> "$HOME/.ralph/deliver.outcomes.log"

The conventions the example carries — and what enforces each one:

  • One shared spawn lock, skip-don't-queue keeps the claim protocol's "one flock-serialized scheduler per machine" assumption literally true: a deliver fire during a 45-min work tick skips and retries next interval. This is a convention the examples follow, not a rule ralph checks — lanes are state-disjoint, so a user who drops it loses a safety margin, not an invariant. Loosen it in your own scripts on contention evidence, not principle.
  • Fail-closed opt-in and the billing guard travel with the example, not the enforcement layer. That is acceptable — they guard the user's own spend and machine, not board integrity — but it is exactly why they sit at the top of the example, prominent enough that copies inherit them by default instead of discovering the need later.
  • Proof-of-input outcome lines (checked=N acted=M) make a dead lane visibly dead, never silently green (waystone W1). readiness detects-if-present and recommends: "your deliver loop emits no outcome lines" is a level-3 recommendation, never a gate. doctor stays what it is — board invariants — and never audits user scripts.
  • Selectors live in code, judgment lives in the skill. Deliver's eligibility test (checks concluded ∧ settle age ∧ head-binding) is deterministic — the funnel test assigns it to typed code ralph ships and maintains. What to do about a failing check is judgment the skill owns. The user's script is just the wire between them.
  • Creating a new agent = one SKILL.md plus your own scripting. The skill (auto-registered from ralph/skills/<lane>/, no manifest edit) is the plugin-shipped judgment; the loop is yours, started from an example. "Easy to create" is honest here because the contracts carry the weight — not because ralph runs the loop for you.
! What deliberately does not exist: no lanes registry in .ralph.json, no lane.sh harness ralph executes, no lane priorities, no lane-to-lane messaging, no scheduler-side routing, no orchestrator agent, no --force. The v2 record vetoed scheduler-side choreography once already; lanes coordinate only through board state, exactly as work sessions already coordinate through claims.

Cost and model tiers

Sonnet drives every lane. The existing tier policy transfers unchanged: haiku only for mechanical fan-out inside a session, frontier only as in-session bookends on feature/epic units, never as a driver — a five-lane split would tempt per-lane haiku drivers, but deliver's judgment calls (is this conflict resolution semantic?) are exactly where a cheap model quietly does damage. The selector, not the model tier, is the cost control: idle polls cost API calls only.

idle poll: ≈ $0 (gh API only) deliver pass: short session, bounded 15 min measured CI cost: ~55–75 billed min / PR pilot datum: ~40 PRs/day tripped a spending cap CodeRabbit nudge: 1 rate-limit unit each

The measured PR cost model cuts for the deliver and tend lanes, not against them: marginal CI cost is per-PR and size-independent, so the expensive failure mode is PR count — stranded PRs re-pushed into fresh ones, duplicate work from stale backlog items, abandoned branches. Deliver shepherds existing PRs to merged instead of letting them rot; tend kills duplicate work before it forks a branch. Both lanes should net-reduce PR count. The loop's own token spend is bounded by cadence × timeout per lane — knobs that live in scripts and schedules the user owns, not in plugin config.

Grading the lanes on the waystone ladder

Each lane exists to close a named edge, and each gets graded like any other subsystem — the ladder is the shared maturity vocabulary, so the design targets are stated as rungs:

Open questions

Thread-reply depth for deliver. decide at Phase 1
Replying in-thread is ground truth for review handling, but where is the line between "answer already in the diff" and relitigating a finding? Proposal: deliver replies only with evidence links (commit, line, test run), never with argument; anything argumentative demotes to rework.
Host repos without the merge gate. decide at Phase 1
Deliver must degrade gracefully where scripts/merge-pr.sh doesn't exist (recommend-never-impose): fall back to the repo's own merge flow and native checks, and let board readiness report the gap — never require the gate.
Rework demotion: two-hop vs a direct edge. decide with usage data
The two-hop In Review→In Progress→Backlog works today with zero schema change. If rework turns out to be frequent, a direct In Review→Backlog edge in MACHINE is a one-line, contract-tested change — but add it on observed frequency, not anticipation.
Per-lane holder identity. Phase 1 detail
RALPH_CLAIM_HOLDER should carry the lane (deliver@host vs tick@host) so eviction comments, doctor output, and the decision journal say which lane acted — cheap provenance, zero protocol change.
