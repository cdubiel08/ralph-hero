## Strengths

1. **Discovery notes pattern is excellent.** Constraints #11-13 explicitly call out side-effects that implementers could miss (e.g., `clearAll()` needs a new `DELETE FROM chunks`; vector table column stays `id` but row values become chunk ids; bumping `SCHEMA_VERSION` auto-triggers re-embed via existing path). These are exactly the "gotchas" that cause bugs when plans are followed mechanically.

2. **Phase dependencies are explicit and correct.** The `depends_on:` line on each phase plus the overall graph (`Phase 1 -> everything`; `Phase 4/5/7 parallelizable after 3`; `6 needs 5`; `8 needs 1+3`; `9 -> 8`; `10 -> 9`; `11 -> 9+10`) maps cleanly to the acceptance criteria and reflects real technical dependencies.

3. **Fail-open semantics are specified precisely.** Phase 5's LLM client acceptance (`contextualize()` returns `""` on network/timeout/parse error, `available()` returns `false` on any error) is testable and matches the "survive unreachable Gemma" constraint.

4. **TDD + complexity flags per task.** Every task has `tdd: true/false` and `complexity: low/medium/high`, which is useful for orchestrators picking work units.

5. **Verification steps are specific.** Each phase has automated + manual verification with runnable commands (`sqlite3 ... ".schema chunks"`, `launchctl list | grep ...`, `knowledge_search --memory_tier reflection`). No vague "it should work" criteria.

6. **Back-compat handling called out.** Multiple places (Task 4.1 `content?: string` optional, Task 3.1 `prepareTextForEmbedding()` kept for back-compat, Task 4.3 "when `hit.id` has no `#c`, treat as docId") explicitly preserve non-chunks callers so fixtures and pre-v3 vec rows keep working.

7. **Out-of-scope section is crisp.** The list of "not doing" (model swap, per-project DB, screenpipe, reflection-of-reflections, OAuth, full-corpus backfill) prevents scope creep during implementation.

## Minor Observations (non-blocking)

These are worth noting but do not warrant rejection or iteration:

1. **Phase 1 (GH-762) Task 1.1 `context_prefix` column.** The plan adds `context_prefix TEXT NOT NULL DEFAULT ''` to the `chunks` table in Phase 1, but the column isn't *used* until Phase 6. This is fine — adding columns later via `ALTER` would be messier. Just noting that Phase 1 tests should not assert context_prefix population since that happens in Phase 6.

2. **Phase 3 Task 3.4 stale deletion nuance.** The task says "chunks themselves cascade via `ON DELETE CASCADE` on `chunks.document_id` when `deleteDocument(id)` runs" — this is correct, but `documents_vec` rows for the deleted chunks do NOT cascade (virtual tables don't participate in FK cascades). The task correctly addresses this via the new `deleteChunkVecsByDoc(docId)` method. Good catch in the plan; no issue.

3. **Phase 6 Task 6.4 content-hash cache.** The task author explicitly notes "Implementer may opt to defer the content-hash logic and rely on mtime only; document this choice in a comment." This is a reasonable escape hatch. The current mtime-based skip at `reindex.ts:68-73` does indeed already catch the unchanged-doc case. The only gap is: mtime same but content different (e.g., touch without edit) — an edge case. Acceptable to defer.

4. **Phase 8 Task 8.2 vector-only post-filter performance.** "HybridSearch post-filters vector-only results by re-fetching `doc.memory_tier` (when `memoryTier !== 'any'`, skip docs whose memory_tier differs)" — this N+1 lookup is fine at current corpus scale (few thousand docs) but could be optimized later by joining to `documents` in the `VectorSearch.search()` LEFT JOIN established in Phase 4 Task 4.1. Not worth addressing now.

5. **Phase 9 line count trimming.** Phase 9 ingester shells out to `git log ... -n 50`. At high-commit-volume repos over a 24h window this may hit the cap and silently drop commits. Low priority because the dream-loop runs nightly and will catch up; and 50 commits/24h/repo is generous.

6. **Phase 11 plist personal-path hardcoding.** The plist template hardcodes `/Users/dubiel/...` paths and `com.dubiel.dream-loop` label. The plan does call this out implicitly (it's in the user's `~/Library/LaunchAgents/`) but the "template" naming suggests portability. For a user-local nightly job on one machine, this is fine. If we ever publish this for others, the template should use `__USER__` placeholders.

7. **Phase 3 Task 3.4 "embed" change is unbounded.** The plan removes the 500-char slice in Phase 3 Task 3.1 and notes "transformer's own 512-token window handles overflow." Worth verifying: does the Xenova `all-MiniLM-L6-v2` pipeline truncate silently or error on inputs > 512 tokens? If the former, fine. If the latter, tests with long content might surface the issue. The plan doesn't test this explicitly but covers it implicitly via Phase 3 Task 3.3 "8K chars returns array with length >= 4" which proves the chunker slices before embedding.

None of these rise to "NEEDS_ITERATION." They are observations for the implementer.

## Risk Assessment

| Risk | Severity | Mitigation in plan |
|------|----------|--------------------|
| Schema v3 migration breaks existing v2 DBs | Medium | Existing migration pattern at reindex.ts:25-30 auto-drops sync + re-embeds. Plan relies on this. |
| Chunker algorithm bugs lose content | High | Phase 2 Task 2.2 invariant `text.slice(chunk.charStart, chunk.charEnd) === chunk.content` is the safety test. Unicode/code-fence tests in Task 2.3. |
| LLM hang blocks reindex | High | `available()` probe has 2s timeout; `contextualize()` has 30s timeout; both fail open. |
| HDBSCAN clustering produces no reflections on small corpus | Medium | `min_cluster_size=5` is sensible but day-1 corpus may be < 5 memories. Noise-only result is acceptable (reflect.py returns nothing, no error). |
| launchd job silently fails | Medium | stdout/stderr piped to `/tmp/dream-loop.out`; manual verification step includes `launchctl list` check. |
| Contextualization cost explosion | Medium | Cache-hit logic in Task 6.4 avoids re-calling LLM on unchanged docs. Mtime-only fallback is acceptable. |
