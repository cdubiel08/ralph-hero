# Plan Critique: GH-1171 (group plan, 5 phases)

**Verdict**: APPROVED

## Summary

Group plan to fix project-wide MCP read-path 500-item silent truncation. Phase 1 extends the shared `paginateConnection` helper with `scanUntilExhausted`, an `until` predicate, and a `truncated` return flag. Phases 2-4 each switch one downstream call site (`list_issues`, `fetchDashboardItems`, `list_groups`) and add tool-description updates plus regression tests. Phase 5 adds a cross-tool consistency test asserting `list_issues` and `pipeline_dashboard` see the same OPEN issues per workflow state.

The plan is unusually thorough for a 5-phase atomic group: every line reference checks against current source, every shared constraint maps to a documented research finding, and every phase explicitly states what it creates for the next phase.

## Strengths

1. **Empirical anchoring**: cites concrete numbers (734 items, item #1102 at position 640, page 7 boundary) from the linked research, so Phase 5's fixture choices have a defensible rationale.
2. **Backward-compat discipline**: shared constraint #1 + Task 1.2's "byte-identical output for callers passing only `pageSize`/`maxItems`" + the `truncated: boolean` returned default of `false` together form a tight backward-compat contract.
3. **Capture of the fourth call site**: the plan separately handles `directions-tools.ts:389-395` in Task 3.2, even though the issue body only mentions "three call sites." This is correct — `directions-tools` has its own inline `paginateConnection` invocation that bypasses `fetchDashboardItems`.
4. **Negative test included**: Task 1.4 is a verification-only task confirming `bulk-archive.test.ts:333-334` (the assertion that `paginateConnection` is NOT used in `project-management-tools`) survives. Cheap insurance against accidental cross-talk.
5. **Phase 5 manual revert check**: the manual verification "temporarily revert Phase 2 and Phase 3 changes locally and rerun this test" is a strong correctness signal — the test exists to catch regressions, and the planner says how to confirm it would.

## Minor Observations (non-blocking)

These are polish items, not failures:

1. **Phase 1 Task 1.2 `console.warn` content**: the acceptance says the warning "includes the connection path, `maxItems`, and the `totalCount` if available" — this is fine for consumers, but the implementer might want to also include a hint to migrate to `scanUntilExhausted`. Not required by acceptance; up to implementer judgment.
2. **Phase 5 fixture realism**: the fixture uses 7 pages × ~100 items totaling 734. This matches research evidence. Worth noting that it does NOT exercise the `until` predicate (Phase 2/3 callers don't use it). That's fine — Phase 1's `pagination.test.ts` covers `until` behavior in isolation.
3. **`PaginateOptions` -> `PaginateOptions<T>` migration**: Task 1.1 acceptance says "confirm callers compile after this signature change." Currently no caller imports `PaginateOptions` by name (verified via grep — all callers pass options inline as object literals). The change is safe, but flagging for the implementer to re-grep at implementation time in case a future PR lands first.

None of these block approval.
