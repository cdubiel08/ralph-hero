# GH-1136 Plan Critique

**Plan**: [2026-05-07-GH-1136-autopilot-skill.md](https://github.com/cdubiel08/ralph-hero/blob/main/thoughts/shared/plans/2026-05-07-GH-1136-autopilot-skill.md)
**Verdict**: NEEDS_ITERATION

## Summary

The plan is well-researched, technically literate, and the architectural premise (skill calls `ScheduleWakeup` itself with `<<autonomous-loop-dynamic>>`/self-prompt; coexists with `ralph-loop.sh`) is sound. However, three concrete issues prevent approval as-is: (1) hero's resumability assumes per-session `TaskList` state but the plan reuses hero across cross-tick fresh-context fires, which causes redundant work or stale-task confusion; (2) the cache-window heuristic for "PR awaiting CI" undershoots typical CI duration; (3) the audit-log-as-state-vehicle is more fragile than the obvious alternative (encode state in the `prompt` field of the next ScheduleWakeup). Plus a couple of smaller scope/sizing concerns. None require a redesign — they're targeted plan edits before implementation.

## Dimension Scoring

### 1. Completeness — PASS WITH NOTES

Five phases, each with `Overview`, `Changes Required`, `Success Criteria` (Automated + Manual). The phase boundaries are sensible (scaffold → tick body → loop+termination → audit/safety → docs). Phase 1's success criteria correctly defer the looping behavior to Phase 3, and the Implementation Note pause is appropriate.

Gaps to fix:
- Tasks are described inline but do not include the dispatchability table (`files`, `tdd`, `complexity`, `depends_on`, `acceptance`) per the canonical quality-standards. Each phase should be split into discrete tasks with these annotations so an impl agent can execute one phase without reading the whole plan.
- Phase 5's CLAUDE.md edit and README.md edit are mentioned but not pre-drafted — the implementer should not have to invent the prose.
- Token-cost estimation (Phase 3, Step 6, condition 5) is hand-waved (`coarse $0.01-per-1k-output-token estimate ... falling back to a fixed $0.50/tick estimate`). This needs a concrete acceptance: where does the per-tick cost actually come from? Hero does not currently surface a token tally back to its caller.

### 2. Feasibility — FAIL on three claims

Verified what's verifiable:

- `next_actions(audience="agent")` exists in `plugin/ralph-hero/mcp-server/src/lib/directions.ts` with `audiencePenalty()` at line 270 and `ESTIMATE_PENALTY` at line 211. CONFIRMED.
- `__ESCALATE__` resolves universally — true by inspection.
- `HUMAN_STATES` excluded from `ACTIONABLE_PHASES` — true.
- Hero's resumability section at `plugin/ralph-hero/skills/hero/SKILL.md:491-499` exists. CONFIRMED but see issue (a) below.
- No existing skill anywhere in `plugin/` calls `ScheduleWakeup` (`grep -rn ScheduleWakeup plugin/` returns zero results). CONFIRMED — the hook gate cannot break any current skill.
- `set-skill-env.sh` writes to `$CLAUDE_ENV_FILE`; the env var only persists across Bash invocations within the **same session**, not across ScheduleWakeup re-fires which are documented as fresh contexts. This is a critical gap — see issue (b) below.

Concrete failures:

**(a) Hero re-entrancy across ScheduleWakeup ticks is unverified — possibly broken.**

Hero's documented resumption (lines 491–499) uses TWO sources of truth:
1. `get_issue(includePipeline=true)` — server-side (GitHub project board) — survives fresh contexts.
2. `TaskList()` — per-session — does NOT survive a ScheduleWakeup re-fire (the docs the plan itself cites describe ScheduleWakeup as starting a fresh turn, and `TaskList` is per-session).

Per-tick this is mostly fine because each autopilot tick targets a *different* root issue (one issue per tick). But there is a real failure mode: if hero on tick 1 makes partial progress on issue #500 (e.g., research done, plan in review) and hero is dispatched again on tick 2 for issue #500 (because it's still the top action) — hero will rebuild its TaskList from `get_issue(includePipeline=true)` and will *not* see the in-flight plan-review state from tick 1's session unless GitHub state already reflects it. That's mostly OK in steady state, but the plan does not analyze it.

More importantly: when autopilot picks issue #501 on tick 2 (after issue #500 advanced past one phase on tick 1 but is still actionable), hero starts fresh against #501 — fine. But if tick 1 was interrupted mid-implement and hero left a worktree behind, tick 2's hero fires in a **new context** with no awareness of that worktree. The plan doesn't address worktree liveness across ticks, even though `impl-worktree-gate.sh` is one of the most important gates in the codebase.

Required plan additions:
- A subsection under "Resumability and tick-isolation" explicitly stating: "Each tick is a fresh context. Hero's TaskList is rebuilt from GitHub state. Worktrees from previous ticks are NOT visible to the current tick's agent — autopilot MUST verify worktree state via `git worktree list` at the start of each tick if hero is to be re-dispatched on an in-flight issue."
- Explicit handling for "tick N picks the same issue tick N-1 was working on" — likely identical to the no-progress-streak path, but the plan should say so.

**(b) RALPH_COMMAND across ScheduleWakeup fires is unverified.**

The plan's hook gate (`autopilot-wakeup-gate.sh`) checks `RALPH_COMMAND=autopilot`. This works on tick 1 because `SessionStart` runs `set-skill-env.sh RALPH_COMMAND=autopilot` and the var persists for that session's bash calls. But ScheduleWakeup fires a NEW turn — does `SessionStart` re-fire? If yes, the hook works (the new turn IS a new session start in some interpretation). If no, the hook gate will block every continuation tick after the first.

The plan does not investigate this. There are two outcomes:
- If SessionStart re-fires per ScheduleWakeup turn: the gate works; document this assumption.
- If it doesn't: the gate is broken on ticks 2+ and the plan fails to terminate cleanly.

A safer design: the hook gate should also accept a sentinel in the `prompt` field — e.g., `prompt` matches `^/ralph-hero:autopilot` is *itself* sufficient evidence the call is autopilot-driven. The plan already requires that match (gate line `^/ralph-hero:autopilot`), so the additional `RALPH_COMMAND` check is redundant defense and possibly broken. Either drop one check or document why both are required.

**(c) Cache-window heuristic for CI is wrong.**

Plan picks 270s (`Hero completed but PR is awaiting CI`). GitHub Actions for this repo (per `ci.yml`: build + test across Node 18, 20, 22 for three plugins) typically takes 4–8 minutes. 270s = 4.5 minutes — best case the wakeup fires while CI is still running, the agent re-checks, finds no merge possible, falls into the "no-progress" path, and burns a streak slot.

This is the exact 5-min cache-window trap, just inverted: by *ending* the cache window 30 seconds before CI typically completes, you guarantee a tick that does no useful work AND incurs a cache miss.

Two cleaner choices, both covered by the existing 1200/1800 buckets:
- 1200s (20 min) — let CI finish, accept the cache miss, do useful work next tick.
- Don't dispatch a "CI-awaiting" tick at all — finish skill already has a dedicated CI-watch loop (`finish/SKILL.md:142-162`); autopilot's "PR awaiting CI" outcome should treat the issue as "done for this loop iteration" and move to the next backlog item.

The second option is much simpler — autopilot is a dispatcher, not a CI babysitter. Document that PR-awaiting-CI is a "tick complete, move on" outcome, not a "wait" outcome.

### 3. Clarity — PARTIAL PASS

Many success criteria are specific and testable (e.g., `delaySeconds is not exactly 300`, `audit log file is created on first tick`, `each audit log line is valid JSON`). Good.

Weak spots:
- "No infinite-loop possibility — every code path either calls ScheduleWakeup OR exits, never both, never neither (read the skill body and confirm by inspection)" — this is asking the reviewer to manually verify a property the plan should prove constructively. Replace with an explicit invariant table mapping {outcome} -> {schedule | stop}, then the reviewer checks the table is exhaustive.
- "Hero will report back via text output. Capture three signals from its output: ... look for 'COMPLETE' or 'PR URL' markers" — string-grepping hero's free-text output is exactly the fragility the plan calls out as wrong in `ralph-loop.sh` ("queue-empty detection ... is fragile string-matching"). The plan replaces one fragile grep with another. Required: a structured outcome contract — either hero adopts a JSON-tail summary line, or autopilot reads `get_issue(includePipeline=true)` *after* hero returns and derives outcome from the post-state vs. the pre-state. The latter is no-code and reuses existing tooling.

### 4. Scope — PASS WITH NOTES

"What We're NOT Doing" is explicit and well-bounded (8 bullets, each correctly scoped). The non-replacement of `ralph-loop.sh` is wisely called out.

But two scope items deserve a closer look:

**(d) Five termination conditions is over-engineered for an MVP.**

Specifically:
- Condition 1 (backlog empty) — keep, primary stop.
- Condition 2 (escalation this tick) — keep, hero already raises this and it's structured.
- Condition 3 (no-progress streak >= 3) — keep, mirrors `code-review-agent`'s proven 3-round limit.
- Condition 4 (`iteration > MAX_ITERATIONS`) — keep, hard ceiling.
- Condition 5 (budget cap) — defer. The plan itself acknowledges the token-tracking is `coarse` and `falling back to a fixed $0.50/tick estimate`. A flat-rate fallback is functionally equivalent to MAX_ITERATIONS at a different ratio — the two conditions overlap. Drop budget cap from MVP, ship MAX_ITERATIONS only, and add real token tracking later when hero surfaces a structured token tally.

Saving condition 5 for a follow-up reduces the implementation surface and removes the most hand-wavy success criterion.

**(e) Plan claims pure markdown, but adds a hook script — that's fine, but Phase 4 is the only phase that touches shell.**

The phase split correctly isolates this. No issue here, just confirming.

### 5. Dispatchability — FAIL

The plan describes phases with prose ("Append the dispatch and outcome-capture sections", "Append loop scheduling and termination sections") rather than discrete tasks with the required dispatchability table.

For an impl agent to execute phase 2 without reading phases 1, 3, 4, 5, each phase needs:

| Field         | Status  |
|---------------|---------|
| files         | partial — referenced inline but not enumerated as a list |
| tdd           | absent — none of the phases declare TDD posture |
| complexity    | absent |
| depends_on    | implicit (sequential phases) but not stated |
| acceptance    | present (Success Criteria sections) — but tied to manual verification, not testable assertions |

Required: rewrite each phase intro as a task block that an impl agent can read in isolation. The Phase 1, 2, 3, 4, 5 ordering is fine — but each phase should be tagged `depends_on: [previous-phase]` explicitly.

For multi-issue group plans this would also require integration testing across phases, but this is a single-issue plan so that's N/A.

## Issues Summary (for the iteration response)

1. **Hero re-entrancy and worktree liveness**: add a "tick isolation" subsection covering (a) `TaskList` does not persist across ScheduleWakeup ticks (only `get_issue(includePipeline=true)` does), and (b) worktrees from previous ticks are not visible — autopilot must `git worktree list` at the start of each tick if it might re-dispatch hero on an in-flight issue.

2. **`RALPH_COMMAND` gate semantics across ticks**: investigate whether `SessionStart` re-fires per ScheduleWakeup turn. If not, the hook gate is broken on tick 2+. Either confirm SessionStart fires (and document) or drop the `RALPH_COMMAND` check (the `prompt =~ ^/ralph-hero:autopilot` check is sufficient evidence).

3. **CI cache-window heuristic is wrong**: 270s undershoots typical CI duration (4–8 min). Either bump to 1200s, or — better — drop the "PR awaiting CI" path entirely and treat it as "tick complete, move on." Autopilot is a dispatcher, not a CI babysitter.

4. **State-passing via audit log vs prompt field**: passing `--iteration N --resume-token X` in the `prompt` field of the next ScheduleWakeup is more robust than re-reading the audit log's tail every tick. The audit log should be append-only audit; tick-to-tick state should ride on the prompt. Reduces file-race and stale-state risks.

5. **Outcome-detection fragility**: replace string-grepping hero's text output (`look for 'COMPLETE' or 'PR URL' markers`) with a structured signal — either a JSON-tail line from hero or, simpler, a pre/post `get_issue(includePipeline=true)` diff that derives outcome from the workflow state delta.

6. **Defer budget-cap termination (condition 5)**: token-cost estimation is unverified (hero does not surface tallies). Drop to MAX_ITERATIONS-only for MVP; add real budget tracking in a follow-up issue once token telemetry exists.

7. **Dispatchability**: each phase needs explicit `files / tdd / complexity / depends_on / acceptance` annotations so an impl agent can execute a phase in isolation.

8. **Pre-draft README and CLAUDE.md prose** in Phase 5 — don't make the implementer invent the docs.

## Sizing

The plan is sized **M**. Given the resumability and outcome-detection rework above (which require small but non-trivial edits to either hero's contract or autopilot's state-derivation logic), the issue is **closer to M-going-on-L** if all eight issues are addressed in one iteration. If issue 6 (drop budget cap) is taken, scope contracts back to M cleanly. Recommend the planner take issue 6 as scope-shrink and keep the issue at M.

## Verdict

NEEDS_ITERATION. The architecture is right; the safety-rail discipline (env-var opt-in + hook gate) is exactly the standard this codebase uses for autonomous skills; the audit log + 60/270/1200/1800s discipline is sensible. The issues are concrete and addressable in a plan revision (no redesign needed).

After the revision: the plan should re-enter review.
