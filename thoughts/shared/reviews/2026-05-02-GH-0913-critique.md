# GH-913 Plan Critique — Reindex Heap Regression Microbenchmark

VERDICT: APPROVED

The plan is a clean, additive, three-phase guard for the OOM fix from #907 (#911 + #916). ### 3. Clarity — PASS

Success criteria use the canonical `- [ ] Automated:` / `- [ ] Manual:` format with specific, testable predicates. Examples:

- "Bench completes in under 60 s on M5 Pro" — measurable
- "TSV row's `peak_heap_used_mb` falls in 30-150 MB range and `peak_rss_mb` falls in 350-550 MB range" — bounded, falsifiable
- "CI fails on a PR that reverts `output.dispose()` in `embedder.ts`" — directly verifiable

The bad-commit verification recipe in Phase 2 is reproducible: explicit `grep -n "output.dispose"`, comment out, rebuild, run, restore. Threshold tuning recipe in the README addition (95th-percentile × 2) gives future maintainers a deterministic recalibration procedure.

The plan correctly distinguishes the bench's role from existing `reindex.test.ts` — the test mocks the embedder (`vi.mock("../embedder.js", ...)` at line 14), so the regression we're guarding against (a real `dispose()` removal) is invisible to vitest by design. A bench that calls the real `embedDocument()` is the only place this regression can be caught short of a full live-corpus reindex.

### 4. Scope — PASS

"What We're NOT Doing" section is detailed and well-bounded:

- Not measuring throughput (clear non-goal)
- Not running against live corpus (explicit reproducibility argument)
- Not adding vitest test (explicit technical justification — the mock would defeat the guard)
- Not auto-committing the bad-commit revert
- Not adding Node-version-specific threshold matrix
- Not changing `package.json` engines / dev deps
- Not modifying `embedder.ts`, `chunker.ts`, or `reindex.ts`

This last bullet is critical: a regression guard that modifies the code it guards is anti-self-validating. The plan correctly keeps the guard purely additive.

The scope respects the XS estimate. Three phases × small file changes each, with no novel infrastructure. The CI hook (Phase 3) is the only piece with non-local risk, and the plan flags this explicitly ("Phase 3 is the only one that can't be fully verified locally — observe the first few PRs that land after merge").

## Minor Observations (Non-Blocking)

These are noted for the implementer but do not block approval:

- **`pathToFileURL` import in stubs**: Phase 1's TypeScript scaffolding imports `pathToFileURL` from `node:url` but does not show it being used. The reranker template uses it in the `isMain` check. Implementer should keep it for the same `isMain` pattern, or drop the import if a different `isMain` form is chosen.
- **Chunk-count query**: Phase 1's stub leaves `chunk_count: /* … */` as a placeholder. The plan implicitly suggests `better-sqlite3` direct query against the tmp DB; the implementer should pick `SELECT COUNT(*) FROM chunks` (the schema is created in `KnowledgeDB`'s constructor via `reindex` itself).
- **`appendOrCreateTsv` semantics**: Phase 2 introduces an append-mode TSV writer (vs reranker-bench's overwrite). The implementer must handle the header row carefully — write it only when the file does not yet exist, otherwise append data rows only. This is clear from the plan's reasoning ("multiple runs on the same day should append rows, not overwrite") but the implementation note is worth highlighting.
- **CI `timeout-minutes: 5`**: 5 minutes is generous and the plan justifies it (model-download cold-start). On warm cache the bench should finish in well under 2 minutes; the timeout is there for the first runner-cell-cache miss. Acceptable.
- **External memory tracking**: The plan tracks `peak_external_mb` but does not assert against it. This is correct — `external` is dominated by the transformer's native ONNX buffers, which are normal load. Tracking-only is the right call so the data is in the TSV for future trend analysis.

None of these are blockers. They are implementation hints the executor will hit naturally.
