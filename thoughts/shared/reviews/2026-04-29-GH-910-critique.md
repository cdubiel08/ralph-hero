## Strengths

- **Treats LLM client as a confound to remove**, not a target. `RALPH_CONTEXTUAL_RETRIEVAL=0` for the headline run isolates the leak to the embedder + sqlite-vec + accumulator triad, exactly matching the audit's observation that contextual retrieval reduces but does not eliminate the OOM.
- **Two-data-point methodology**. Default 4 GB run (proves OOM) plus 8 GB run (deeper corpus walk) gives a per-doc growth rate computation, which is more diagnostic than either run alone.
- **Microtask-queue hypothesis surfaced**. The plan explicitly notes that if the V8 microtask queue is the actual retainer (not heap data structures), the fix shape changes from "release tensors" to "yield to macrotask queue (`setImmediate`) between chunks". This is non-obvious reasoning that the planner extracted from the audit's stack trace and forwards to the analysis task — exactly the kind of upstream thinking that prevents a wasted fix in a sibling.
- **Branch for unanticipated retainer**. Task 1.6 has explicit "if dominant retainer is NOT one of the four sibling-mapped suspects, file a new ticket and redirect sibling scopes via comments". Plan does not over-commit to the audit's hypotheses.
- **Recoverable DB state**. Backing up `~/.ralph-hero/knowledge.db` via rename rather than delete is a correct safeguard — the on-disk corpus is regeneratable from `~/projects/thoughts/` but the chunked embeddings and index-graph state would be expensive to re-derive.

## Minor Observations (not blocking)

- Line-number drift noted above. Trivial.
- Task 1.4 references `node-heapdump-analysis` as an alternative to Chrome DevTools. That npm package may not exist; the plan offers DevTools as the primary path, so the fallback is decorative. Could be tightened in iteration but not blocking.
- The "Heap Profile Artifacts" section in Task 1.5 conditions committing the snapshot on `<1 MB and not user-data-sensitive`. Heap snapshots from a 1.7k-doc corpus will likely exceed 1 MB and may contain document content fragments — committing them is unlikely to be appropriate. This is correctly handled by the conditional, but the plan could spell out the default expectation (commit a summary, store the raw artifact in `/tmp/`).

## Suspected-Retainer Audit (mapped to sibling tickets)

The plan's Current State Analysis already pre-classifies the four suspects from the issue body and maps each to a sibling owner. This is appropriate calibration work — the analysis task (1.4) just has to confirm or refute each.

| Suspect | Plan's pre-classification | Sibling owner |
|---------|---------------------------|---------------|
| Transformer tensor cache (per-call output.data alias) | Likely contributor | #911 |
| `Float32Array` chunks accumulating | Small in absolute terms unless tensors aliased | #911 |
| `parsedDocs[]` accumulator | ~17 MB at 1,700 docs in absolute terms — small unless deep retention | #911 |
| sqlite-vec per-chunk INSERT allocations | Plausible buffer retention, no transaction batching | #912 |
| LLM `contextualize` response accumulation | At most a contributor, since `RALPH_CONTEXTUAL_RETRIEVAL=0` only reduces OOM | already excluded from headline run |

The plan correctly notes that all four hypothesized in-heap retainers are *small in absolute bytes* at the 1.7k-doc scale, which is what makes the microtask-queue hypothesis interesting — the actual retainer may not be a heap object at all.
