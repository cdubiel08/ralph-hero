## Gaps

- **[File ownership — Phase 1] The `detectWorkStreams` survival claim is wrong.** Phase 1 states "detectWorkStreams is still consumed by the dashboard streams section." It is not: `pipeline_dashboard`'s `streams` param takes pre-computed assignments and `lib/dashboard.ts:24` defines its own local `WorkStream` interface — the only non-test consumer of `detectWorkStreams` is the `detect_stream_positions` handler being deleted (`dashboard-tools.ts:338`). The only other reference to the lib is a type-only import in `lib/pipeline-detection.ts:10`, used by `detectStreamPipelinePositions` — which Phase 1 also deletes. So after Phase 1, `lib/work-stream-detection.ts` is fully orphaned, and the test directive "`work-stream-detection.test.ts` (keep — lib survives)" points the implementer at keeping dead code — the opposite of this wave's goal. The phase's own "verify with grep before deleting" hedge makes this self-correcting rather than breaking, hence GAP not FAIL.

## Recommended Changes

Non-blocking; apply during implementation or as PR-review notes:

1. **Phase 1**: correct the `detectWorkStreams` claim. Expected outcome of the grep-verify step: `lib/work-stream-detection.ts` and `work-stream-detection.test.ts` are deleted along with the tool (and the now-dead `type WorkStream` import in `pipeline-detection.ts:10`), or a deliberate keep is recorded. Either way, do not leave the "lib survives" note as-is.
2. **Release semantics**: seven tool removals ride `release.yml`'s default patch bump. Consider putting `#minor` in the merge commit message (per CLAUDE.md's CI section) so the npm version signals the surface break to downstream `ralph-hero-mcp-server` consumers. The plan handles release *notes* well; the version *number* is the one release consequence it doesn't address.
3. **Phase 3**: specify the `capture: true` × `format: "markdown"` interaction on `metrics_trends` (today `format: "markdown"` returns `{markdown}` only — say whether the snapshot row is included, or restrict capture to json format).
4. **Phase 6 sweep note**: the `cross-tool-consistency.test.ts:125-126` fixture is a project-item (list_issues-shaped) mock, not a `get_issue` mock — the phase's guarded wording ("that mock get_issue") already prevents a wrong edit; just don't retarget that particular fixture.
5. **Phase 3 naming**: the guard skips parents with ANY children (`subIssuesSummary.total > 0`), mirroring `hygiene.ts:142` exactly — but "open-children guard" prose in Desired End State could read as open-only. The `skipped` reason string `open-or-any-children` already acknowledges this; keep the release-notes wording precise ("parents with sub-issues").
