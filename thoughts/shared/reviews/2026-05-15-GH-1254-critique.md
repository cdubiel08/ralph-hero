## Section-by-Section

### Completeness — PASS

- Single phase with six tasks; phase definition is appropriate for an S-estimate ticket. No bloat.
- Each task names the file to create/modify, the dependency graph, and per-bullet acceptance criteria.
- Phase Success Criteria are split into Automated (9 bullets, all script-runnable) and Manual (7 bullets, requires `pi` + `mlx-openai-server`) — matching the standard `automated:` / `manual:` convention.
- Integration Testing section adds 6 end-to-end checks across cache hit/miss, JSONL run-log row format, skill discoverability, and stub-mode pointer messages.

### Feasibility — PASS

- The pre-flight verification section (lines 51–58) is unusually rigorous: each claim cites a specific file path with line number where applicable.
- Spot-checked from this critique session:
  - `plugin/ralph-hero/scripts/cos/cos.sh` exists with the documented `[--role <name>] [--help] <prompt>` surface and `~/.ralph-hero/cos/runs/YYYY-MM-DD.jsonl` log path (confirmed in shebang block).
  - `plugin/ralph-hero/justfile` line ~57 (`pick:`) calls `_mcp_call` directly; recipes 83+ (`triage *args:`, etc.) `source` cli-dispatch.sh — confirms both patterns coexist.
  - `plugin/ralph-hero/scripts/ralph-cli.sh:124` pre-flight check uses `just --summary` exactly as the plan claims.
  - All four precedent files referenced in the References section exist.
- **Minor finding (non-blocking):** The Prior Work section references two files that do NOT exist on disk:
  - `thoughts/shared/plans/2026-05-14-GH-1252-ralph-hero-cos-mode.md` (parent plan-of-plans) — absent
  - `thoughts/shared/research/2026-05-14-pi-coding-harness-as-chief-of-staff.md` — absent
  This is non-blocking because (a) the plan's "Pre-flight verification" section anchors the technical claims directly in code paths, not in those documents; (b) the constraints attributed to those documents (no fork of pi, MCP write tools off, etc.) are re-stated in this plan's Shared Constraints section; (c) the Phase 1 plan exists at the documented path and provides the binding contract for Phase 2. Recommend during implementation: either link these files if they exist elsewhere, or remove the `builds_on::` references to avoid dangling pointers. The plan itself is self-sufficient.

### Clarity — PASS

- Success criteria are testable. Examples:
  - `head -1 plugin/ralph-hero/skills/cos/SKILL.md` matches `^---$` — boolean.
  - `wc -l plugin/ralph-hero/skills/cos/system-prompt.md` returns ≤ 80 — boolean.
  - `grep -rE '(^|\s)claude(\s|$)' plugin/ralph-hero/scripts/cos/cos-remote.sh` returns nothing — boolean.
- Cache schema is explicit and parseable: `{"timestamp", "summary", "model", "prompt_hash"}` — same fields tested by `jq` in the verification section.
- The plan explicitly resolves the ambiguity between the parent plan's `prompts/system.md` path and the issue body's `skills/cos/system-prompt.md` path (lines 73–75), and picks the issue body as authoritative. Good conflict resolution.

### Scope — PASS

- "What We're NOT Doing" is unusually thorough — 10 bullets, each tied to a downstream phase or a design principle.
- Explicit constraint: single-slot cache (no multi-project keying) is called out as a known limitation that must be documented in `SKILL.md` (line 119). That's the right way to handle the tradeoff — surface it, don't hide it.
- The `desk` and `unattended` stubs are correctly framed as user-discoverable surface area, not silent no-ops (line 48, 78–79). The acceptance bullets specify the exit-0 + pointer-message contract.

### Dispatchability — PASS

- Each of the six tasks could be handed to a fresh subagent with zero additional context:
  - **Task 2.1 (SKILL.md)**: 10 acceptance bullets specify frontmatter fields, body sections, and a frontmatter-validity check. A subagent reading this task alone can write the file.
  - **Task 2.2 (cos-agent.md)**: 7 acceptance bullets specify name/description/model/skills/tools allowlist + body content. The tools allowlist is fully enumerated.
  - **Task 2.3 (system-prompt.md)**: 7 acceptance bullets specify heading, voice, tool preferences, output conventions, non-actions, example output, and length cap.
  - **Task 2.4 (cos-remote.sh)**: 13 acceptance bullets — the heaviest task but each bullet is mechanical. The JSON cache shape is fully specified. The macOS-vs-Linux `stat` divergence is called out. The "no claude invocations" check is mechanizable.
  - **Task 2.5 (stubs)**: 7 bullets, identical structure for both stub scripts. Exit-0 message strings are quoted literally in the acceptance.
  - **Task 2.6 (justfile)**: 9 bullets specify recipe name, group annotation, dispatch table, path resolution via `{{justfile_directory()}}`, and the negative test (`grep -A20 '^cos '` should not match `cli-dispatch.sh`).
- Dependency graph is explicit: 2.1, 2.2, 2.3 are parallel; 2.4 → 2.3; 2.5 → null; 2.6 → 2.4 + 2.5.

## Recommendations (non-blocking, can be addressed during implementation)

1. **Reconcile `builds_on::` references.** Either ensure the two missing files (`2026-05-14-GH-1252-ralph-hero-cos-mode.md`, `2026-05-14-pi-coding-harness-as-chief-of-staff.md`) exist before merge, or remove them from the frontmatter to avoid dangling pointers in the knowledge graph. The plan stands on its own technically; this is a hygiene fix.
2. **Consider adding a single negative-test smoke script** to Task 2.4 or 2.6 — a one-shot bash that runs `ralph cos remote`, asserts the cache file appears, and checks `pgrep claude` count delta is zero. The plan already lists this as a manual check; pre-committing the script would shave the manual loop time. Non-blocking — Phase 4 owns the bats scaffold.
3. **Task 2.4 acceptance bullet 8** (cache-miss invocation) inlines the prompt in `cos-remote.sh`. Note the tradeoff: the `prompt_hash` field in the cache JSON becomes meaningful for invalidation, but prompt edits require touching the script. The plan acknowledges this with "no separate prompts/ file in this phase — keeps the cache key simple." This is the right call for v1.
