# Plan Critique — GH-1257 cos mode Phase 5 (Streamlit desktop at :8502)

Reviewer: ralph-review (AUTO mode)
Verdict: **NEEDS_ITERATION** — one feasibility blocker (incorrect SQL column name), plus two clarity gaps that will trip implementation.

## Summary

The plan is well-structured, deeply researched, and the scope is tight: one phase, five tasks, with explicit acceptance criteria per task and a thorough "What we're NOT doing" section. Pre-flight verification is excellent — file paths, line ranges, MCP tool names, and the `uv` precedent are all checked. Tasks 5.1, 5.2, 5.4, and 5.5 are dispatchable as written.

The blocker is **Task 5.3 / Panel 3 (KG Growth)**: the SQL query references a `created_at` column that does not exist in the `documents` table (verified at `plugin/ralph-knowledge/src/db.ts:104-113`). The actual columns are `id, path, title, date, type, status, github_issue, content, is_stub, memory_tier`. An implementer following the plan literally will write a query that fails with `OperationalError: no such column: created_at`, then have to discover the correct column name on the fly. The plan's defensive `try/except` will catch the crash but leave Panel 3 permanently broken.

Two additional clarity gaps surfaced (see Clarity below).

## Per-Dimension Assessment

### 1. Completeness — PASS

All five tasks have files, complexity, tdd, depends_on, and acceptance arrays. The phase has both Automated Verification and Manual Verification subsections. The plan distinguishes per-task acceptance from phase-level success criteria. Files-to-touch are enumerated with create/modify/read annotations. Dependencies between tasks (5.2 -> 5.4, 5.1-5.4 -> 5.5) are explicit.

### 2. Feasibility — FAIL

**Blocker — KG schema mismatch (Panel 3, Task 5.3)**:

The plan specifies (line 240, line 92):

```sql
SELECT date(created_at) AS day, memory_tier, COUNT(*) AS count
FROM documents
WHERE created_at >= date('now', '-30 day')
GROUP BY 1, 2 ORDER BY 1
```

Verified against `plugin/ralph-knowledge/src/db.ts:104-113`:

```sql
CREATE TABLE IF NOT EXISTS documents (
  id TEXT PRIMARY KEY,
  path TEXT,
  title TEXT,
  date TEXT,        -- <-- this is the timestamp column
  type TEXT,
  status TEXT,
  github_issue ...,
  content TEXT,
  is_stub ...,
  memory_tier ...
)
```

There is no `created_at` column. The correct column is `date`. The plan also asserts at line 68:

> SQLite schema includes a `documents` table with a `memory_tier` column (per the dream-loop spec); Panel 3 queries `SELECT date(created_at), memory_tier, COUNT(*) FROM documents WHERE created_at >= date('now', '-30 day') GROUP BY 1, 2`.

The `memory_tier` half of the claim is correct; the `created_at` half is wrong. The pre-flight verification missed this because it did not actually `PRAGMA table_info(documents)` against the live DB.

**Fix needed**: Update Task 5.3 acceptance (line 240) and the Key Discoveries paragraph (line 92) to use `date` instead of `created_at`. The query becomes:

```sql
SELECT date(date) AS day, memory_tier, COUNT(*) AS count
FROM documents
WHERE date >= date('now', '-30 day')
GROUP BY 1, 2 ORDER BY 1
```

Note that `date(date)` is awkward but valid SQLite (the outer `date()` is the function, the inner `date` is the column). Renaming the alias to `day` keeps the dataframe ergonomic. Implementer should also verify the column stores ISO-8601 strings (per `db.ts:108` it is `TEXT`) — if values are partial dates the comparison still works lexicographically.

**Non-blocking but worth noting** — Task 5.3 acceptance line 272 (Streamlit / MCP fallback): the plan correctly notes that if both the `--json` CLI flag and a built MCP server are missing, the panel should render an `st.warning` rather than crash. This is good defensive design but the plan never actually verifies that `ralph status --json`, `ralph activity --json`, or `ralph list --json` exist as CLI flags today. A quick `grep -rn "\\--json" plugin/ralph-hero/scripts/ralph*` would have confirmed. This is more of a scope clarification than a blocker — the implementer will discover it during 5.3 and can fall back to the MCP-stdio path, which the plan already documents.

### 3. Clarity — PASS WITH GAPS

Success criteria are specific and testable. Automated Verification uses concrete grep / bash -n / `ast.parse` commands. Manual Verification enumerates per-panel checks.

Two gaps:

1. **Chat panel streaming semantics**. Line 262 says "spawns `subprocess.Popen([...], stdout=PIPE, stderr=STDOUT, text=True, bufsize=1)` and streams stdout via `st.write_stream(line_generator)`". This is correct for `cos.sh` that prints token-by-token, but `cos.sh:33-228` is a single-prompt wrapper that returns the full response in one chunk (it does not stream tokens through stdout in real time — pi accumulates and prints at the end). The implementer will discover that `st.write_stream` over a line generator from a non-streaming process produces a one-shot render, not progressive token-by-token rendering. This is fine functionally but the plan should clarify the expectation: "stream lines as they arrive" rather than "stream tokens" — and acknowledge that if `cos.sh` buffers, the user sees a single block. Otherwise reviewers/users may expect ChatGPT-style token streaming.

2. **Two `st.set_page_config` calls**. Acceptance line 226 says "`st.set_page_config(...)` at top of `main()`" and acceptance line 265 also says "`st.set_page_config(...)` then `st.title(...)`" inside `main()`. The plan is internally consistent (both refer to the same call inside `main()`), but the wording is duplicated and could read as two separate calls. Streamlit will throw `StreamlitAPIException: set_page_config can only be called once per app` if invoked twice. One-line wording fix.

### 4. Scope — PASS

The "What We're NOT Doing" section is excellent. It explicitly excludes: Streamlit auth, persistent chat history, multi-tab/multi-page apps, mobile layout, auto-refresh, themes, alternative ports, Tailscale auto-publish, additional MCP tools, unit tests beyond AST, `streamlit_extras`, CI tests, `@walterra/pi-charts`. Each exclusion has a sentence of rationale. Future-state hooks (Phase 6 grade panel, `desk/grades.py`) are gestured at without committing.

The phase deliberately substitutes `@walterra/pi-charts` (mentioned in the issue body) with Streamlit-native charts, and the substitution is justified in the Key Discoveries section. This is a legitimate plan-level decision to make, not a scope creep.

### 5. Dispatchability — PASS WITH ONE GAP

Per-task fields (files, tdd, complexity, depends_on, acceptance) are present for all five tasks. A subagent dispatched to Task 5.1, 5.2, 5.4, or 5.5 with just the task block plus the inherited "Shared Constraints" section has enough context to ship without reading the full plan.

**Gap**: Task 5.3 (`app.py`) is annotated `complexity: high` and the acceptance list is 30+ items spanning six panel functions, a chat panel, and a main entry point. A subagent dispatched to "implement Task 5.3" will need to read more than the task block — it must read at least the "Shared Constraints" and "Implementation Approach" sections for the file structure, plus the Current State Analysis for the brief-glob and chat-streaming details. The plan acknowledges this implicitly (it tells the planner to structure `app.py` as one panel function per panel), but does not say "this task is too big to dispatch alone; the implementer must read sections X, Y, Z first." A one-line note ("**Subagent context**: this task requires reading the full Implementation Approach section before starting") would tighten dispatchability. Not blocking — the structure is workable — but worth a clarification.
