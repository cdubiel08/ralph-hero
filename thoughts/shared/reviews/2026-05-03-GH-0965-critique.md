# Plan Critique: GH-965 — Optional LLM Delegation via Bash to Local or Cheaper Endpoint

## Summary

Verdict: **APPROVED**.

This is a plan-of-plans (epic) that decomposes a delegation mechanism into six features across four waves. Foundation (F1) is fully specified at file-level detail; downstream features (F2-F6) carry scope-fences and acceptance criteria with file-level detail deferred to their own sub-plans when picked up. That structure is appropriate for an epic-tier plan.

The plan demonstrates strong alignment with established repo patterns (fail-open delegation, `ralph_resolve_env`, `portable_timeout`, bats testing already in CI), explicitly states the no-regression invariant, scopes out three concrete pilots (F4a/b/c) for measurable validation, and articulates an audit-trail-over-silent-fallback policy that responds to a known prior feedback memory.

A handful of minor accuracy issues (one missing file claimed for "update", one inaccurate env-var claim) are flagged below as **MINOR** notes the planner should clean up when sub-plans are written, but none are blocking for the epic-level decision.

## Five-Dimension Assessment

### 1. Completeness — PASS

- All six features (F1-F6) are defined with their owner area, dependencies, scope, and acceptance criteria.
- F1 (Foundation) has full file-level detail: files introduced, env vars table, CLI surface, exit codes, audit log line format, and seven discrete acceptance criteria.
- F2-F6 are scope-fenced with acceptance criteria but not file-level detailed — explicitly called out as the epic's design (sub-plans land file-level detail when picked up). Appropriate for plan-of-plans.
- Dependency graph and four-wave phasing table are explicit.
- Risks table covers eight categories with mitigations.
- Migration notes address backwards compatibility with existing `RALPH_LLM_URL`/`RALPH_LLM_MODEL` consumers.

**MINOR — feasibility accuracy issues to fix in F1/F3 sub-plans:**

1. **F3 claims "Update: `plugin/ralph-hero/skills/shared/conventions.md`"** — that file does NOT exist. Existing `plugin/ralph-hero/skills/shared/` directory contains `quality-standards.md`, `artifact-comment-protocol.md`, `integration-test-scenarios.md`, plus a `fragments/` subdir. F3 should either (a) create `conventions.md` as a new file, or (b) extend an existing file (e.g., add a "Delegation pattern" section to `quality-standards.md`). 2. **F3 claims "New section in `plugin/ralph-hero/CLAUDE.md`"** — that file does NOT exist either. Only the top-level `/CLAUDE.md` and the per-skill READMEs exist. F3 should either (a) create `plugin/ralph-hero/CLAUDE.md` as a new file, or (b) add the section to top-level `CLAUDE.md`. Sub-plan should clarify.

These are accuracy issues, not blocking flaws — the design is feasible and the file paths can be corrected when sub-plans are picked up. Hence still PASS.

Most could be wrapped as `- [ ] Automated:` / `- [ ] Manual:` per quality standards but they are already specific enough to dispatch.

**Minor (non-blocking):** Top-level "Success Criteria (epic-level)" section uses the `- [ ] Automated:` / `- [ ] Manual:` split but per-feature acceptance bullets are not formatted with that prefix. Sub-plans for F1-F6 should adopt the standard prefix for downstream-orchestrator consumption.

### 4. Scope — PASS

The "What We're NOT Doing" section is exceptionally well-bounded:

- Eight explicit non-goals (no Anthropic-native API, no auto-routing, no streaming, no changes to existing knowledge/dream consumers, no per-task model router, no prompt-caching/batching, no delegation of mutation steps, no replacement of Claude as primary reasoner).
- Each non-goal is paired with rationale or a deferred follow-up, not just a flat list.
- The "no-regression invariant" is stated three times (overview, desired-end-state, success criteria) and is testable: "with `RALPH_DELEGATE_ENABLED` unset, ralph-hero behaves bit-identically to today."
- Scope fences for F4a/F4b/F4c each name a specific delegation site, what changes, what stays the same, and acceptance criteria with quantified eval sets (5-query, 3-PR eyeball, 10-issue).

### 5. Dispatchability — PASS (epic-tier scope)

For an epic-tier plan-of-plans, dispatchability is inherited from sub-plans rather than embedded in this document. The epic plan correctly:

- Declares each feature's owner area, depends-on edges, estimate, scope, and acceptance criteria.
- Defers file-level task decomposition to sub-plans, which is the documented expectation for epic plans.
- Locks the F1 (Foundation) feature to file-level detail because nothing else can land without it; this gives the F1 sub-plan all the dispatchability fields needed (files introduced, env vars, CLI surface, exit codes, log format, acceptance criteria).

Sub-plans (F1-F6) when written must include the standard task-level fields per quality standards (files with create/modify/read, tdd, complexity, depends_on, acceptance). The epic plan does not need them.

**Phase-dependency clarity (multi-issue group plan check):** The dependency graph at L324-334 explicitly shows F1 → {F2, F3, F6}, F2+F3 → F4a/b/c, F1 → F5 (optional). Each feature's "Depends on" line restates this. Wave phasing table cross-checks. Phase dependencies are explicit. **Integration testing across waves** is implicit in F4*/F5 acceptance (Wave 4 telemetry consumes F1 audit log; Wave 3 pilots all exercise F1+F2+F3 end-to-end). Could be tightened with an explicit "cross-feature integration" section but not blocking.

## Plan Strengths

- **Reuses existing infrastructure correctly.** `RALPH_LLM_URL`/`RALPH_LLM_MODEL` are already in use; not redefining them is the right call. `ralph_resolve_env`, `portable_timeout`, hook-utils.sh, and the bats test pattern are all leveraged. This is a low-risk plan because the foundation is paved.
- **Audit-trail-over-silent-fallback** directly addresses the saved feedback memory at `~/.claude/.../feedback_no_gh_auth_fallback.md` ("Don't use gh auth token as fallback — it masks bad config; surface errors instead"). The 126 (silent skip when disabled) vs 127 (visible degradation when endpoint dies) exit code split is a thoughtful application of that principle.
- **Three concrete pilots with quantified eval sets.** F4a/b/c each have specific delegation sites, acceptance criteria with numerical baselines (5-query eval, 10-issue agreement-threshold). This makes the epic measurable rather than aspirational.
- **No-regression invariant stated three times and is testable.** With `RALPH_DELEGATE_ENABLED` unset, every existing test must still pass; this is enforced by the smoke-test acceptance criterion and is straightforward to verify in CI.
- **Hook-system caveat called out as a risk.** The Risks table explicitly mentions "Hooks block `Bash(curl …)` calls in agent contexts" and mitigates with an F1 acceptance check + narrow allowlist if needed. This is a real concern in this codebase (50+ hooks) and getting it on the radar at the epic level prevents surprise during F4* implementation.
- **Migration story is benign.** No data migration; existing consumers unaffected; opt-in is one env var; setup-skill detection is offered, not forced.

## Issues

### MINOR — accuracy fixes for sub-plans (non-blocking for epic approval)

1. **F3 file claims:** `plugin/ralph-hero/skills/shared/conventions.md` does not exist. Either create it as a new file or pick an existing host (e.g., `quality-standards.md`).
2. **F3 file claims:** `plugin/ralph-hero/CLAUDE.md` does not exist. Either create it or fold the section into the top-level `/CLAUDE.md`.
3. **reflect.py env-var claim:** Plan says reflect.py "consumes `RALPH_LLM_URL`/`RALPH_LLM_MODEL`"; it actually uses CLI flags + config-file values with the same defaults. Update the current-state-analysis paragraph to be technically accurate; defaults match so behavior is consistent, but the env-var consumption claim is wrong.
4. **CI bats already integrated:** Plan F1 acceptance reads as if bats integration is greenfield ("CI workflow runs the bats suite alongside …"). Bats is already integrated via `bats-core/bats-action@2.0.0`. Reword to "extend the existing bats matrix" so the work is correctly scoped as additive.
5. **Acceptance-criteria formatting:** Sub-plans for F1-F6 should use the `- [ ] Automated:` / `- [ ] Manual:` prefix per the canonical quality standards. The epic plan's top-level success criteria section does this; per-feature acceptance bullets do not.

None of the above blocks the epic from advancing to implementation. They are sub-plan-level accuracy fixes the planner can make when each feature is picked up.

## Verdict

**APPROVED** as an epic / plan-of-plans. F1 is fully specified and ready for its own sub-plan to be written and dispatched. F2-F6 are appropriately scope-fenced and will get file-level detail in their own sub-plans.

Implementation should begin by spinning up the F1 sub-issue and writing the F1 implementation plan with file-level task decomposition and the standard `- [ ] Automated:`/`- [ ] Manual:` acceptance format. The MINOR accuracy items above should be corrected in the F1/F3 sub-plans rather than re-opening this epic plan.
