## New material in v2 worth noting

### Task 1.0: Pre-flight install verification (new gating task)

The new Task 1.0 (lines 125–136) is the right shape:
- Runs the three `pi install` commands in a controlled order.
- STOP-and-escalate on any failure — no silent package-name substitution.
- Captures the pi-mcp-adapter README excerpt for `lifecycle` / `directTools` /
  `directToolAllowlist` into a new `PREFLIGHT.md` so Task 1.3 has a known-good
  reference inline.
- Task 1.3 now `depends_on: [1.0]` (line 188), so the MCP config writer cannot
  run until the adapter conventions are confirmed.

This is a tight, low-cost gate. It de-risks the most likely failure mode (the
upstream pi extension package names) without ballooning the phase estimate.

### What We're NOT Doing now has 10 exclusions

The list was 8 in v1, is now 10 (lines 87–98). New exclusions explicitly call
out (a) parent plan-of-plans authoring deferred, (b) issue-body kebab-vs-snake
inconsistency intentionally not blocking. Both are defensible boundary calls.

  to that effect would make the task even more self-contained. Not blocking —
  the existing language is unambiguous enough.
- **(nit) Phase Success Criteria → Automated could include `bash -n smoke.sh`.**
  Already there (line 253). Disregard.
- **(observation) Task 1.5's smoke fixture is the only task that exercises the

  there's no MLX server in CI. The plan correctly does not pretend this can be
  automated.
