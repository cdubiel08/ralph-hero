# Plan Critique: Auto Mode Pipeline Gaps (GH-756)

## Overall Assessment

The plan is well-structured, technically accurate, and actionable as-is. It identifies two clear gaps where `auto` mode env vars fail to flow through to downstream skills, and proposes surgical changes to three skill files (ralph-merge, finish, plan) plus documentation updates. All file references and line numbers have been verified against the current codebase. The phased approach with explicit pause points for manual verification is appropriate for this type of behavioral change.

## Completeness

**Rating: Strong**

- All four phases are clearly defined with specific file paths, line ranges, and replacement content.
- Success criteria are split into automated and manual verification for every phase.
- The "What We're NOT Doing" section is well-scoped: explicitly excludes human reviewer feedback from the auto-fix cycle, preserves the existing val fix cycle, and avoids CLI flag changes.
- The desired end state includes a concrete verification checklist (read Step 4, confirm auto path, confirm human-reviewer path).
- The testing strategy covers both auto and interactive modes, plus the human-reviewer edge case.

One minor gap: Phase 3 (plan skill auto mode) doesn't explicitly mention that the plan file needs to be committed and pushed to `main` before the Artifact Comment URL will resolve. However, this is handled by the existing plan skill workflow (Step 4 writes the file), and the git commit/push is an implicit part of the autonomous flow. Not blocking.

## Feasibility

**Rating: Strong**

All technical claims verified:

- ralph-merge `allowed-tools` includes `Skill` (line 22) -- can invoke `code-review:code-review`. No tool availability issue.
- finish `allowed-tools` includes both `Skill` (line 22) and `Agent` (line 23) -- can dispatch impl-agent. No tool availability issue.
- The `RALPH_REVIEW_MODE` env var flows through process inheritance and is already resolved via backtick preprocessing in `hero/SKILL.md:49`. Adding it to ralph-merge's Configuration section follows the established pattern.
- The `CODE_REVIEW_FEEDBACK` output status is a new convention, but it follows the existing pattern (`MERGE BLOCKED`, `MERGE NOT READY`, `MERGED`, `VALIDATION PASS/FIX/FAIL`). finish already demonstrates parsing skill output for structured status strings.
- impl-agent's Address Mode (lines 410-441) auto-activates when the issue is "In Review" with an open PR containing review comments -- exactly the state that exists when code-review requests changes.
- The plan skill correctly resolves `RALPH_REVIEW_PLAN` (not `RALPH_REVIEW_MODE`) in its Configuration section (line 35).

## Clarity

**Rating: Strong**

- Success criteria are specific and testable. Each phase has both automated (grep for specific strings in skill files) and manual (run the skill, verify behavior) verification.
- The replacement content for Step 4 in Phase 1 is provided as a complete, self-contained markdown block -- no ambiguity about what to write.
- The branching logic (auto vs. interactive vs. no-plugin) is clearly laid out with distinct code blocks.
- The `CODE_REVIEW_FEEDBACK` vs. `MERGE BLOCKED` distinction is explicitly documented and motivated (automated review feedback triggers fix cycle; human reviewer feedback does not).

## Scope

**Rating: Strong**

- "What We're NOT Doing" is comprehensive and prevents the most likely scope creep vectors.
- The plan explicitly avoids modifying the val fix cycle in finish (Phase 2 adds a parallel pattern for code review, doesn't touch the existing val pattern).
- The decision to only auto-fix automated code review feedback (not human reviewer feedback) is sound -- human reviewers may have nuanced feedback that shouldn't be auto-addressed.
