# Plan Critique — GH-921 (Hello Directions, Phase 1 of 3-issue group plan)

The plan under review covers issues GH-921, GH-922, GH-924 as a single atomic group plan. GH-921 is the primary (Phase 1: pure ranker library + parent-edge GraphQL extension). The critique evaluates the entire group plan because Phase 1 is not independently shippable — it's the foundation for Phase 2/3.

## Summary verdict

**APPROVED.** Plan is dispatchable, technically sound, well-scoped, and verifiable. One minor Feasibility finding (`ensureFieldCache` import path) is annotated below — it does not block implementation because the plan already lists both viable workarounds.

## Dimension assessment

### 1. Completeness — PASS

All three phases have explicit task lists with file paths, marked create/modify/read, and per-task acceptance criteria. Pseudocode for the ranking algorithm is inlined (lines 107-126) and references the parent plan-of-plans for full detail. Shared Constraints (lines 38-49) make inherited rules explicit. Phase dependencies are documented (`depends_on: [phase-1]`, `depends_on: [phase-2]`).

### 2. Feasibility — PASS (with one minor note)

**Minor finding (Phase 2 Task 2.2 acceptance, plan line 265-267):** The plan describes `ensureFieldCache` as private in `dashboard-tools.ts:36` and offers two workarounds (export from `dashboard-tools.ts` or copy 10 lines). In fact, `ensureFieldCache` is **already exported from `lib/helpers.ts:116`** (verified by grep: `lib/helpers.ts:495,605,633` already use it via `import { ensureFieldCache }`). The cleaner third option — and the project's existing convention — is `import { ensureFieldCache } from "../lib/helpers.js";`. The two `dashboard-tools.ts:36` and `helpers.ts:116` definitions are independent (the dashboard-tools one is private, used only internally by `pipeline_dashboard`). The implementer should pick the helpers-import path; both plan-listed workarounds also work but are less idiomatic.

This is not blocking — the plan's listed workarounds yield correct code; the helpers-import is just simpler.

### 3. Clarity — PASS

Every phase has explicit `#### Automated Verification` and `#### Manual Verification` blocks. Test cases are enumerated (13 for ranker, 6 for tool wrapper) with one-line behavior descriptions. Acceptance criteria use `- [ ] Automated:` / `- [ ] Manual:` checkbox shape and grep guards (e.g., `grep -q "rankDirections" plugin/.../directions.ts`) to make verification mechanical.

The Determinism Contract is stated three times (Shared Constraints, Phase 1 acceptance, Phase 2 manual verification) — appropriately redundant for a load-bearing invariant.

### 4. Scope — PASS

`## What We're NOT Doing` (lines 90-99) is explicit and well-bounded — 9 bullets covering what stays untouched (`pipeline_dashboard`, `pick_actionable_issue`, picker shape, MCP PR-fetching, `trackedIssues` GraphQL, ranking-weights config, other consumers, Stop hook). This is exactly the kind of fence-posting that keeps a 3-phase group plan from sprawl.

### 5. Dispatchability — PASS

Each task has all required fields (`files`, `tdd`, `complexity`, `depends_on`, `acceptance`). Tasks are self-contained: a subagent could pick up Task 1.3 (create `directions.ts`) with only the parent plan-of-plans + Task 1.3 acceptance and produce the right code. Notably, the plan inlines the `Direction` shape, the `RankConfig` defaults, and the score precedence (lock-stale > tree-continue > issue) directly into Task 1.3's acceptance — the implementer doesn't have to cross-reference.

For multi-issue group plans, dependency edges between phases are explicit: Phase 1 "Creates for next phase" line (230) names the exports Phase 2 will consume. Phase 2's "Creates for next phase" (329) names the registered tool Phase 3 calls. Integration testing section (lines 443-447) covers the cross-phase end-to-end check.

This is a real ralph-hero release-pipeline gotcha, and the plan addresses it head-on.
- GH-0838 output-budget regression is guarded by both Phase 3 Task 3.7 (preserve grep) and the Manual Verification check (≤40-line briefing).

## Conclusion

This is a high-quality, dispatchable plan. The pseudocode-plus-acceptance-criteria pattern, explicit phase deliverables, and well-bounded out-of-scope list make it suitable for autonomous execution. Approve and proceed to implementation.
