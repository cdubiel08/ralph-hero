# Plan Critique: GH-1306 — `knowledge_expert(domain)` MCP tool

## Summary

The plan is well-structured, technically grounded, and clearly scoped. It composes existing primitives (`outcome_events.payload` JSON column, `tags` table joins, `HybridSearch`) rather than introducing new infrastructure, and the design choices (open-string domains, optional `query_id`, JSON1 `json_extract` correlation) avoid schema migrations entirely. Three sequential phases with explicit pause points keep risk per landing low. Technical claims I spot-checked against the codebase all hold up.

## Dimension Assessment

### Completeness — PASS
All three phases declare concrete file paths (`plugin/ralph-knowledge/src/index.ts`, `src/db.ts`, `src/__tests__/index.test.ts`, `plugin/ralph-hero/agents/research-agent.md`, `plugin/ralph-hero/skills/ralph-research/SKILL.md`), specific line-number anchors (e.g., "after line 720, before `registerGraphTools(server, db)` on line 722"), and full code samples — not pseudocode. Each phase has its own Success Criteria (automated + manual) section.

### Feasibility — PASS
Verified against the live source:
- `server.tool("knowledge_record_outcome", ...)` block is at `src/index.ts:644-682` (matches plan claim exactly).
- `registerGraphTools(server, db)` is at `src/index.ts:722` (matches insertion point).
- `outcome_events.payload TEXT DEFAULT '{}'` schema exists at `src/db.ts:144` — JSON column ready for `query_id`, no migration needed.
- `tags` table has composite PK `(doc_id, tag)` with `idx_tags_tag` index at `src/db.ts:115-128` — `queryByDomain` join is index-backed as claimed.
- `outcome_events.issue_number INTEGER NOT NULL` (`src/db.ts:133`) — plan correctly identifies this as forcing `issue_number` to be required on `knowledge_expert`.
- `DocumentRow` interface at `src/db.ts:7-17` matches the columns selected in the proposed `queryByDomain` SQL.
- Tool registration uses inline `server.tool()` inside `createServer()` — plan correctly notes ralph-knowledge does not use the `registerXyzTools()` factory pattern from ralph-hero.

One minor feasibility note (not a blocker): the test fixture uses `db.upsertDocument({ id, path, title, memoryTier, date })` but `upsertDocument` requires the full `Omit<DocumentRow, "isStub">` shape — `type`, `status`, `githubIssue`, `content` are non-optional in the interface. The impl agent will need to either include those (set to null / "") in the seed call or destructure-with-defaults. This is a 30-second fix during implementation, not a plan-level concern.

### Clarity — PASS
Success criteria are testable. Automated items use `npm run build` / `npm test` invocations. Manual items reference concrete commands like `knowledge_expert({ domain: "ralph-knowledge", issue_number: 1306 })` against the real DB. The verification roundtrip in "Desired End State" is unambiguous (call expert → record two outcomes with returned `query_id` → query by `query_id` returns both).

### Scope — PASS
"What We're NOT Doing" enumerates six specific exclusions: OTel/Langfuse spans (correctly flagged — the issue body mentions Langfuse spans as a deliverable, but the plan reasonably defers because ralph-knowledge has no OTel SDK today), SSE dashboard, auto-promotion reflection→wiki, reflection domain backfill, other consumer agents beyond `research-agent`, and registry-based domain validation. Each exclusion is justified with a reason, and the discrepancy with the issue's "Langfuse span emitted per call" acceptance bullet is explicitly called out in "Key Discoveries". Treating the persistent `outcome_events` row as the day-one telemetry contract (with OTel as a follow-up) is the right call.

### Dispatchability — PASS (with one note)
Each phase is self-contained with explicit file paths, code blocks, and acceptance criteria. The "Implementation Note: Pause for human confirmation" between phases is appropriate for sequential delivery. The plan does not use the formal `files / tdd / complexity / depends_on / acceptance` task table format, but the per-phase "Changes Required" sub-sections + Success Criteria deliver equivalent information. An impl agent dispatched on Phase 1 alone has everything it needs (file, line, full code snippet, test patterns) — same for Phase 2 and Phase 3. No phase requires reading the full plan to make sense of the immediate task.

The one note: Phase 3 Step 2 references `ralph-research` skill steps without exact line anchors ("Find the section that fetches the issue and prepares for research"). For an autonomous impl agent this is slightly underspecified vs. Phases 1-2; the agent will need to read the skill file first. Not a blocker — the change is local and the search target is described.

## Verdict

**APPROVED** — ready for implementation.

Strengths:
- Zero schema migration (`payload` JSON column already there; `query_id` is additive optional param).
- Telemetry-first ordering (Phase 2 lands before Phase 3 consumer) so the first real call generates observable data.
- Explicit OTel deferral is principled, not handwavy — plan documents *why* (no OTel SDK in ralph-knowledge) and points at a future separate effort.
- Strong reference layer: every claim about existing code is cited with file:line, and spot-checks confirm accuracy.

Minor notes for the impl agent (none rise to needs-iteration):
1. Phase 1 test fixture: `upsertDocument` requires more fields than the snippet shows — fill in `type/status/githubIssue/content` defaults.
2. Phase 3 Step 2: read `skills/ralph-research/SKILL.md` first to locate the insertion point for Step 1.5.
3. Domain extraction heuristic in Phase 3 is intentionally informal — fine for first consumer; future consumers can codify it once a pattern emerges.
