# Review: Repo-wide issue search — close the Project-V2 scoping blind spot in `list_issues`

## Plan Reference

[thoughts/shared/plans/2026-07-21-GH-1572-repo-wide-issue-search.md](../plans/2026-07-21-GH-1572-repo-wide-issue-search.md)

## Strengths

- **Grounded in verified precedent.** Every load-bearing code claim checks out against source: `resolveConfig` (helpers.ts:550) requires only owner+repo with no project dependency while `resolveFullConfigOptionalRepo` (helpers.ts:622) throws on a missing project — exactly the resolver distinction the plan pivots on; and both `fetchOpenPRs` (directions-tools.ts:367) and `findExistingDebugIssue` (debug-tools.ts:64) use `search(type: ISSUE)` via `client.query()` with the try/catch-swallow-and-log failure mode the plan cites. The plan reuses an established pattern rather than inventing client plumbing.
- **Clean, dependency-honest phasing.** Phase 1 (doc-only) → Phase 2 (helper + `scope` param, the load-bearing new code) → Phase 3 (dedup, `depends_on: [phase-2]` so it consumes the already-tested helper). The ordering rationale is explicit and correct.
- **Shape-compatibility discipline.** Desired End State #4 and Phase 2(d) require the repo-scope response to return project-only fields as `null` (not omitted) so existing consumers doing `item.workflowState` need no scope-aware branching — a real regression risk that most plans would miss.
- **Asymmetric failure contract is deliberate and justified.** The plan explicitly distinguishes `list_issues` repo-scope (throw → `toolError`, because silent-empty-on-error recreates the exact GH-1572 bug) from `create_issue` dedup (swallow → create anyway, because a best-effort net must never make issue creation newly impossible). Both sides are argued from the incident, not asserted.

## Gaps

None that rise to a rubric GAP. Two observations carried to Caveats rather than scored as gaps (estimate is at the upper edge of S; decision #2 is the most escalatable of the three resolved calls).

## Failures

None. Each resolved decision is consistent with what the phases actually implement (scope-param → Phase 2; on-by-default dedup → Phase 3 schema+handler; swallow-on-search-error → Phase 3 try/catch), so there is no resolved-decision-vs-phase contradiction.

## Recommended Changes

No blocking changes. Optional polish the planner may fold in without a re-review:

1. **Phase 2 grep assertion phrasing coupling.** Phase 1's automated check hardcodes `grep -q "Project V2 board"`. If the Phase 1 description wording is later softened, that grep and the mirrored `issue-tools.test.ts` structural assertion must move together. Consider asserting on a more stable token (e.g. `scope: "repo"` reference in the description) so a wording pass can't silently break the test.
2. **create_issue latency note.** Migration Notes already flags the one extra `search` call per default `create_issue`. Worth a one-line mention in the `create_issue` tool description itself (Phase 3 item #2) so a caller reading the schema — not just the plan — knows a dedup round-trip now happens by default.

## Caveats

- **Estimate is at the S/M boundary, not comfortably mid-S.** The work spans a new `lib/repo-issue-search.ts` module (two exported functions), two Zod schema additions across two tools, two structurally different handler branches, and three test surfaces (new `repo-issue-search.test.ts`, new `create-issue-dedup.test.ts`, extended `issue-tools.test.ts`). Realistically ~6-7h of focused work. It stays S because it is one cohesive feature reusing shipped patterns with additive/backward-compatible defaults — but if Phase 2's search-qualifier mapping (the `reason:`/`sort:`/`updated:` translations) proves fiddlier than the `findExistingDebugIssue` template suggests, this is the phase that would push the whole unit into M. Flagging, not down-scoring.
- **Decision #2 (create_issue dedup on-by-default) is the one resolved call closest to warranting a human `#### Decision:` block.** It changes behavior for *every* `create_issue` caller (added latency plus a possible false-positive block on a legitimately-reused exact title). The plan resolves it toward on-by-default with a strong incident-framed rationale, and the risk is well-bounded (exact-title-only match, always-available `skipDedupeCheck: true` override, fallback-on-search-error). I judge resolving-in-plan acceptable rather than escalate-to-human given those mitigations — but a reviewer who weights "changes a mutation tool's default behavior for all callers" more heavily could reasonably have wanted this as an open decision. It is surfaced with full rationale, so it is not a buried decision either way.
- I did not exercise the actual GitHub Issues Search API to confirm every qualifier translation (`reason:"not planned"`, `sort:comments-desc`, `updated:<`) behaves as the plan assumes; those are asserted from GitHub's documented search syntax and the two existing in-repo `search()` call sites, not run live. Phase 2's unit tests (`buildRepoSearchQuery` against exact qualifier strings) are the right place to lock these down.
