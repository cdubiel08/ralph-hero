# Plan Critique: GH-1120 Vitest Coverage Thresholds Across Node Packages

## Summary

VERDICT: **APPROVED**

The plan is a tight, well-bounded atomic phase of the parent epic GH-1118. It correctly identifies that the work is plumbing-only (no new tests, no refactors), accurately maps the three packages and their package managers, references the existing CI surface line-for-line, and explicitly addresses the trickiest part of measure-then-lock thresholds (Task 1.4 capturing measured baselines before Tasks 1.5–1.7 bake them in). All five plan-quality dimensions pass.

## Dimension Scores

### 1. Completeness — PASS

Phase 1 contains 9 tasks covering: 3 install tasks (one per package, each with the right manager — npm vs pnpm), 1 baseline measurement task, 3 config-authoring tasks (modify mcp-server, create ralph-knowledge, modify ralph-demo), 1 lcov verification task, and 1 threshold-enforcement sanity check. Every task names specific files with (create/modify/read) annotations. The "Desired End State" section enumerates 6 concrete post-conditions and the "Verification" section provides 5 testable checkboxes.

### 2. Feasibility — PASS

Verified live in the worktree:

- `plugin/ralph-hero/mcp-server/vitest.config.ts` exists (7 lines, minimal) — matches plan's "exists, minimal".
- `plugin/ralph-knowledge/vitest.config.ts` does NOT exist — matches plan's "missing", consistent with Task 1.6 creating it.
- `plugin/ralph-demo/remotion/vitest.config.ts` exists with `environment: "jsdom"`, `globals: true`, `include: ["src/**/*.test.{ts,tsx}"]`, `setupFiles: ["src/test-setup.tsx"]` — matches Task 1.7's preserved-block claim verbatim.
- vitest versions: mcp-server `^4.0.18`, ralph-knowledge `^4.0.0`, ralph-demo `^4.1.5` — exactly as plan states.
- `.github/workflows/ci.yml` lines 38, 67, 102 all run `npm test` / `pnpm test` — matches plan's claim that no CI workflow edits are needed.

### 3. Clarity — PASS

Each task uses the canonical `- [ ]` acceptance checkbox format. Acceptance criteria are specific and testable (e.g., "package.json lists @vitest/coverage-v8 in devDependencies at the same major as vitest", "vitest exits non-zero with a clear 'X% < threshold' message"). The Phase Success Criteria split into Automated and Manual sections, each enumerating discrete checkboxes. Inline date comment convention (`// 2026-05 baseline N%`) is documented in Shared Constraints and re-asserted in each config-authoring task.

### 4. Scope — PASS

"What We're NOT Doing" enumerates 6 explicit exclusions:

1. Codecov / external coverage upload (stretch goal).
2. Refactors to improve coverage on specific files.
3. Writing new tests (deferred to phases 3, 4, 6, 7 of parent epic).
4. CI workflow file changes.
5. Touching ralph-demo/remotion's test fixtures, setup files, or jsdom env.
6. Adding a separate `test:coverage` script.

Each exclusion is paired with a rationale. Bounds are tight enough that an executor cannot scope-creep into adjacent phases of the parent epic.

### 5. Dispatchability — PASS

Every task in Phase 1 declares: files (with create/modify/read), tdd, complexity, depends_on, acceptance. Dependency chain is explicit and correct:

- 1.1, 1.2, 1.3 — independent (depends_on: null).
- 1.4 — depends on [1.1, 1.2, 1.3] (must install coverage tool before measuring).
- 1.5, 1.6, 1.7 — each depends on [1.4] (can't lock thresholds without baseline data).
- 1.8, 1.9 — depend on [1.5, 1.6, 1.7] (verify after thresholds are baked in).

Tasks 1.4, 1.8, 1.9 are verification-only (no edits), but acceptance criteria are concrete enough that a subagent can execute them without reading the full plan. The flagged stop condition in Task 1.4 ("If any package's tests fail under coverage instrumentation … record the failure and stop") is a thoughtful guardrail.

## Notes

- **Optional improvement (not blocking)**: Task 1.8's `.gitignore` check ("OR added in this PR if missing") could be promoted to a discrete sub-task to make the dependency on `coverage/` directory hygiene explicit. As written it's tucked into a verification acceptance criterion. Approve as-is.
- **Optional improvement (not blocking)**: The Implementation Approach mentions Tasks 1.5–1.7 "could be parallelized — but the work is small enough that linear is fine." Since the plan declares dispatchability as a goal, an explicit "execute serially" or "execute in parallel after 1.4" hint in dispatch metadata could help an orchestrator. Not required for approval.

Both notes are nits — the plan is fundamentally executable as written.

## Recommendation

Approve and route to implementation. This is a textbook atomic phase: scoped tightly, references verified, dependencies explicit, verification automated where possible.
