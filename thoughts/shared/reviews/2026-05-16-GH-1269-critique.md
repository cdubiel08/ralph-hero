# Plan Critique: GH-1269 — Director Skill + Event Classifier

### 3. Clarity — PASS

Success criteria are specific and testable. Phase Success Criteria section explicitly splits Automated (lint, typecheck, grep checks, skill-invokability) and Manual (label-add-and-watch, voice review, taxonomy readability). Each task's acceptance bullets are concrete enough to verify without re-reading the plan body — e.g., "Frontmatter includes: `description` (one sentence...), `argument-hint: "[optional: --issue NNN]"`, `context: inline`, SessionStart hook running `set-skill-env.sh RALPH_COMMAND=director`."

Grep-based verification is a strong choice for this work since the deliverables are markdown frontmatter and skill bodies (no compilable TypeScript surface to typecheck).

### 4. Scope — PASS

"What We're NOT Doing" section is explicit and well-bounded. Six exclusions enumerated:
- Watch/Scouts/Caretake team entrypoints (Features C, F, G)
- Live producers for `watcher-auto`/`scout-auto`/`process-improvement` (Features D, F)

The plan correctly identifies that the taxonomy table needs to include rows for not-yet-shipped automation labels (so Features D/F can edit them later with one-row PRs) but explicitly marks those rows as "label exists, producer pending" — distinguishing "schema present, producer deferred" from "TODO." This is the right call.

## Risks & Considerations

- **Director SOUL ships independently of Feature A's `load-team-soul.sh` hook.** The plan correctly notes this: Director's SOUL.md exists as a stub; once Feature A lands, the loader picks it up automatically. This decoupling is sound but means Director's voice/refusals are not enforced at runtime until A ships. The plan does not claim otherwise.
- **`event-classes.md` is extension-friendly by design**, but the plan body relies on prose convention ("Features D/F edit it via PR") rather than a structural mechanism (e.g., named anchors or a parseable section). For a one-row PR edit this is acceptable; if the taxonomy grows large, a generator-friendly format may be worth revisiting.
- **No automated test for the classifier path.** The plan's verification leans on manual smoke tests (label-add-and-dispatch). This is consistent with the codebase's existing skill-testing posture but should be flagged as a known gap for future hardening.
