# Plan Critique: GH-975 — Direction Signals + LLM-Synthesized Prose

## Summary

Approved. The plan is unusually well-grounded — it cites exact line numbers in the
target file, mirrors a deprecation pattern already established in this codebase
(`hello_directions`), preserves the determinism contract called out as a load-bearing
invariant in the lib's module-level docstring, and routes the structural change to the
correct seam (lib produces structure, skill synthesizes prose). All five quality
dimensions pass. Minor non-blocking nits captured below.

## Dimension Assessments

### Completeness — PASS
Three phases with explicit task IDs, file paths, dependency edges, and acceptance
checkboxes. Per-task `tdd`, `complexity`, `depends_on`, `files`, and `acceptance` fields
are all present. Phase 1 covers types + scoring + compat shim + tool registration JSDoc;
Phase 2 covers the skill rewrite end-to-end (rendering, picker label, constraints);
Phase 3 covers unit tests per ranker branch, tied-at-score, integration wire shape, and
a fixture/manual smoke for the skill. Nothing material is missing.

### Feasibility — PASS
Verified against source. All referenced files and line numbers exist and are accurate:
- `lib/directions.ts:437` `buildReason` definition (plan cites 437-499 — matches).
- `lib/directions.ts:640, 654` `buildReason` call sites in `rankDirections` (matches).
- `lib/directions.ts:309` `scoreIssue` signature (matches "returns `{ score, kind, tags }`").
- `tools/directions-tools.ts:215` `hello_directions` description, `:281` `next_actions`
  description (matches).
- `skills/hello/SKILL.md:81` `direction.reason verbatim` (the load-bearing line — matches).
- `skills/hello/SKILL.md:73-79` per-option label rules (matches).
- `__tests__/directions.test.ts:537-562` determinism test (matches; correct citation).
- `__tests__/directions.test.ts:694-726` buildReason smoke block (matches exactly).

The deprecation strategy mirrors the existing `hello_directions` deprecation pattern,
which is already established convention in this codebase — credible.

The `signals` shape is computed from data the ranker already has internally
(`audiencePenalty` is already called at `scoreIssue:320`; `staleDays` is already computed
in `buildReason:475-476`; the tied-count post-pass after `merged.sort` is mechanical).
No new wall-clock reads or randomness — the determinism contract holds.

The contingency in Task 3.4 ("if no harness exists, write a manual smoke checklist .md")
is appropriate — verified there are no existing skill `__tests__/` directories under
`plugin/ralph-hero/skills/`, so the fallback path will trigger as designed.

### Clarity — PASS
Success criteria use the required `- [ ]` checkbox format, mix automated and manual
verification appropriately, and are testable. The Phase 3 acceptance list enumerates 8+
specific assertions with concrete expected values (e.g., `signals.staleThresholdDays === 2`
for the 48h/24h case, `signals.estimateWeight === 60` for an XL agent-audience item).

The skill prose changes in Phase 2 are inherently softer-edged (LLM behavior), but the
plan correctly anchors them with negative assertions ("never contains `small unblock`
for an XL") and a fixture-driven smoke test in Phase 3 — so the soft edge is checkable.

### Scope — PASS
The "What We're NOT Doing" section is one of the strongest in this codebase's recent
plans. It explicitly excludes:
- Memory-aware ranker boost (defers to original spec follow-on).
- Score weighting changes (calls out the bug is about prose, not ranking).
- Cross-repo / multi-project nuances in `signals` (single-project ships first).
- Removing `reason` field (kept through 2.6.x as `@deprecated`, removed in 2.7.0).
- Removing top-level `tags` field (same one-cycle window).
- Schema changes to MCP tool inputs.
- Touching `pick_actionable_issue` (already on a separate deprecation track).
- Headless orchestrator changes (`hero` / `team` ignore prose).

Each exclusion has a one-line justification. This level of explicit boundary-drawing
is exactly what the issue body asks for ("single-project case ships first"). The plan
also correctly identifies that headless orchestrators are unaffected, preserving the
load-bearing claim in the spec.

### Dispatchability — PASS
Every task is self-contained:
- Task 1.1: types-only change with the full interface inlined in the acceptance criteria.
- Task 1.2: cites the exact functions to modify (`scoreIssue`, `scorePR`,
  `rankDirections`) and the exact computation rules per field.
- Task 1.3: pins the `buildReason` signature change explicitly and points at the existing

- Phase 3 tasks: each test case enumerated with the expected assertions inline.

A subagent could pick up any single task with the plan, the issue, and the cited files

The phase dependency edge (`Phase 2 depends_on Phase 1`, `Phase 3 depends_on both`) is
explicit and correct: Phase 2 references `direction.signals` which Phase 1 creates;
Phase 3 asserts both. The "Creates for next phase" notes at the end of each phase make
the data-flow seam concrete.

## Cross-cutting checks

- **Determinism preserved**: Plan explicitly calls this out in Shared Constraints and
  asserts via the existing determinism test. The new `tiedAtScore` post-pass is a count
  on the already-sorted array — pure function of the existing input.
- **Backwards-compat strategy is correct**: `reason` and top-level `tags` stay for one
  minor cycle, derived from `signals`. Mirrors the existing `hello_directions`
  deprecation. Holdout consumers keep working.
- **Test coverage is genuinely new, not rearranged**: Phase 3 adds 8+ shape assertions,
  a tied-at-score scenario, an integration wire-shape assertion, and a fixture/manual
  smoke for the skill. None of these existed before (verified against the existing
  `directions.test.ts` and `directions-tools.test.ts`).
- **Spec alignment**: The fix restores the design philosophy table from
  `2026-05-02-hello-composable-rewrite.md` ("Synthesizing a narrative recap" → LLM,
  not deterministic code). The `tensions` block in the plan explicitly notes the
  GH-938/941 implementation diverged from the spec it was built against — this plan
  doesn't introduce a new tension, it resolves one.

## Non-blocking nits (do NOT need iteration)

These are observations a careful implementer should consider but they do not gate
approval:

1. **`scoreIssue` return type change ripples to two callers**: `rankDirections:560`
   destructures `const { score, kind, tags } = scoreIssue(...)`. After Phase 1 Task 1.2,
   it will need to also pull `signals` and store it on the `ScoredCandidate` type
   (line 505-510 in `directions.ts`). The plan covers this implicitly by saying "thread
   through `rankDirections`" but doesn't call out the `ScoredCandidate` interface
   change. Minor — implementer will hit it on first compile.

2. **`buildReason` test signature mismatch**: The existing tests at
   `directions.test.ts:701, 711, 722` pass `tags` as a positional `string[]` arg. After
   Task 1.3 changes the signature to take `signals` instead, these existing tests will
   need to pass `{ tags: [...] }` (a `DirectionSignals` shape). Task 1.3's acceptance
   criterion ("byte-identical output … for every input combination tested in the
   existing buildReason test block at directions.test.ts:694-726") implies the tests
   get updated to pass the new arg shape; worth being explicit but not a blocker.

3. **PR `signals` computation lives in `scorePR`**: Plan Task 1.2 states `scorePR`
   returns a `signals` object on `PRScored`. Today `PRScored` (line 369) has `tags` and
   `linkedIssueNumber` as siblings to `pr` and `score` — adding `signals` is mechanical.
   The plan could have called out the `PRScored` interface change explicitly the way it
   did for `Direction` and `DirectionSignals`, but again the implementer hits this
   immediately.

4. **Picker truncation at 30 chars is borderline tight for some titles**: The example
   in the plan ("Skill audit phase 2 — deep individual audits for remaining skills" →
   "Skill audit phase 2 — deep…" at 30 chars) clips mid-clause. The "do not break
   mid-word if a clean word boundary is available within the last 5 chars" rule should
   handle this gracefully, but it's worth confirming during implementation that the
   word-boundary heuristic actually fires for the live-smoke-test issue's title. Minor.

None of the above are blockers — they're implementation details that surface naturally
during compile/test and don't require re-planning.

## Verdict

APPROVED.

The plan accurately diagnoses the root cause (deterministic prose synthesis where the
spec called for LLM synthesis), routes the fix to the correct seam (lib produces
structure, skill produces prose), preserves all load-bearing invariants (determinism,
back-compat for one minor cycle, headless orchestrator independence), and provides
phase-level checkpoints small enough to verify with `npm test` between phases. The "What
We're NOT Doing" section is exemplary. Ready for implementation.
