`plan/SKILL.md` sets `RALPH_COMMAND=plan` via `set-skill-env.sh` (`:21`) but **never exports `RALPH_SUBCOMMAND` for any mode** — deliberately, per `plan/SKILL.md:135`:

> No env-flip is needed between modes: the hooks discriminate by the file path being written (review-no-dup / review-verify-doc no-op outside `thoughts/shared/reviews/`; doc-structure-validator picks its branch from each session-written doc's artifact dir; state-gate.sh accepts the union of legitimate transitions across all modes).

Compare `caretake/modes/split.md:6` (`export RALPH_SUBCOMMAND=split`), which is why the guards work today. Without an added export, `${RALPH_SUBCOMMAND:-}` is empty in plan context, each re-keyed guard falls through its `!= "epic"` early-exit (`split-estimate-gate.sh:31`, `split-size-gate.sh:27`, `split-postcondition.sh:22`), and the M/L/XL parent gate, the XS/S child gate, and the ≥2-children Stop postcondition all vanish — precisely the "Split-hook no-op risk" the plan's own Risks section names.

**This is a verification defect as much as a correctness one.** Phase 4's automated checks are `grep -n 'RALPH_COMMAND.*plan' ralph/hooks/scripts/split-*.sh` → 3 hits; `grep -n 'split-' ralph/skills/plan/SKILL.md` shows 4 registrations; `grep -n 'split-' ralph/skills/caretake/SKILL.md` → 0. **All three pass in the fully broken state.** `split-size-gate.test.sh` re-keyed to plan/epic fixtures also passes, because it sets the env vars itself. Nothing in the phase can fail on the phase's headline risk.

### F2 — Re-registering `split-size-gate.sh` under `RALPH_SUBCOMMAND=epic` breaks `plan --mode epic`'s existing plan-of-plans path (Decision honesty)

The two decomposition paths Phase 4 merges have **incompatible child-estimate contracts**, and Phase 4 gives them one shared scope key with no discriminator:

- `split-size-gate.sh:34` sets `valid_estimates="${RALPH_VALID_SUB_ESTIMATES:-XS,S}"`; the batch path (`:38-56`) blocks any `create_sub_issues` child whose estimate is not in that set.
- `plan --mode epic`'s existing plan-of-plans children are **S or M by spec**: `decomposition.md:32` (`**Estimate**: S | M`) and `decomposition.md:62` (`children: [{title, body, estimate: <S|M>, ...}]`), consumed by `plan/SKILL.md:174`. The estimate-defaults table at `decomposition.md:68-70` makes M children the documented norm for L/XL epics.

So once F1 is fixed and the guards actually arm, **every epic whose Feature Decomposition contains an M feature child is blocked** at `create_sub_issues` with "Sub-ticket estimate too large". That is a regression of an existing capability, not a preserved guarantee. Phase 4's Manual Verification asserts the broken behavior as correct — *"size gate blocks an M child"* — true and desired on the atomic-split path, fatal on the plan-of-plans path that now shares the mode.

`split-postcondition.sh` has the same shape of problem: keyed on `RALPH_SUBCOMMAND=epic` it fires at Stop on every epic session, while Phase 4 specifies the `RALPH_SPLIT_COUNT` export only inside the salvaged `## Atomic split` section. A pure plan-of-plans epic run reaches Stop with `RALPH_SPLIT_COUNT` unset (`split-postcondition.sh:38` defaults it to `0`), and whether it blocks then depends entirely on `RALPH_TICKET_ID` being empty — which the plan does not establish either way.

The merge needs an explicit discriminator between the two paths under `--mode epic` (a distinct scope value for the atomic path such as `RALPH_SUBCOMMAND=epic-split`, or a path-scoped `RALPH_VALID_SUB_ESTIMATES` widening) plus an explicit statement of what each of the four registrations does on the plan-of-plans path. As written, the resolved decision — *"the three split hooks are re-keyed to `RALPH_COMMAND=plan` + `RALPH_SUBCOMMAND=epic`"*, with *"guarantees preserved verbatim"* — cannot be implemented without either disarming the guards (F1) or regressing epic decomposition (F2).
