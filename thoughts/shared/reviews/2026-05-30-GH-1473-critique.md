# Plan Critique: GH-1473 — caretake: new `watch-blockers` mode to auto-advance dependency-unblocked items

**Verdict:** NEEDS_ITERATION
**Reviewed:** 2026-05-30
**Plan:** `thoughts/shared/plans/2026-05-30-GH-1473-caretake-watch-blockers-mode.md`

## Summary

The underlying problem is real and worth solving: nothing in caretake watches intra-project dependency edges and auto-advances an issue once all its `blockedBy` blockers reach a terminal state. `unblock.md` even explicitly disclaims this ("Does NOT auto-detect dependency-unblocked issues — that's a separate concern"), and `get_issue` genuinely returns `blockedBy`, so the data source exists. However, the plan is **not executable as written**: it is scaffolded almost entirely on anchor files, a marker format, and a hook subsystem that **do not exist anywhere in the repository**. Every "mirror the existing X" instruction points at fiction, so an implementer would have nothing to copy and would have to design the whole shape from scratch — exactly what a plan is supposed to have already done.

## Gaps & required changes

1. **Nonexistent mirror targets (blocking).** caretake has exactly 7 modes — `triage, hygiene, unblock, trends, split, debug, report` (`ralph/skills/caretake/modes/_index.md`, `SKILL.md:41`). There is **no** `watch-upstream.md`, **no** `watch-pr.md`, and **no** "watcher" concept anywhere in `ralph/skills/caretake/`. The plan's Phase 1 ("mirror `modes/watch-upstream.md`") and AC #2 ("mirrors the sweep/report/heartbeat shape of `watch-upstream`") have no referent. The plan must either (a) drop the "mirror" framing and fully specify the sweep/report/loop shape itself, or (b) be put behind a separate plan that first creates the watcher family.

2. **No heartbeat fan-out exists (blocking).** Phase 2 says "add it to the heartbeat fan-out list alongside `watch-pr` and `watch-upstream`." There is **zero** occurrence of `heartbeat`, `fan-out`, or `watch` in `ralph/skills/caretake/` (`SKILL.md` mode table is the 7 modes only). The insertion point is fictional. Specify the actual SKILL.md change against the real mode table, or design the heartbeat mechanism as an explicit phase.

3. **No outcome-token registry / postcondition hook (blocking).** Phase 3 references `outcome-tokens.md` and "the postcondition hook allowlist (mirror `WATCH-PR` / `WATCH-UPSTREAM`)." There is **no** `ralph/skills/caretake/outcome-tokens.md`, and **no** hook under `ralph/hooks/scripts/` contains `WATCH-PR`, `WATCH-UPSTREAM`, `outcome`, or a caretake/triage postcondition allowlist. The `WATCH-BLOCKERS` token has no allowlist to be added to. Either build the token+hook subsystem as a first-class phase (with the real hook filename) or remove AC #3's hook dependency.

4. **Marker-format mismatch with what #1472 shipped (blocking for detection).** The review brief expects detection to read the `WAIT-issue=NNN` + `## Escalation` / `Unblock-When` marker format. That format appears **nowhere** in the `ralph/` plugin (searched the whole tree). What exists is the `## Unblock Request` marker in `unblock.md:9`. The plan's detection should key off real `blockedBy` edges from `get_issue` (which it can) and/or the actual `## Unblock Request` convention — not a marker format that was never shipped. State the exact marker/edge the sweep parses.

5. **Missing MCP tools the approach implies.** Surface is `add_dependency` and `advance_issue` only (`mcp-server/src/tools/relationship-tools.ts`); there is **no `list_dependencies`** and **no `remove_dependency`**. The plan's sweep avoids `list_dependencies` (it reads `blockedBy` per-issue via `get_issue`, which is fine), but it should call this out explicitly: enumeration is N× `get_issue` calls, not a single dependency-list call — a perf/rate-limit note belongs in the plan. If any future step needs `remove_dependency`, that tool must be added first (blocking).

6. **Test homes are undefined.** The "blocker-detection logic" test (Phase 4) has no module to target — the logic lives in skill markdown prose, which is not unit-testable. Either route the detection through a real MCP/lib function (testable) or replace the unit test with a documented manual verification. The hook-token test depends on gap #3 being resolved first.

## Verdict rationale

NEEDS_ITERATION. The problem is legitimate, but four of the plan's load-bearing anchors (watch-upstream/watch-pr modes, heartbeat fan-out, outcome-tokens registry, postcondition hook allowlist) and its detection marker format are fiction — they exist in neither the caretake skill nor the hooks tree. An implementer could not execute Phases 1–4 without first reverse-engineering and inventing the entire "watcher family" the plan assumes is already present. The plan must be re-grounded against the real caretake surface (7 modes, no watchers, no outcome-token hook, `## Unblock Request` marker, `blockedBy` from `get_issue`) and re-scoped to either build that infrastructure explicitly or stand alone without it.
