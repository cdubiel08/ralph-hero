## Summary

The plan adds a third caretake watcher — `--mode watch-blockers` — that resolves triage's `WAIT-issue=NNN` parking: it sweeps Human-Needed/Backlog items carrying a `blockedBy` dependency edge or a `## Escalation` body, advances them (default → Ready for Plan, + `## Unblocked` comment) once all blockers are CLOSED, leaves them on any OPEN blocker, and emits `WATCH-BLOCKERS <n> advanced, <m> still blocked`. It is doc + test only, mirroring the existing `watch-upstream` shape. Re-verified against the live tree, every anchor the plan cites exists and the approach is sound. APPROVED.

## Strengths

- **Correct asymmetry insight carried through.** The plan honors the load-bearing design from #1472: WAIT-pr/WAIT-upstream rest in Backlog (a watcher owns them), but WAIT-issue parks in Human Needed precisely *because* no watcher owned it — this plan is that missing watcher. It also keeps the default advance target = Ready for Plan to match the triage contract.
- **Dual detection signal (edge + `## Escalation` body) with a clear precedence rule** (prefer the edge; fall back to the escalation text; skip if neither) is robust against hand-written escalations.
- **Conservative advance posture** mirrors watch-upstream's "never false-advance": only an all-CLOSED blocker set advances; unresolvable blockers leave the item parked.

## Minor notes (non-blocking — for the implementer, not gates)

1. **Verify the `remove_dependency` parameter name before writing the call.** The plan writes `remove_dependency(number: NNN, blockedByNumber: <blocker>)`. `add_dependency` uses `blockedNumber` / `blockingNumber` (`relationship-tools.ts:348,361`); confirm `remove_dependency`'s actual schema (it lives at `relationship-tools.ts:428`) and match it exactly rather than assuming the `blockedByNumber` spelling. A wrong param name will be rejected by the tool schema at runtime.
2. **Enumeration cost.** The sweep does one `list_dependencies` (or `get_issue`) per candidate across two `list_issues` queries (Human Needed + Backlog, limit 250 each). On a large board that is a meaningful number of API calls per heartbeat tick — fine for now, but worth a one-line rate-limit note in the mode body (watch-upstream has the same shape, so this is parity, not a regression).
3. **Heartbeat child count bookkeeping.** Phase 3 correctly updates the "5 total" → "6 total" string at SKILL.md:149 and inserts the serial child at :146-147; the implementer should grep for every "5" occurrence tied to the fan-out so none is missed (the plan's Phase 3 verification already greps for `6 total`).

None of these block approval — they are precision reminders for implementation.
