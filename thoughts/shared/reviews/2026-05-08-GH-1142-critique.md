# GH-1142 Plan Critique — ralph-hero:unblock skill pair

## Verdict

**NEEDS_ITERATION** — three feasibility issues require correction (one substantive, two minor) before implementation. The plan is otherwise complete, well-scoped, and clearly written, with strong dispatchability and explicit phase dependencies. None of the issues are fundamental; all can be addressed with surgical edits to Phase 1 and Phase 4.

## Summary of Plan

Adds a paired skill set to bridge `Human Needed` issues back into the pipeline: `ralph-hero:ralph-unblock` (autonomous; posts blocking questions as `## Unblock Request` comments) and `ralph-hero:unblock` (interactive; captures answers via `AskUserQuestion`, posts `## Unblock Resolution`, transitions issue to one of four valid re-entry states). 4 phases: foundation (state graph + protocol), autonomous skill, interactive skill, surfacing/scheduling/docs. Estimate: M.

## Dimension Assessments

### 1. Completeness — PASS

All four phases define specific file changes with concrete contents. Each phase has explicit Success Criteria split into Automated/Manual sections. Phase 1 specifies exact `COMMAND_ALLOWED_STATES` entries, JSON edits, hook diff snippets, and event-type schemas. Phase 2 and 3 include full skill frontmatter, postcondition hook source, state-gate hook source, and eval-scenarios lists. Phase 4 includes the launchd plist template and CLAUDE.md insertion text.

The "Implementation Approach" section explicitly calls out the foundation-first ordering and per-skill independence rationale. Migration Notes, Performance Considerations, and Testing Strategy are all present.

### 2. Feasibility — FAIL

Three feasibility issues. The first is substantive; the other two are documentation/path mismatches that the planner partially anticipated but should still be corrected.

**(a) Phase 1.5 — `outcome-events.ts` does not exist; there is no event-type allowlist.**

The plan instructs:

> **File**: `plugin/ralph-knowledge/src/lib/outcome-events.ts` (or wherever `event_type` is enumerated — locate the enum during implementation)
> **Changes**: Add `unblock_requested` and `unblock_resolved` to the event-type allowlist with payload schemas

Verified against the codebase:

- `plugin/ralph-knowledge/src/lib/` does not exist as a directory.
- `event_type` is not enumerated anywhere. In `plugin/ralph-knowledge/src/db.ts:130-151`, `outcome_events.event_type` is a free-form `TEXT NOT NULL` column with no CHECK constraint or enum table. In `plugin/ralph-knowledge/src/index.ts:351`, the `knowledge_record_outcome` Zod schema treats it as `z.string().describe(...)` with no enum.
- The plan's hedge ("If the schema is keyed on a flat string union without per-event payloads, just add the two strings to the union") is *also* incorrect — there is no flat string union to add to.

**Net effect**: Phase 1.5 has no work to do. `unblock_requested` and `unblock_resolved` can be passed as event-type strings today without any code change in ralph-knowledge. The "Migration Notes" line ("The new outcome event types are additive; no schema migration in ralph-knowledge") is correct in spirit but contradicts the implementor's instructions in Phase 1.5.

**Required correction**: Replace Phase 1.5 with documentation only. Two acceptable framings:
- Drop Phase 1.5 entirely and note in Migration Notes that `event_type` is open-string and the new types are usable immediately, OR
- Reframe Phase 1.5 as a *documentation* change: extend `plugin/ralph-knowledge/src/index.ts:351` `.describe()` text or a separate `docs/outcome-events.md` to register the new event types and their canonical payloads, since there is no runtime allowlist to extend.

This also affects Phase 1's Automated Verification line "ralph-knowledge build passes" — that line stays valid only if the doc-only change actually touches a file in ralph-knowledge. If Phase 1.5 is dropped, remove that verification line too.

**(b) Phase 4.1 — `next_actions` lives in `directions-tools.ts`, not `dashboard-tools.ts`.**

The plan says:

> **File**: `plugin/ralph-hero/mcp-server/src/tools/dashboard-tools.ts` (or wherever `next_actions` is implemented — locate during implementation)

Actual location: `plugin/ralph-hero/mcp-server/src/tools/directions-tools.ts` (line 280 registers `ralph_hero__next_actions`). The planner's hedge correctly anticipates this, but the canonical path should be cited so the implementor doesn't waste a task cycle. Update to `directions-tools.ts`.

**(c) Phase 1.4 — `human-needed-outbound-block.sh` line numbers are stale.**

The plan claims insert "between the existing `command` check and the `current_state` check (lines 27–37)". Actual file shows the `command` check at lines 27-30 and `current_state` check at lines 33-40, so the placement is correct in spirit but the cited line range (27-37) doesn't span both blocks cleanly. The diff snippet itself is correct and unambiguous, so this is purely a citation polish issue. Either drop the line numbers or update to "lines 26-40".

### 5. Dispatchability — PASS (with one caveat)

This is a phase-based plan, not a per-task atomic plan, so the "every task is self-contained" check is loosely applicable. Reading each phase as a unit:

- **Phase 1** is dispatchable: each of the 5 changes lists exact file path, exact diff content, exact verification commands. The dependency between sub-changes 1 and 2 (TS hardcoded must match JSON, enforced by existing drift test) is called out explicitly.
- **Phase 2** is dispatchable: full skill frontmatter is given, full postcondition hook script is given, agent definition is given, eval scenarios are listed.
- **Phase 3** is dispatchable: full skill frontmatter, full state-gate hook script, eval scenarios.
- **Phase 4** is mostly dispatchable. The `next_actions` ranker change in 4.1 references an `unblockRequestAgeDays` signal that requires a per-issue comment-history fetch — this isn't currently a signal computed by `directions-tools.ts`. The plan should either (i) explicitly note the signal computation work or (ii) acknowledge the new signal must be wired through `next_actions` source data. As-is, an implementor following Phase 4 will discover this mid-task. This is a small caveat, not a blocker.

Phase dependencies are explicit: Phase 1 wires the state machine before any skill exists; Phase 2 requires the postcondition hook from Phase 1; Phase 3 requires the state-gate hook + Phase 1 outbound-block change. Phase 4 requires Phase 2 + 3 to be testable end-to-end.

Cross-phase integration testing is covered in the "Testing Strategy" section ("Key end-to-end happy path: escalate → autonomous unblock posts questions → interactive unblock answers and routes → next pipeline run picks it up").

## Issues to Address (for NEEDS_ITERATION)

1. **Phase 1.5 is structurally incorrect.** `plugin/ralph-knowledge/src/lib/outcome-events.ts` does not exist. `event_type` is a free-form `TEXT NOT NULL` column in `db.ts:130` with no enum or allowlist. The Zod schema in `index.ts:351` is `z.string()` — no union to extend. Either drop Phase 1.5 entirely (preferred) and update Migration Notes accordingly, or reframe it as a documentation-only change (extend `.describe()` text or add a registry doc). Also remove the corresponding "ralph-knowledge build passes" entry from Phase 1's Automated Verification if Phase 1.5 is dropped.

2. **Phase 4.1 cites the wrong file path for `next_actions`.** Update `plugin/ralph-hero/mcp-server/src/tools/dashboard-tools.ts` to `plugin/ralph-hero/mcp-server/src/tools/directions-tools.ts` (registration at line 280). The planner's hedge anticipates this but the canonical path should be cited.

3. **Phase 4.1 underspecifies the new `unblockRequestAgeDays` and `questionCount` signals.** These signals require parsing issue comments — a new data dependency for `next_actions`. Either add an explicit sub-step describing how the ranker will fetch/compute these, or explicitly defer this signal computation to the implementor with a documented acceptance criterion.

4. **(Minor)** Phase 1.4 line-number citation `(lines 27–37)` does not cleanly span the two blocks the diff sits between. Update to `(lines 26-40)` or drop the citation. Diff content itself is correct.
