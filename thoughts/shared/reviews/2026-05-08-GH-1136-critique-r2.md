# GH-1136 Plan Critique — Revision 2

**Plan**: [2026-05-07-GH-1136-autopilot-skill.md](https://github.com/cdubiel08/ralph-hero/blob/main/thoughts/shared/plans/2026-05-07-GH-1136-autopilot-skill.md) (revision 2)
**Verdict**: NEEDS_ITERATION (one critical regression introduced by R2)

## Summary

R2 substantially improves on R1 — seven of the eight R1 findings are addressed cleanly. The Tick Isolation section is well-constructed, the prompt-field state-vehicle is correct, the pre/post `get_issue` diff is the right replacement for text-grep, and the dispatchability table plus pre-drafted README/CLAUDE.md prose make the plan genuinely paste-ready.

However, **R2 introduces a new critical regression** while addressing R1 finding #3. Dropping the "CI-awaiting" bucket without simultaneously excluding "just-PR'd" issues from the next tick's `next_actions` pick creates a false-positive escalation loop: in interactive mode (the default), hero lands a PR and stops; the issue's workflow state is `In Review` which is in `ACTIONABLE_PHASES`; the next 60s tick re-picks the same issue; hero detects nothing to do; outcome is `no_progress`; three such ticks later autopilot wrongly escalates a perfectly healthy in-review issue.

This is a real bug, not a hypothetical. Below: per-finding verification, then the regression detail.

### R1 #3 — CI-awaiting bucket dropped — **FAIL (new regression)**

R2 dropped the 270s "PR awaiting CI" bucket entirely and now uses only `{60, 1200}`. The plan justifies this as "autopilot is a dispatcher, not a CI babysitter" — which is correct.

**But the implication wasn't followed through**: when hero in `RALPH_REVIEW_MODE=interactive` (the default) lands a PR, hero stops. The picked issue's workflow state is now `"In Review"`. On the next 60s tick, autopilot calls `next_actions(audience="agent")` again.

Verified in `plugin/ralph-hero/mcp-server/src/lib/directions.ts:180-185`:

```typescript
const ACTIONABLE_PHASES: ReadonlySet<string> = new Set([
  "Plan in Review",
  "In Review",
  "Ready for Plan",
  "Research Needed",
]);
```

`"In Review"` is in `ACTIONABLE_PHASES`. The just-PR'd issue is therefore the top candidate again. The plan filters to `kind == "issue"` only — but `scoreIssue` (lines 481-488) returns `kind: "issue"` for any item not flagged as lock-stale or tree-continue, regardless of workflow state. So the just-PR'd issue WILL be re-picked.

What happens next:
1. Tick 2 picks the same issue (`In Review`)
2. Worktree check passes (worktree was cleaned up by `pr-agent` after PR creation, or the worktree no longer matches because finish ran)
3. `pre.workflowState = "In Review"`
4. Dispatch `Skill("ralph-hero:hero", args="<picked> --review-mode interactive")`
5. Hero detects phase=INTEGRATE, in interactive mode it stops immediately without re-running anything (`hero/SKILL.md:454-458`)
6. `post.workflowState = "In Review"` (unchanged)
7. Outcome table row: `any | unchanged | no_progress`

This burns a `no_progress_streak` slot. Tick 3 and tick 4 same thing — three `no_progress` ticks in a row triggers Phase 3 Step 8 termination condition `no_progress_streak >= 3`, which **escalates the picked issue** with reason "autopilot detected no-progress streak of 3."

Result: autopilot moves a perfectly healthy in-review PR into `Human Needed` after ~3 minutes of polling, and stops the loop. This is much worse than R1's "wait 270s and check" — at least R1 gave CI a chance to complete.

**Fix options (any one):**

A. **Drop `"In Review"` from the autopilot's actionable filter** — when calling `next_actions`, filter out items whose `workflowState == "In Review"`. The PR is human-gated by design in interactive mode; autopilot must not touch it. Requires either a flag on `next_actions` (`includeInReview=false`) or a post-filter in the skill body (`items.filter(d => d.kind === "issue" && d.workflowState !== "In Review")`).

B. **Treat `"In Review"` as a `pr_landed` outcome** — when the picked issue's pre-state is already `"In Review"`, treat that as "this tick has nothing to do here, look elsewhere" without dispatching hero. Cleaner: add a Step 2.5 "if picked issue's workflowState is `In Review`, log `already_in_review`, do not dispatch, retry pick excluding that issue, or stop if no other candidates remain."

C. **Track per-tick "issues already PR'd this loop" in `state.history`** and exclude them from re-picking. The history field already exists in the state shape (line 174). Filter: `items.filter(d => !state.history.some(h => h.issue === d.issue && h.outcome === "pr_landed"))`.

Option B is the smallest delta to the plan and reuses existing tooling. Option A is the most principled — `next_actions(audience="agent")` arguably should not return `"In Review"` items at all (the agent cannot do anything useful with them in interactive mode), but that's a wider behavior change.

The plan needs to pick one and update Phase 2 Step 2 (pick) and Step 6 (outcome derivation) accordingly.

### R1 #4 — State-via-prompt-field — PASS WITH NOTES

`--state BASE64(json)` in the next ScheduleWakeup prompt is the correct mechanism. Verified:

- (a) Claude Code's `prompt` field accepts arbitrary string content; base64 is plain ASCII so no truncation risk from non-UTF8.
- (b) Encoded JSON shape (lines 167-172) is small: ~250 bytes uncompressed → ~340 bytes base64. After 20 iterations with 20 history entries, ~5 KB total — well under any reasonable prompt-length cap.
- (c) First-tick init path is well-handled at line 174: `If absent, initialize: {iteration: 1, no_progress_streak: 0, started_at: <now>, history: []}`.

One robustness improvement worth noting (not blocking): the plan should specify that `--state` must come AFTER all other flags so the base64 blob (which can contain `=` padding chars) doesn't confuse a positional parser. Or specify `--state=BASE64...` (equals-syntax) to be unambiguous. This is a minor implementation note, not a plan-level issue.

### R1 #5 — Pre/post `get_issue` diff outcome derivation — PASS WITH GAPS

The state-transition table at lines 246-253 covers the common paths. Sub-issue count delta as `advanced` (line 255) is a good catch.

**Edge cases the table misses:**

1. **Hero performed a SPLIT only** — sub-issue count grows but the parent's `workflowState` is unchanged. The plan handles this via the OR-condition at line 255 (`pre.subIssueCount < post.subIssueCount`). Good.

2. **Hero failed mid-implement** — if hero's impl-agent crashes, the workflow state may remain `"In Progress"` (lock state) without the worktree being cleaned up. Pre = `In Progress`, post = `In Progress`, table row matches `any | unchanged | no_progress`. This is **wrong outcome detection**: hero failed, but autopilot records it as a no-progress tick instead of an escalation. The next tick's worktree-liveness gate (Step 3) will catch it and escalate, so the system recovers — but the audit log entry for tick N records `no_progress` when the truth was `interrupted`. Minor forensic issue; acceptable for MVP if documented.

3. **Hero detected ambiguous spec and escalated WITHOUT moving to Human Needed** — if hero posts an "I need clarification" comment but doesn't explicitly call `__ESCALATE__`, post.workflowState may be unchanged. Same as case 2 — rolls into `no_progress`. The plan's no-progress streak then handles it, but slowly (3 ticks). Acceptable.

4. **Hero advanced through MULTIPLE phases in one tick** — e.g., started at `Backlog`, ran SPLIT then RESEARCH then landed at `Ready for Plan`. Table row 3 (`Backlog/Research Needed → Ready for Plan/Plan in Review/In Progress`) covers this as `advanced`. Good.

5. **State went BACKWARD** — e.g., issue starts at `In Progress`, hero detected it shouldn't have been there and reverted to `Ready for Plan`. Pre = `In Progress`, post = `Ready for Plan` — table doesn't have this row. Falls into `any | unchanged | no_progress` (which is wrong because pre != post). **Missing row.**

Recommend adding a catch-all row: `any | (different from pre, not in above rows) | other_change | yes (treat as advanced)` so any unexpected state transition is recorded as progress and not silently dropped. The state machine is supposed to be monotonic but we shouldn't trust that for outcome derivation.
