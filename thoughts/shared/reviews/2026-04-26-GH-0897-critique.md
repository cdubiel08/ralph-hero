# Plan Critique: GH-897 — Stub leak through traverse, search (FTS leg), and memory_stats

**Verdict: APPROVED**

The plan is single-phase, mechanical, and grounded in a complete code trace. Every file location and predicate cited in the plan was independently re-verified against the working tree. The work is dispatchable to an implementation agent without further context.

## Dimension Scoring

### 1. Completeness — PASS

All bypass sites are enumerated with exact line ranges and the fix predicate is the same canonical idiom (`is_stub = 0 OR is_stub IS NULL`) used by `graph-builder.ts:33`. Three source files (`traverse.ts`, `search.ts`, `index.ts`) and four test files (`traverse.test.ts`, `search.test.ts`, `memory-stats.test.ts`, `graph-builder.test.ts`) are all enumerated, each with a per-file task. The plan documents both implementation tasks and regression-test tasks, with the latter exercising production code paths rather than asserting filter syntax.

### 2. Feasibility — PASS

Spot-checked every cited file and line range against the actual source:

- `traverse.ts:51, :108` — `LEFT JOIN documents` exactly as described. Plan's choice to filter on the outer SELECT (not the recursive CTE body) with `WHERE d.id IS NULL OR d.is_stub = 0 OR d.is_stub IS NULL` is correct — the `d.id IS NULL` term preserves orphan-relationship rows.
- `search.ts:123-153, :155-171` — confirmed `conditions` array exists with the `documents_fts MATCH @query` predicate as anchor; adding a stub filter as a non-bound literal is straightforward and matches the existing pattern.
- `search.ts:101-103` — `rebuildIndex()` does `INSERT ... SELECT FROM documents` with no filter; plan correctly chooses approach (a) query-time filter (avoids forcing a rebuild on existing installs).
- `index.ts:196, 213-215, 224-228, 240-243, 262-268` — five aggregation/scan queries, each correctly identified. The plan's defense-in-depth additions on the v2-fallback query and `last_reflection_at` query are appropriate.
- `db.ts:181, 241` — `is_stub` column added via migration with `DEFAULT 0`; `upsertStubDocument` writes `title = id`. Both verified.
- `reindex.ts:160-167` — both typed (`db.upsertStubDocument(rel.targetId)` then `addRelationship(... rel.type)`) and untyped (`db.addRelationship(... "untyped", edge.context)`) paths create stubs identically. Plan's decision to test both paths in §1.4 is well-grounded.
- `graph-builder.ts:33` — canonical predicate confirmed verbatim.

All four test files (`traverse.test.ts`, `search.test.ts`, `memory-stats.test.ts`, `graph-builder.test.ts`) exist with the `:memory:` `KnowledgeDB` pattern and the helpers (`seedDoc`, `callStats`) the plan refers to.

### 3. Clarity — PASS

Success criteria are specific and testable. Each acceptance bullet either prescribes an exact predicate string or names a property of returned data that can be asserted. The Verification section ends with `npm test` — a single, runnable command. Automated Verification §"Phase Success Criteria" includes a `grep -rn "is_stub = 0 OR is_stub IS NULL"` count check that turns the canonical-predicate constraint into a test.

Minor note (not blocking): the grep-count expectation is "approximately 7+" and the actual after-patch count is 1 (graph-builder existing) + 2 (traverse outer SELECTs) + 1 (search conditions) + 5 (memory_stats sites = lines 196, 213, 224, 241, 262 per the task spec) = **9 hits**. ### 4. Scope — PASS

"What We're NOT Doing" is unusually explicit: parser hardening, allowlist/validation, FTS auto-rebuild, fixing `knowledge_subgraph`, fixing the vector leg, schema migrations, and refactoring into a helper function are all called out with rationale. The "no helper function" decision is well-defended (three lines in three files with different SQL contexts — agreed, a helper would obscure more than it saves).

The decision-record paragraph for approach (a) vs (b) at search.ts is exemplary: states what was chosen, why, and what the alternative would cost. The same level of rigor appears in the traverse.ts outer-vs-inner-CTE filter decision.
