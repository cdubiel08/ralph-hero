# Plan Critique: GH-0918 — Hello Deterministic Directions

## Summary

Verdict: **NEEDS_ITERATION**.

The plan is well-researched, motivates the change crisply (Option B from GH-0480), partitions work into three independently-shippable phases, and lists explicit ranking weights with a deterministic algorithm. However, three issues prevent immediate approval:

1. Phase 2's import block points `resolveProjectOwner` and `resolveProjectNumbers` at `helpers.js`, but both functions live in `types.ts`. A subagent dispatched on Phase 2 with zero additional context would write a non-compiling file.
2. The plan repeatedly references `dashboard-tools.test.ts` (e.g., "mirror `dashboard-tools.test.ts` patterns", "`dashboard-tools.test.ts` still passes"), but no such file exists. The actual test file is `dashboard.test.ts` (pure-function tests, no `client.projectQuery` mocking demonstrated). Phase 2's "mirror patterns" instruction has no concrete reference, leaving the dispatched subagent to invent a mock harness.
3. The `Direction` interface is described twice with subtly different `kind` enums: in the algorithm prose (lines 154–155: `kind` includes `"tree-continue"` and `"lock-stale"` as first-class kinds) versus the dispatch table (Step 5, line 583: `tree-continue` and `lock-stale` rows are listed but the underlying issue still exists with a `workflowState`). The plan should either treat `kind` as a presentation tag layered over `kind: "issue"` or commit to disjoint kinds — both consumers (`reason` builder and dispatch table) need the same model.

Also worth flagging (not blocking, but important): the issue carries an **M** estimate, and the ralph-review skill constraint is "XS/Small estimates only." The user explicitly invoked review on it, so this is being honored, but the underlying mismatch (M-sized issue with three sub-phases) is a strong signal this should have been split into three S issues before reaching plan review.

## Dimensions

### 1. Completeness — PASS

All three phases enumerate the files to create/modify, the GraphQL change, the new types, the test names (13 + 6 cases), and explicit success criteria with `npm run build` / `npm test` commands. The "What We're NOT Doing" section is generous and well-bounded.

Minor gap: the plan says `DashboardItem` may need `parentNumber, parentState` added "in `lib/dashboard.ts` — verify" but does not commit to the change. A dispatched subagent will need to verify and add the fields. Acceptable, but slightly hand-wavy for a fully-dispatchable plan.

### 2. Feasibility — FAIL

Three concrete technical issues:

- **Wrong import path for `resolveProjectOwner` / `resolveProjectNumbers`.** Plan Phase 2 (lines 391–393) writes:
  ```typescript
  import {
    ensureFieldCache,
    resolveProjectNumbers,
    resolveProjectOwner,
  } from "../lib/helpers.js";
  ```
  Verified: `resolveProjectOwner` is at `src/types.ts:296` and `resolveProjectNumbers` is at `src/types.ts:306`. `ensureFieldCache` IS in `helpers.ts:116`. The plan groups them as one import — they need two import lines. As written, Phase 2 will not compile.

- **Test-pattern reference is to a nonexistent file.** Plan claims to "mirror `dashboard-tools.test.ts` patterns" for the new `directions-tools.test.ts`. There is no `dashboard-tools.test.ts` in `src/__tests__/`. The closest existing file is `dashboard.test.ts`, which is a pure-function test suite (line 4: "All functions under test are pure (no I/O), so no mocking is needed"). It does not demonstrate how to mock `client.projectQuery`. A subagent will have to invent the mock harness — which is feasible (other test files like `issue-tools.test.ts` likely demonstrate it) but the cited reference does not exist.

- **`closedAt` is already fetched.** Plan claims (line 176) that `trackedInIssues.nodes.closedAt` needs to be added. The existing `DASHBOARD_ITEMS_QUERY` at line 235 already fetches `closedAt` on the parent Issue object. The plan's incremental graphql change adds it inside `trackedInIssues(first: 3) { nodes { number state closedAt } }` (parent edge). That is correct *for the parent edge*, but the prose conflates the existing `content.closedAt` with the new `trackedInIssues.nodes.closedAt`. A reader might think `closedAt` is missing from the schema entirely and over-engineer. Tighten the wording: "The parent Issue (`trackedInIssues.nodes`) needs its `closedAt` fetched; this differs from the candidate's own `closedAt` already in the query."

### 3. Clarity — PASS (with one ambiguity)

- Success criteria are specific and testable, using the required `- [ ] Automated:` / `- [ ] Manual:` shape. Multiple grep-based smoke checks add good lightweight regression catches.
- The ranking algorithm is laid out in pseudocode with explicit constants and weights — exactly what's needed for deterministic behavior.
- Ambiguity: the `Direction.kind` enum is `"issue" | "pr" | "tree-continue" | "lock-stale"`. But a tree-continue or lock-stale direction is *also* an issue (it has an `issue` field populated). Is `kind` a presentation tag or a discriminated union? The dispatch table (lines 583–593) treats them as exclusive (single agent per kind), which implies discriminated union. The score function (line 263 returns `isLockStale, isTreeContinue` as flags) implies tags. Pick one model; the test fixtures and the `reason` string builder need it.

### 4. Scope — PASS

"What We're NOT Doing" is comprehensive: nine bullets covering `pipeline_dashboard` preservation, `pick_actionable_issue` non-changes, rendering, PR fetching, GraphQL surface, weights config, other consumers, Stop hooks. Output budget regression tested via grep. Good fences.

Phase 1: dispatchable.

Phase 2: NOT cleanly dispatchable as written. A subagent given only Phase 2 + the plan would:
- write incorrect imports (helpers vs types — see Feasibility)
- have no concrete mock-harness reference
- have to flip back to read Phase 1's `directions.ts` skeleton to know what `RankConfig` shape to wire up. (This is normal cross-phase dependency, but the plan does not explicitly state "Phase 2 imports from `src/lib/directions.ts` which Phase 1 produces" — it's implied. State it.)

Phase 3: Mostly dispatchable. Has six discrete sub-tasks (1: Step 1 fetch; 2: Step 2 orient; 3: Step 3 directions; 4: Step 4 picker; 5: Step 5 dispatch table; 6: frontmatter; 7: Constraints). Each sub-task names the section to edit. Good. One edge: sub-task 4 says "Picker options map 1:1 to `directions[]` entries" — what happens if `directions` is empty? Step 3 says "end with *'Nothing urgent jumping out…'* and stop." So Step 4 is skipped on empty. State that explicitly in sub-task 4 to remove ambiguity.

## Recommendations to Address Before Re-Review

1. **Fix the imports in Phase 2's code skeleton.** Split into:
   ```typescript
   import { ensureFieldCache } from "../lib/helpers.js";
   import { resolveProjectOwner, resolveProjectNumbers } from "../types.js";
   ```
2. **Replace the `dashboard-tools.test.ts` reference** with a real test file that demonstrates `client.projectQuery` mocking (e.g., `issue-tools.test.ts` or whichever test currently mocks the project endpoint). Or note explicitly: "no existing test mocks `client.projectQuery` against `paginateConnection`; build the harness from scratch using vitest's `vi.fn()`."
3. **Disambiguate `Direction.kind`.** Either:
   - (a) make it a presentation tag and add a separate `agent: "review-agent" | "plan-agent" | …` field to drive dispatch, OR
   - (b) keep it as a discriminated union but clarify in `scoreIssue` that the function returns the *winning* kind, not flags. Then update the dispatch table to consume `direction.kind` directly.
4. **Tighten the `closedAt` prose** so it's clear which `closedAt` is new (`trackedInIssues.nodes.closedAt` — parent's closure date) vs. already fetched (`content.closedAt` — candidate's own).
5. **State Phase 2's dependency on Phase 1 explicitly** in Phase 2's overview ("Phase 2 imports `rankDirections, DEFAULT_RANK_CONFIG, OpenPR, RankConfig` from the `src/lib/directions.ts` produced in Phase 1.").
6. **Specify Step 4 picker behavior on empty directions** (skip Step 4 entirely, exit after Step 3's prose).
7. *(Out of scope but recommended)*: split this M issue into three S issues (one per phase). Each phase already has its own success criteria and is independently mergeable per the plan's own framing.
