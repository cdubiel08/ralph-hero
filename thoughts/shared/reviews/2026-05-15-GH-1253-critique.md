## Detailed Findings

### Feasibility — missing artifacts (blocking)

The plan frontmatter declares:

```yaml
parent_plan: thoughts/shared/plans/2026-05-14-GH-1252-ralph-hero-cos-mode.md
```

And the body uses Obsidian-style backlinks:

- `builds_on:: [[2026-05-14-GH-1252-ralph-hero-cos-mode]]`
- `builds_on:: [[2026-05-14-pi-coding-harness-as-chief-of-staff]]`
- `builds_on:: [[2026-05-14-pi-gemma-4-claude-code-setups]]`

Disk check:

```
$ ls thoughts/shared/plans/2026-05-14-GH-1252-*  -> not found
$ ls thoughts/shared/research/2026-05-14-pi-coding-harness-as-chief-of-staff.md -> not found
$ ls thoughts/shared/research/2026-05-14-pi-gemma-4-claude-code-setups.md -> not found
```

Impact: the plan claims to inherit constraints from the parent plan ("Shared Constraints" section says they are "inherited verbatim from the parent plan"), but those constraints cannot be verified because the parent plan is not present. The Implementation Approach for downstream phases (2–6) is also only summarized inline — a reviewer cannot cross-check whether Phase 1's contract surface actually satisfies the downstream phases' needs.

Recommended fixes (either is acceptable):
1. Commit the parent plan and primary research docs to `thoughts/shared/plans/` and `thoughts/shared/research/` so the graph is whole, or
2. Drop the `parent_plan` frontmatter field and `builds_on::` edges to missing docs, and inline the constraints they would have provided.

Option 1 is strongly preferred — it preserves the plan-of-plans hierarchy GH-1252 is supposed to anchor.

### Feasibility — unverified external claims

The following claims are plausible but not verified by this critique:

- `pi install pi-mcp-adapter`, `pi install @walterra/pi-charts`, `pi install pi-web-access` — assumed to be the correct install commands for pi 0.74.0. No reference link to pi-mcp-adapter docs is provided.
- `npx -y ralph-hero-knowledge-index@latest` is the documented entry for the ralph-knowledge MCP server — the `plugin/ralph-knowledge/` package exists locally but the published npm name should be verified against `plugin/ralph-knowledge/package.json` before Task 1.3 runs.
- `lifecycle: "lazy"` and `directTools: true` / `directToolAllowlist` are valid keys in `~/.config/mcp/mcp.json` — these look like pi-mcp-adapter specific extensions; a one-line link to the adapter's README in the plan would harden the review.

None of these are blocking individually — they are normal "verify-as-you-implement" items — but flagging them so the implementer doesn't get stuck mid-task.

### Clarity — minor

- Task 1.2 acceptance specifies `--no-session --no-context-files --provider mlx-local --model "$COS_MODEL" --tools "..." -p "$PROMPT"`. The flag set is concrete and good. Recommend the implementer also confirms `pi --help` on 0.74.0 supports `--no-session` and `--no-context-files` exactly as named — these flag names should be sanity-checked once before Task 1.2 starts.
- The JSONL row example uses `prompt_hash` (snake_case) while the GitHub issue body uses `prompt-hash` (kebab-case). Plan acceptance criteria says `prompt_hash` — agree with the plan; suggest fixing the issue body for consistency.

### Scope — clean

"What We're NOT Doing" is unusually thorough. No suggested changes.

### Dispatchability — clean

Each task is independently dispatchable. The dependency graph is shallow (1.1 → 1.2 → 1.5; 1.3 and 1.4 parallel). A subagent picking up any single task should have everything needed inline.

## Recommendations for Iteration

1. **(blocking) Commit the missing parent plan and research docs** so `builds_on::` and `parent_plan` edges resolve. If they have not been written yet, either author them as part of this phase or drop the references.
2. **(non-blocking, do-during-implementation) Verify pi 0.74.0 flag names** (`--no-session`, `--no-context-files`, `--provider`, `--model`, `--tools`, `-p`) match the actual `pi --help` output before Task 1.2 starts. Adjust acceptance criteria if any flag is misnamed.
3. **(non-blocking) Verify ralph-knowledge MCP npm package name** matches whatever is in `plugin/ralph-knowledge/package.json` (or the published name) before Task 1.3.
4. **(nit) Reconcile `prompt_hash` vs `prompt-hash`** in the GH-1253 issue body to match the plan's JSONL acceptance.

## Conclusion

The plan is technically well-formed and would be a clean approve if the parent plan and primary research existed on disk. Routing back to "Ready for Plan" with `needs-iteration` so those artifacts can be added (or the references removed) before implementation begins.
