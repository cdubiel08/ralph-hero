These are observations that can be addressed during implementation if encountered; none rise to `needs-iteration`:

- Task 1.2 acceptance bullet 3 says hook error messages name "the step index" but the `by_step` keys are stringified integers (per Task 1.1's schema comment) — the implementation should confirm that `yq`'s output of the map key matches the human-readable step index (likely fine since both are the stringified int, just worth double-checking when writing the iteration block).
- §Open Questions §"Severity-filtered prior-signal triggers" correctly flags that the current broad "any signal on N-1 escalates N" may over-escalate under load. The plan punts this to follow-up — appropriate for a first-landing, but worth surfacing in the PR description when this ships so the team has a clear metric to watch (escalation rate per journey).
- Task 2.1 acceptance 7 caps the section at 80 lines; given the seven subsections plus YAML example, that's tight but achievable. If it grows past 80 during drafting, consider moving the Example into `skills/reflect/references/step-importance-escalation-example.yaml` rather than dropping content.
- Integration Testing item enumerates 5 files (including the plan doc itself) but §Desired End State item 5 says "Diff scope is exactly four files." The plan doc commits alongside the impl PR per project convention — this is consistent, but worth harmonizing language ("four source files + the plan doc" or similar).
