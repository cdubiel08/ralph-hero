# Plan critique — GH-1159: Remove deprecated `hello_directions` and `pick_actionable_issue`

## Summary

Single-phase XS plan to delete two deprecated MCP tools and migrate two production callers (skill allowed-tools lists) plus two `justfile` recipes to `next_actions(limit=1, audience="agent")`. Verified against the live tree on 2026-05-09. All file paths, line ranges, and dependency claims hold up. Approved without iteration.

## 1. Completeness — PASS

Every artifact named in the issue body is addressed:

- Server registrations (both deprecated tools) — Tasks 1.1, 1.2
- Skill allowed-tools (team + hero) — Tasks 1.3, 1.4
- `justfile` migration (a scope item NOT in the issue body, but caught during planning research) — Task 1.5
- Test deletions (whole-file + selective prune) — Tasks 1.6, 1.7
- Doc cleanup (root `CLAUDE.md`) — Task 1.8
- Final consistency grep — Task 1.9

The plan also explicitly notes which files DON'T need edits (`plugin/ralph-hero/README.md`, `plugin/ralph-hero/CLAUDE.md` — both stale references in the issue body), which is the right level of due diligence for an XS deletion plan.

The "What we're NOT doing" section is bounded and specific (helpers `makeRunDirections` and `extractUnblockSignal` stay; `next_actions` API surface untouched; agents/ untouched).

## 2. Feasibility — PASS

Spot-checked file/line claims via grep on 2026-05-09:

- `directions-tools.ts:481` — `server.tool("ralph_hero__hello_directions", ...)` confirmed at this line. Plan says 477-534; the surrounding comment banner extends back to ~477, so the range is reasonable.
- `issue-tools.ts:1665` — comment banner `// ralph_hero__pick_actionable_issue [DEPRECATED]`; `server.tool` at 1679; closing `},)` at 1871. Range 1665-1871 confirmed.
- `team/SKILL.md:23` — `pick_actionable_issue` line; line 22 has `next_actions`. Confirmed.
- `hero/SKILL.md:37` — `pick_actionable_issue` line; line 36 has `next_actions`. Confirmed.
- `justfile:60` and `justfile:637` — both call deprecated tool with the documented inline migration NOTE comment. Confirmed.
- `directions-tools.test.ts` — describe blocks confirmed at 313 (hello_directions), 698 (next_actions), 750 (hello_directions backwards-compat — plan says 747, drift of 3 lines, acceptable since edits are content-anchored), 826 (extractUnblockSignal — confirmed).
- `pick-actionable-issue.test.ts` — exists.
- `CLAUDE.md:113` — confirmed: `| hygiene-tools.ts | pick_actionable_issue, project_hygiene |`. The plan's diagnosis that `pick_actionable_issue` is incorrectly grouped under `hygiene-tools.ts` (it actually lives in `issue-tools.ts`) is correct — dropping it cleanly is the right call.
- Helpers `makeRunDirections` (line 363) and `extractUnblockSignal` (line 132) confirmed exported and consumed by both deprecated and live tools.

Dependency chain is real: parent group plan's Phases 1, 2, 3 are CLOSED (issues #1154, #1155, #1156). The widened `next_actions` agent set from Phase 1 (GH-1154) is exactly what makes the migration semantically equivalent.

## 3. Clarity — PASS

Phase Success Criteria split cleanly into Automated (npm build/test, grep checks) and Manual (`mcp list-tools`, skill load tests, `just pick`, commit message contains `#minor`). Each criterion is a verifiable command or observable outcome. No vague aspirational language.

Task acceptance lists are specific. Example: Task 1.5 names exact line edits ("doc comment changes from `# Find next actionable issue` to `# Find next actionable issue (rank-1 from next_actions, audience=agent)`") and explicit signature changes (recipe becomes parameter-less).

## 4. Scope — PASS

"What We're NOT Doing" enumerates 7 explicit boundaries. Most importantly, it pins down that helpers stay, the `next_actions` API stays untouched, and no new tests are added (parity tests die with the wrapper, which is correct — the wrapper's filter semantics WERE the test surface).

Out-of-scope justifications hold: README has no references (verified by plan), agents/ has no references (verified), GitHub Actions workflows have no references (verification step in 1.9).

## 5. Dispatchability — PASS

All 9 tasks have files (with create/modify/delete), tdd, complexity, depends_on, and acceptance fields. Dependencies are minimal and correct:

- Task 1.6 depends on 1.2 (delete test only after deleting source — avoids transient broken-import state)
- Task 1.7 depends on 1.1 (same rationale, but for `directions-tools.test.ts` after the source-side delete)
- Task 1.9 depends on all prior tasks (final grep verification)
- All other tasks have `depends_on: null` — they're independent file edits

Each task is small enough for a subagent to execute without re-reading the full plan. The acceptance criteria are concrete enough to mechanically verify (line-anchored, content-anchored, or grep-anchored).

## Minor observations (not blockers)

1. **Line-number drift**: A few line references drift by 1-5 lines (e.g., `directions-tools.ts:477-534` → actual `server.tool` at 481; test describe at 750 vs plan-claimed 747). Since all task acceptance criteria are content-anchored ("the `server.tool("ralph_hero__hello_directions", ...)` call ... is removed entirely"), this is harmless. An impl-agent following the plan will not be misled.

2. **Task 1.8 wording quirk**: The acceptance text reads `Line 113 changes from ... to ... minus pick_actionable_issue — concretely: the row reads | hygiene-tools.ts | project_hygiene | after the edit`. The "concretely" sentence is the right instruction; the surrounding diff-by-subtraction phrasing is slightly awkward. An impl-agent will parse the concrete result correctly.

3. **Justfile recipe signature change**: Task 1.5 removes recipe parameters (`state`, `max-estimate`) since `next_actions` ignores them. This is the right call — but worth flagging that any hypothetical user with a `just pick state=...` muscle memory will see "unexpected parameter" errors. The plan documents this as acceptable since the recipes are non-public CLI surfaces.

## Verdict

**APPROVED**. The plan is well-scoped, technically accurate, and dispatchable. The single-phase XS shape is appropriate for a pure deletion-and-migration task with no test additions. Minor line-number drifts are content-anchored away. Ready for implementation.
