# Plan Critique — GH-1250 Hero Workflow Model-Tier Optimization

## Verdict

NEEDS_ITERATION — the plan is technically sound and the verified mechanics
section is exceptionally well-grounded, but it contains a small number of
file-path errors that will cause Phase 1, Phase 4, and Phase 5 to fail
"Automated Verification" as written. These are surgical edits, not a
re-design.

## Completeness — PASS

All five phases are defined with explicit file paths, before/after diffs,
rationale, and per-phase Automated + Manual Verification. The non-goals
section is unambiguous. Migration notes and rollback are addressed. The
expected-impact table at the end gives a concrete delta target.

## Feasibility — FAIL (path errors)

The plan references `plugin/ralph-hero/CLAUDE.md` in three places (Phase 1
"Cross-reference in CLAUDE.md", Phase 4 step 5 "CLAUDE.md table: note the
dedup behavior", Phase 5 step 2 "CLAUDE.md per-phase agents table"). That
file does NOT exist. The repository's `CLAUDE.md` lives at the **repo
root** (`/CLAUDE.md`), not under `plugin/ralph-hero/`. The Per-Phase Agents
table the plan wants to update is at `CLAUDE.md:58-71`.

Other file references verified accurate:
- `plugin/ralph-hero/agents/{split,impl,plan,review}-agent.md` — exist
- `plugin/ralph-hero/skills/ralph-impl/SKILL.md` — exists; line 298 hosts
  the `Agent(subagent_type=..., model=selected, ...)` precedent as cited
- `plugin/ralph-hero/skills/ralph-impl/SKILL.md:105-130` — Plan Reference
  reader exists as described
- `plugin/ralph-hero/hooks/scripts/impl-plan-required.sh:59-67` — Plan
  Reference acceptance path verified (lines 59-67 contain the
  `RALPH_PLAN_REFERENCE` check)
- `plugin/ralph-hero/skills/ralph-val/SKILL.md:442-452` — verdict-prefix
  protocol exists as described
- `plugin/ralph-hero/skills/ralph-plan/SKILL.md:152-159` — `--parent-plan`
  handling exists as described
- `plugin/ralph-hero/hooks/scripts/{impl,plan,val}-postcondition.sh` — all
  three hooks exist (the plan correctly avoids assuming the val pattern
  exactly matches impl/plan)
- `plugin/ralph-hero/README.md` — exists (Phase 5 target)

Required correction: every reference to `plugin/ralph-hero/CLAUDE.md`
should resolve to `CLAUDE.md` (repo root). The Phase 1 grep check
`grep -q "model-tier-policy" plugin/ralph-hero/CLAUDE.md` and the Phase 5
check `awk '/split-agent/{print}/impl-agent/{print}' plugin/ralph-hero/CLAUDE.md`
will both fail because the path does not exist.

## Clarity — PASS

Success criteria are split into `Automated Verification` and `Manual
Verification` per phase using the canonical `- [ ]` checkbox style. The
`IMPL BLOCKED` and `PLAN REUSED` terminal prefixes are specified verbatim
with examples. The synthetic-BLOCKED test procedure (Test B) is
operationally explicit. Phase 4's mapping rules (frontmatter, GH-NNN in
heading, title-token-overlap >= 70%) are concrete enough to implement
without further design.

Minor nit: the Phase 4 mapping rules use letters `(b)` and `(c)` where
the surrounding numbered list uses `1./2./3.`. Renumber to keep the
hierarchy consistent.

## Scope — PASS

"What We're NOT Doing" enumerates six explicit exclusions covering
telemetry, research sub-agents, auto-replanning, MCP changes,
plan-epic/review tier changes, and retrofit. The boundary against the
deferred "plan-iteration efficiency" work is clear. The five-phase
ordering is justified by reversibility and independent testability — each
phase is a useful checkpoint.

One scope concern that doesn't change the verdict: the issue is sized
**M**, but Phase 3 (hero dispatch wiring + BLOCKED escalation) and Phase
4 (plan dedup with new postcondition prefix acceptance) each have the
complexity profile of an S issue on their own. The plan is internally
honest about Phase 3 being "the riskiest" and Phase 4 being "the biggest
token saver." The M estimate is defensible because the changes are all
single-file frontmatter or contained skill/hook edits with no new MCP
tooling — but if iteration introduces additional verification steps, the
plan should be split.

## Dispatchability — PASS WITH MINOR GAPS

Each phase enumerates files-to-modify, includes verifiable acceptance
criteria, and is independently dispatchable to a single sub-agent. The
file/acceptance/complexity shape is implicit rather than explicit (the
plan uses prose sub-sections rather than a structured field table per
task), but the content satisfies every dispatchability requirement when
read with a generous interpretation:

- `files`: enumerated per phase (e.g., Phase 3 lists
  `skills/hero/SKILL.md`, `skills/ralph-impl/SKILL.md`,
  `hooks/scripts/impl-postcondition.sh`)
- `tdd`: not explicit per task, but the synthetic test recipes in the
  Testing Strategy section play the role
- `complexity`: implicit (Phase 5 is documentation = low; Phase 3 is
  multi-file orchestration = medium)
- `depends_on`: explicit in the Implementation Approach intro (1 → 5)
- `acceptance`: per-phase Automated + Manual checklists

If the implementer agent reads the plan top-to-bottom, the missing
structured-table format will not block it. If a future revision wants to
make this airtight, a single per-phase metadata block would do it.

The Phase 3 step 2 "Also update `impl-postcondition.sh` (hook) if it
currently treats Stop without an artifact comment as a failure" is the
only spot where the implementer must do additional investigation. The
plan acknowledges this with "Exact transcript-line discovery mechanism
depends on how the hook currently reads agent output — verify against
existing val-postcondition.sh". That's acceptable but borderline — a
20-second investigation would have let the planner specify the exact
read mechanism.

## Issues Identified (NEEDS_ITERATION feedback)

The following must be addressed before approval:

1. **File path correction (3 occurrences)**: every reference to
   `plugin/ralph-hero/CLAUDE.md` is wrong; correct path is `CLAUDE.md`
   (repo root). Affects Phase 1 (step 2 + Automated Verification),
   Phase 4 (step 5), Phase 5 (step 2 + Automated Verification). Without
   this fix the grep checks will fail and the table update will land in
   a non-existent file.

2. **Phase 3 step 2 ambiguity**: the `impl-postcondition.sh` "verify
   transcript-line discovery against val-postcondition.sh" hand-wave
   should be resolved before implementation. Read val-postcondition.sh
   once, specify the exact pattern, and bake it into the plan.

3. **Phase 4 numbering**: convert the mapping rules letter list
   (`a./b./c./d./e.`) inside step 1 to a consistent style with the
   surrounding numbered list, or explicitly note the hierarchy.

Non-blocking observations:
- Consider whether the M estimate should be S+S (split Phases 1+2 from
  3+4+5). Not required, but the plan itself notes Phase 3 as risky.
- The `--parent-plan PATH` flag is referenced in Step 3.5 but the plan
  doesn't explicitly verify the ralph-plan-epic dispatcher passes the
  child issue NUMBER (Phase 4 step 3 says "verify" but doesn't include
  the verification as an acceptance criterion). Add an Automated check
  if possible.

## Decision

NEEDS_ITERATION. The issues are mechanical (path errors + minor
clarifications), not structural. After the file-path corrections land,
this plan is ready for implementation.
