# Review: Capability-tier model config — generalize RALPH_IMPL_MODEL (GH-1593)

## Plan Reference

`thoughts/shared/plans/2026-07-26-GH-1593-capability-tier-model-config.md` (research: `thoughts/shared/research/2026-07-26-GH-1593-capability-tier-model-config.md`)

## The ceremony test (adversarial check, answered honestly)

The sharpest question: is a YAML config + build-time codegen + CI drift check genuinely lighter or more portable than the ~35 static pins it governs, or net-new ceremony of the kind epic #1588 exists to remove?

**Honest accounting.** The machinery is heavier in artifact count than the thing governed: ~6-8 new artifacts (`.ralph-models.yml` with a 35-entry hand-maintained site manifest, a Zod loader + vitest suite in mcp-server, a standalone renderer + package.json + node:test suite, a bash CI wrapper, a CI job) to govern ~35 one-word literals that have changed roughly three times in repo history (GH-1487, the 2026-07-01 `best` retier, GH-1538). It also levies a permanent tax: every future skill edit that adds or moves a `model="` literal now requires a manifest edit or CI fails. Under a Claude-Code-only present, the pins-as-greppable-prose status quo is cheaper.

**Why this is still not teardown-worthy.** Epic #1588 has two thrusts — surface reduction AND portable enforcement — and this feature is squarely the second. The pattern here (repo-root YAML + scripts/ + CI verifier instead of prose convention) is the same move #1589's merge gate made, i.e., it is the ceremony the epic *adds on purpose*, not the skill-prose rails it removes. Two payoffs are real today, not speculative: (a) AC-1 becomes permanent — nothing currently stops silent tier drift, the exact GH-1452-class rot `check-doc-rosters.sh` was built for; (b) the non-Fable retarget becomes a one-file edit instead of the all-flattening `CLAUDE_CODE_SUBAGENT_MODEL` blunt instrument. The third payoff (a non-Claude-Code harness reading the YAML) is speculative until such a harness exists, and the plan says so honestly — its Risks section leads with this exact skeptic's case rather than burying it.

**Where the ceremony IS trimmable** (recommended, not blocking): the mcp-server Zod loader ships with **zero consumers** — the plan itself says "No registration in `index.ts` — no tool consumes it yet; it exists as the typed reference implementation and for tests." That is a second parser of the same YAML in a second language, which is precisely the plan's own "two parsers could drift" risk row, shipped in service of a hypothetical future consumer. The routing precedent it mirrors had two *real* consumers from day one; this has one (the renderer). Deferring the mcp-server loader until a real MCP-side consumer exists would delete a risk row and a test suite while losing nothing — the AC-2 exact-inventory regression can live in `render.test.js`. The plan's counter-rationale is recorded in its decisions section, so this is a disagreement with a visible decision, not a buried one — advisory, not a GAP.

**Verdict on the ceremony test: defensible under the epic's portable-enforcement thesis; heavier than the status quo only if that thesis is abandoned — which is an epic-level call already made (this feature was commissioned by #1588 and the full-scope/Shape-A decisions are marked human-directed).**

## Gaps

- **[Plan-of-plans alignment — GAP] Epic sequencing is contradicted and never addressed.** The issue body's own Context says: "Last in the epic — depends on the reduced skill surface (fewer pin sites) and server-side invariant layer (config plumbing) landing first." Siblings #1590 (skill surface 47 modes → ~20), #1591, and #1592 are all still OPEN. This plan sweeps a ~35-site manifest across the *current* skill surface — the surface #1590 is chartered to shrink and restructure. Building now means (a) enumerating sites #1590 will delete or move, and (b) every #1590/#1591 PR thereafter pays the manifest-update tax through `check-model-tiers.sh`. That second effect is arguably a feature (the checker shepherds tier coherence through the restructure — and the `sites:` schema keys on path/kind/tier, not line numbers, so churn is path-rename-sized), but the plan nowhere acknowledges that it is building out of the epic's declared order or weighs the rework cost. **Fix**: add a Migration Note (or resolved decision bullet) explicitly making the build-now call: either "accepted — the drift check is wanted *during* the #1590 sweep and manifest churn is bounded to path renames" or re-sequence behind #1590. This is a note-and-proceed gap, not a redesign.

## Recommended Changes

1. **(Addresses the GAP)** Add the sequencing decision to `## Migration Notes` or the decisions section: state that #1590-#1592 are open, that the epic body ordered this feature last, and why building now is accepted (manifest keys are line-number-free; the drift check governs the #1590 sweep rather than fighting it). One paragraph.
2. **Specify the sweep pattern.** `hero/dispatch.md:38` — `impl_model="${RALPH_IMPL_MODEL:-sonnet}"` — matches a naive `model="` grep. The plan's YAML comment asserts these are "excluded from the sweep by pattern" but never states the pattern. Specify boundary-aware matching (e.g. `\bmodel="` — no word boundary between `_` and `m`, so `impl_model="` is correctly excluded) and add the `dispatch.md:38` false-positive as an explicit renderer test case. Without this, the completeness sweep either false-flags dispatch.md or is silently looser than specified.
3. **(Advisory ceremony trim)** Reconsider shipping the consumer-less mcp-server loader in Phase 1, or mark it explicitly as deliberate dead weight pending an MCP-side consumer; moving the AC-2 regression into `render.test.js` removes the plan's own "two parsers of one YAML" risk instead of mitigating it.
4. **(Advisory)** Phase 3's `claude-code-opus` satisfies AC-3's substance (the map, not the prose, decides models) but is weaker than the AC's own examples (model-gate registry / droid-opencode profile) — it is the same harness with a different entitlement. The plan is honest about this in What We're NOT Doing; consider echoing one line into the eventual PR body so the AC-3 checkbox isn't ticked without that caveat visible to the epic close-out validation.
