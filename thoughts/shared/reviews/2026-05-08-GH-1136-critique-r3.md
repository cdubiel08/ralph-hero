### R2 #1 (CRITICAL) — In-Review re-pick loop — PASS

The new **Step 2.5: Skip "human-gated" candidates** at lines 186-200 of the plan correctly addresses the regression. Trace through the failure scenario the R2 critique described:

1. Tick 1 fires; `next_actions` returns issue X (`Ready for Plan`); Step 2.5 rules pass-through; hero dispatched; PR landed; post-state = `In Review`; outcome = `pr_landed`; `history.push({issue: X, outcome: "pr_landed"})`; Step 9 schedules next at 60s.
2. Tick 2 fires 60s later; state decoded carrying `history: [{issue: X, outcome: "pr_landed"}]`; `next_actions(limit=10)` returns X (still in `ACTIONABLE_PHASES` per `directions.ts:180-185`); Step 2.5 rule 1 filters `workflowState !== "In Review"` → X removed; rule 2 filters `!history.some(h => h.issue === c.issue && h.outcome === "pr_landed")` → also removed (defense in depth); no candidates remain → STOP with `outcome=backlog_empty`.
3. No `no_progress` recorded. No `no_progress_streak` increment. No escalation. The in-review issue is mentioned in the final report as "awaiting human merge."

The two filter rules are complementary, not redundant: rule 1 catches the steady-state case (`In Review` is human-gated regardless of provenance); rule 2 covers the "previously-PR'd this loop" edge case where a board state somehow regresses (e.g., a moderator manually moved an issue back to actionable; rule 1 alone would re-pick it on the next tick). Order doesn't matter functionally — both are AND-filters and idempotent.

**Eval scenarios 12 + 13** at lines 530-531 explicitly cover both the single-issue and multi-issue mix paths. Scenario 12's acceptance copy is precise: "the issue does NOT get re-dispatched to hero, does NOT accumulate a no-progress streak, and does NOT get falsely escalated to Human Needed."

The `--auto-merge` interaction is correctly deferred — the MVP keeps the In-Review filter on regardless of `--auto-merge`, with a follow-up bullet at line 624 capturing the principled relaxation. This is the right scope discipline.

### R2 #3 — Outcome table catch-all — PASS

Catch-all row added at line 274: `any | different from pre, not matched by rows above (catch-all) | other_change | yes (treat as advanced for streak-reset)`. Step 7 streak-reset set at line 311 includes `other_change`. Step 9 delay-bucket logic at line 344 includes `other_change` in the 60s bucket. The forensic note at line 276 correctly justifies the choice: unexpected transitions are recorded as `other_change` in the audit log for review without silently dropping into `no_progress`.

**Risk consideration:** treating `other_change` as progress could mask a genuine "stuck" condition where hero somehow induces a backward transition every tick. This would prevent the `no_progress_streak` from ever reaching 3. Mitigations:
- The `iteration > MAX_ITERATIONS` ceiling (default 20) bounds runaway behavior.
- The audit log records `other_change` distinctly, so post-hoc analysis surfaces it.
- The state machine is designed monotonic; backward transitions in practice should be rare and human-driven (manual reset).

This is acceptable for MVP. If `other_change` proves to be a problem in production, a follow-up could add a separate `other_change_streak` counter. Not blocking.

### R2 #4 — `next_delay_seconds: null` for STOP — PASS

The rule is documented at line 426: *"Whenever `next_action == 'stop'`, `next_delay_seconds` MUST be `null` (not 0, not absent)."* All four STOP cases are enumerated at lines 421-424:
- `escalated` → `next_delay_seconds=null`
- `dry_run` → `next_delay_seconds=null`
- `backlog_empty` → `next_delay_seconds=null`
- `no_progress_streak` / `max-iterations` (catch-all "etc.") → `next_delay_seconds=null`

**Tooling implication check:** the `jq` selector at line 382 (`jq -r '.next_delay_seconds' ~/.ralph-hero/autopilot.jsonl | sort -u`) — when fed JSON `null`, `jq -r` outputs the string `"null"`. So the expected output set is the strings `{"60", "1200", "null"}`. The success criterion's wording at line 382 only confirms 300 is never present, not that nulls are present, so this is fine. Verified plan body at line 426 explicitly states `{60, 1200, null}` is the expected set — consistent.

If `next_delay_seconds` were absent (vs. null), `jq -r '.next_delay_seconds'` would output `"null"` anyway (jq's behavior for missing keys), so downstream parsers don't break either way. The plan's choice to make it explicitly `null` is the more principled option (forensic consumers can distinguish "we considered this and decided not to schedule" from "field was forgotten"). No regression.
