# Plan Critique: GH-1160 — Cross-tool Count Consistency Tests

## Summary

**Verdict**: APPROVED

The plan is well-scoped, technically accurate, and dispatchable. It is a single-phase, single-file plan that builds directly on a verified parent plan-of-plans (GH-1153) and an explicit research audit. The mock-harness pattern it replicates is real and current; the tools/files referenced exist; and the per-task acceptance criteria map 1:1 to the cross-tool invariants captured in the GitHub issue.

## Dimension-by-Dimension Assessment

### 1. Completeness — PASS

All seven tasks (1.1 through 1.7) are defined with explicit `files`, `tdd`, `complexity`, `depends_on`, and `acceptance` checkbox lists. Every task names exactly one create/modify target. The plan's "Current State Analysis" enumerates the prior-phase landings being relied on (Phases 1, 2, 3, 4) and explicitly calls out that Phase 6 has NOT landed — preventing a class of false-failure where the test would assert deprecated tools are absent.

### 2. Feasibility — PASS

Verified against HEAD:

- `plugin/ralph-hero/mcp-server/src/__tests__/directions-tools.test.ts` exists and contains the exact harness pattern the plan replicates (`rawIssue()` at L48-103, `itemsResponse()` at L106-116, `fieldCacheResponse()` at L124-170, query predicates at L173-183, `createMockClient()` at L208-268, `getTool()`/`parsePayload()` at L283-307).
- All four tool registration functions exist:
  - `registerDirectionsTools` at `directions-tools.ts:468` (plan says 474; off-by-6 but the function exists at the named location).
  - `registerDashboardTools` at `dashboard-tools.ts:46` (matches).
  - `registerIssueTools` at `issue-tools.ts:53` (plan says 54; off-by-1).
  - `registerHygieneTools` at `hygiene-tools.ts:36` (matches).
- The `boardItems` contract holds across all three tools that should expose it: `dashboard.ts:154,818,848`, `hygiene.ts:83,446,482`, `directions-tools.ts:455`. `list_issues` correctly does NOT expose `boardItems` (it exposes `filteredCount` at `issue-tools.ts:495`) — the plan correctly documents this asymmetry in Task 1.3.
- The Backlog/null fallback for `audience="agent"` lives at `directions.ts:846-867` exactly as cited.
- `aggregateByPhase` falls back to `"Unknown"` when `workflowState` is null at `dashboard.ts:256` — confirms the Task 1.7 invariant.
- `findStaleItems` does not exclude null-state items (only excludes `TERMINAL_STATES`) at `hygiene.ts:152-154` — confirms the Task 1.7 invariant on `staleItems`.
- Both the parent plan and the audit research document exist on disk.

The line-number drift is cosmetic (the file moved slightly between plan-write time and HEAD); it does not affect feasibility.

### 3. Clarity — PASS

Each task ends with a concrete verifiable checkbox. Where the plan asserts `it(...)` block names, the names are quoted verbatim (e.g., `"all four tools report boardItems = 12 against the same fixture"`), so the implementer doesn't have to invent test names. Phase Success Criteria correctly splits Automated (`npm test`, `npm run build`) from Manual (read names aloud, confirm fixture comment header, guard against mock leakage).

### 4. Scope — PASS

"What We're NOT Doing" section is explicit and well-bounded. Five exclusions are listed:
1. No Phase 6 contract assertions (deprecated tool removal).
2. No `metrics_trends` / `capture_snapshot` / `recent_activity` testing.
3. No shared `cross-tool-fixtures.ts` module — fixture is inline.
4. No score-magnitude correctness assertions.
5. No live-project CI integration.

Each exclusion has a one-line rationale. The "fixture inline, extract on third consumer" rule is exactly the right shape for this kind of test.

Task field discipline is uniform across all 7 tasks:

A subagent dispatched to any single task has enough information to complete it without reading the full plan: each task names the file, the operation (create/modify), the exact `it(...)` name, and the exact assertions to write.

## Notes for Implementer

These are observations, not blockers:

1. **Line-number drift**: the plan cites `directions-tools.ts:474` but the function is at `:468` at HEAD. Don't trust the line numbers; the function names are stable.
2. **Fixture comment header**: Manual Verification step 2 asks for "the fixture comment header references the audit document by relative path". Spell that out as `// Fixture rows from thoughts/shared/research/2026-05-08-shorthand-tools-counts-and-filters.md` so the manual check is mechanical.
3. **`list_issues` total count**: Task 1.3 asserts `listIssues.filteredCount <= 12`. Because the test passes default args (no filters), `filteredCount` should equal 12 exactly — consider strengthening to `=== 12` for tighter regression coverage. (Optional; the loose bound is correct as a contract assertion.)
4. **Open-PR mock leakage guard**: Manual Verification step 3 mentions guarding against the open-PR fetch leaking. The existing `directions-tools.test.ts:248-251` pattern (`isOpenPRsSearchQuery` returning empty `search.nodes`) is correct; if the mock falls through to `throw new Error(...)`, the test will fail loudly. That implicit guard is sufficient.

## Verdict

APPROVED. The plan is ready for implementation. The implementer can dispatch each task to a subagent with the task body alone.
