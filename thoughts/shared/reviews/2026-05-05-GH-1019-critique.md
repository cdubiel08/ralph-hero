# Plan Critique: GH-1019 Track product performance over time

## Verdict

**NEEDS_ITERATION** — The plan is well-scoped, well-bounded, and technically sound on the data model and module boundaries. It fails the **Dispatchability** dimension: phases are described in prose with code sketches but lack the structured per-task fields (`files`, `tdd`, `complexity`, `depends_on`, `acceptance`) required for autonomous subagent dispatch. There is also one minor **Feasibility** inaccuracy (a referenced helper does not exist as named).

## Dimensions

### 1. Completeness — PASS

All five phases are present with concrete file paths, change descriptions, and module boundaries. Snapshot type is fully specified, cycle-time rollup output is typed, trend series shape is typed. Phases 1-3 (MCP core), Phase 4 (skill + scheduler), Phase 5 (docs + CI) cover the full surface area declared in the issue Scope. Testing strategy enumerates unit + integration test files. Migration notes address schema evolution (`schemaVersion` bump).

### 2. Feasibility — FAIL (minor)

Most file references are accurate and verified to exist:
- `plugin/ralph-hero/mcp-server/src/lib/dashboard.ts` — exists; `buildDashboard` at line 706.
- `plugin/ralph-hero/mcp-server/src/lib/metrics.ts` — exists; `calculateMetrics` at line 147 (matches plan).
- `plugin/ralph-hero/mcp-server/src/lib/transition-comments.ts` — exists; `parseAllTransitions` at line 121.
- `scripts/dream/launchd/com.dubiel.dream-loop.plist.template` — exists (precedent valid).

**Issue**: Phase 1 code sketch calls `fetchDashboardItems(client, projectNumber)` as if it were an existing reusable helper. It does not exist — `dashboard-tools.ts` performs the items fetch inline (`buildDashboard(allItems, healthConfig, ...)` at `dashboard-tools.ts:464`). The plan should either (a) extract a shared `fetchDashboardItems` helper as an explicit task in Phase 1, or (b) inline the fetch logic in `trends-tools.ts`. As written, an impl agent could waste time looking for a non-existent symbol.

Convention adherence is good: `~/.ralph-hero/snapshots/` matches the dream-loop convention; `registerXyzTools` registration pattern matches `index.ts` precedent; haiku-tier skill matches the cost guidance for read-only output skills.

### 3. Clarity — PASS

Each phase has explicit `#### Automated Verification` and `#### Manual Verification` checkbox lists in the canonical `- [ ] Automated:` / `- [ ] Manual:` shape. Success criteria are testable (e.g., "Calling `ralph_hero__capture_snapshot` against a fixture client appends exactly one line"). End-state verification at the top of "Desired End State" is concrete.

### 4. Scope — PASS

"What We're NOT Doing" is one of the strongest sections in the plan: explicitly excludes SQLite/DuckDB, web UI, Grafana, backfill beyond `parseAllTransitions()`, Langfuse/OTel, signature changes to existing dashboard/metrics, and retention/compaction. Issue body's "Out of Scope" matches plan's exclusions. No scope creep risk.

### 5. Dispatchability — FAIL

This is the primary blocker. Phases describe work in prose + code sketches but **do not break the work into dispatchable tasks** with the required field structure:

| Field        | Required | Present in plan? |
|--------------|----------|------------------|
| `files`      | yes      | partial — listed in prose under "Changes Required" but not normalized with (create/modify/read) labels per file |
| `tdd`        | yes      | absent — phases imply test-first via Success Criteria but no explicit `tdd: true/false` per task |
| `complexity` | yes      | absent |
| `depends_on` | yes      | implicit (phase ordering only); no per-task ID dependency graph |
| `acceptance` | yes      | present at phase level (Success Criteria) but not per-task |

For a 5-phase plan with multiple sub-tasks per phase (e.g., Phase 4 has 4 distinct sub-tasks: skill, plist template, runner script, report-skill update), an impl agent receiving Phase 4 in isolation cannot reliably dispatch parallel subagents because there is no per-task acceptance gate or complexity hint. Phase 1 also bundles three sub-tasks (persistence module, MCP tool, registration wiring) under one Success Criteria block.

Estimate sizing also flags here: the issue is M-sized (5 phases). Per the workflow constraint, M issues are typically split into XS/S sub-issues before implementation — this plan reads like a feature plan that should be decomposed into 5 atomic sub-issues (one per phase) rather than implemented as a single ticket. Consider running `/ralph-hero:ralph-split` to break #1019 into per-phase children.

## Recommended Iteration

1. **Add a per-task table to each phase** with the dispatchability fields. Minimum viable shape — a markdown table per phase listing each file change as a row with `files | tdd | complexity | depends_on | acceptance` columns. Phases 1, 2, 3 have ~3 tasks each; Phase 4 has 4 tasks; Phase 5 has 3 tasks. Total ~16 tasks.

2. **Resolve the `fetchDashboardItems` reference** in Phase 1. Either:
   - Add an explicit task: "Extract `fetchDashboardItems(client, projectNumber)` from `dashboard-tools.ts:~440` into a shared helper in `lib/dashboard-fetch.ts`", OR
   - Rewrite the Phase 1 code sketch to inline the fetch.

3. **Consider splitting**: M-sized issue with 5 self-contained phases is a strong split candidate. Each phase is independently shippable (Phase 1 alone delivers value; Phase 2 enriches; Phase 3 surfaces; Phase 4 schedules; Phase 5 documents). Recommend `/ralph-hero:ralph-split 1019` to create 5 XS/S children before implementation begins.
