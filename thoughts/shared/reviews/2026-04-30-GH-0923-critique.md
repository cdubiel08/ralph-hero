## Scope — PASS

The "What We're NOT Doing" section explicitly lists:
1. Flipping the `rerank` default to `true` (deferred to follow-up PR after Phase 4).
2. RRF weight tuning / learn-to-rank (separate tickets #899, #900).
3. Changing the embedding model (`Xenova/all-MiniLM-L6-v2` stays).
4. MLX/HTTP reranker endpoint (in-process ONNX only).
5. Qwen3-Reranker support.
6. Refactoring the benchmark to import the new module (only "if trivial").
7. Score caching across calls.
8. `RALPH_RERANKER_MODEL` env var.

This is unusually disciplined — each exclusion has a one-line justification and several reference the follow-up PR boundary. No ambiguous "future work" hand-waves.

Phase 1 also explicitly lists the bench refactor as "optional" with the abandonment criterion ("if not trivial, skip"), preventing scope drift inside the phase itself.

## Minor observations (non-blocking)

These would be nice-to-have polish but do not affect approval:

1. **tsconfig citation drift**: plan cites `tsconfig.json:3-4` for `module: NodeNext`; actual lines are 4-5. Trivial.
2. **Phase 1 Task 1.4 already covers loader-injection invariants**: Task 1.3 calls out the loader injection and Task 1.4 retests it ("loader invoked exactly once"). Mild duplication; harmless.
3. **Phase 4 Task 4.2 acceptance checkbox "Frontmatter mirrors the baseline doc"**: the implementer should literally re-use the baseline doc's frontmatter as a template — calling that out as an explicit instruction would save a few seconds. Not blocking.
4. **No mention of `rerankScore` JSDoc range**: the plan documents `rerankScore` as "raw cross-encoder logit; higher = more relevant" but doesn't pin the expected range (sigmoid-head logits typically span ~[-12, +12] for BGE). Phase 4 will surface real values; documenting an expected range in Phase 2 Task 2.1 JSDoc would help downstream consumers calibrate. Optional follow-up.

None of these warrant iteration. Approving as-is.
