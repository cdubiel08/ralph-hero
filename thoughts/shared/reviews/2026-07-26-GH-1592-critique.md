## Failures

**[Risk coverage — FAIL] The regression inventory is not exhaustive, and its method is what makes it non-exhaustive.** The table enumerates each caller's *happy-path* FROM state rather than its *reachable* FROM set. Four callers fall through that gap, and none is covered by an existing row's mitigation:

1. **`plan --mode epic` Step 1 breaks on a Backlog epic — with a live counterexample on this board.** `plan/SKILL.md:171` is `save_issue(workflowState: "__LOCK__", command: "plan")` on the epic, which resolves to `Plan in Progress`. Epic #1588 is at `workflowState: "Backlog"` *right now*. Post-Phase-1, `Backlog → Plan in Progress` ∉ {Research Needed, Ready for Plan, Done, Canceled, Human Needed} → refused. `intake-routing.md:114` states no state precondition for `--mode epic`, so the direct interactive entry (a human running `/ralph:plan --mode epic 1588`) is a live, currently-working flow that stops working. The autopilot path is unaffected (hero routes PLAN only from Ready for Plan, `dispatch.md:12`), which is exactly why a happy-path-only inventory missed it. Inventory row 13 covers only `Ready for Plan → Plan in Progress`. **Do not fix this by adding a `Backlog → Plan in Progress` edge** — that re-opens the gate-skip the table exists to close. Fix in prose (route Backlog epics through Ready for Plan first, mirroring row 1's hero-fable two-step) plus an inventory row plus a `plan/SKILL.md --mode epic` edit in Phase 5.

2. **`merge-gate.md:161-168` — the sanctioned epic-gaps parent touch — is an autonomous `Done → Human Needed` write, and row 15's mitigation is wrong for it.** The call is `save_issue(number=<parent>, workflowState="Human Needed", command="ralph_merge")`, applied to a parent that `advance-parent.yml` may already have driven to Done, with a documented re-assert loop that adds `issueState: "OPEN"`. Command-level passes (`ralph_merge` allows Human Needed); transition-level refuses (Done has no outbound edges). Row 15 labels this class "Reopen repair" and mitigates it with "this is the intended behavior" — but here the intended behavior is precisely the outcome merge-gate exists to prevent ("so the epic does not silently stand as Done with unmet intent"). The merge-agent has no instruction to pass `force`, and Phase 5's Changes Required file list does not name `merge-gate.md` (the `grep -rn 'issueState: "OPEN"' ralph/` sweep appears only in Migration Notes prose).

3. **Refusal placement produces split-brain partial mutations, and finding 2 is the live instance.** `save_issue` mutates the GitHub issue *first* — close/reopen/metadata at `issue-tools.ts:1452-1584` — and only reaches the project-field block (where the plan places the transition check, "before the mutation batch") at `:1585+`. So `save_issue(number=P, issueState: "OPEN", workflowState: "Human Needed")` on a Done epic reopens the issue on GitHub, *then* returns `toolError`, leaving the issue OPEN with the board reading Done. Same shape for any `title`/`body`/`labels` + illegal-state call. Relatedly, Phase 1 §4's exemption claim — "when `resolvedWorkflowState` came from the reverse-inference / auto-close path, the universal terminal edges make it legal by construction" — **is false for terminal current states**: universal edges run *from non-terminal states*, so re-closing a Done issue as `CLOSED_NOT_PLANNED` (reverse-inferring Canceled) closes it with the new reason and *then* refuses. The transition check must run before the issue-mutation block at `:1452`, not before the field block at `:1585`, and the reverse-inference exemption needs an explicit terminal-source carve-out rather than a "by construction" claim.

4. **`caretake --mode split` §Step 10 demotes REUSED children through `batch_update`, and `batch_update` has no `force`.** `split.md:174-191` sets REUSED (pre-existing, arbitrary-state) children to `Ready for Plan` / `Research Needed` / `Backlog`. Post-Phase-1, `Ready for Plan → Research Needed` and `Ready for Plan → Backlog` are both illegal, on top of the `In Progress → Ready for Plan` case row 8 does acknowledge. Row 8's mitigation ("agent escalates or repairs via `save_issue(force)`") is not written into `split.md` anywhere, and Phase 4's split.md edits cover only the `create_sub_issues` line. Either add the demotion edges with named consumers, or add the per-issue `save_issue(force: true)` recovery instruction to `split.md` §Step 10 in Phase 5.

**[Risk coverage — FAIL, second head] Two server-side Workflow State writers stay unvalidated, and the plan's stated reason for exempting one of them is factually false.**

Desired End State 1 says "Every workflow-state mutation through the MCP server … is validated," then scopes itself to three tools. There are five writers. The two omitted ones both write *parent* state:

- `autoAdvanceParent` (`helpers.ts:832`, via `updateProjectItemField`) — called from `save_issue:1743-1763` and from `create_sub_issues` (`tree-tools.ts:715-728`). The plan never mentions it.
- `advance_issue direction='parent'` (`relationship-tools.ts:1000-1005`) — the plan exempts it: "it advances via `PARENT_GATE_STATES` logic, which is itself a legality proof, and the added edges keep its writes legal."

That rationale does not survive reading the code. Both paths guard only with `stateIndex(parent) >= stateIndex(gate) → skip` (`helpers.ts:825-827`, `relationship-tools.ts:973-975`). `stateIndex` returns `-1` for `Human Needed`, `Canceled`, and unknown/unset. So both paths will happily write:

- `Backlog → In Review` (parent at Backlog, all children hit In Review) — a four-gate skip, illegal everywhere else post-Phase-1;
- `Research Needed → Plan in Review`;
- `Human Needed → Plan in Review` / `Human Needed → In Review` (index −1 always advances) — illegal, and it silently overwrites an escalation;
- writes *over a live lock*: a parent at `Plan in Progress` gets set to `In Review` with no lock-guard consultation.

The result is a server that refuses through `save_issue` exactly what it performs silently one function call later in the *same* `save_issue` invocation. That is the drift class this epic exists to remove, and it makes the #1619 zero-hook evidence claim ("a zero-hook hero-fable transcript proves each invariant server-side") overstated. Fix: either validate both parent writers against the same predicate (with a documented parent-gate carve-out list if gate jumps must stay legal), or state the exemption honestly in What We're NOT Doing with the real reason — not the "legality proof" claim, which is wrong.
