# GH-1322 Plan Critique

## Summary

Verdict: **APPROVED**.

The plan addresses a real, observed failure (PR #1315, 2026-05-19) where
`/ralph-hero:finish` collapsed a three-level nested conditional after the
inline `code-review:code-review` skill flooded its context with ~55K tokens
of reviewer chatter, and skipped the `Found ` self-authorship fix branch.
The proposed fix — extract the gate into a deterministic Bash helper that
emits one of four tokens (`APPROVED` / `NEEDS_FIX` / `BLOCKED` / `ERROR:`)
and replace the buried sub-bullet with a four-arm `case` — is the minimum
viable architectural change. Scope is properly bounded: it does not attempt
the larger `finish-review`/`finish-merge` split, does not modify the
vendored `code-review:code-review` plugin, and does not touch the
forked-context `ralph-code-review` path.

Phases are sequential, each independently verifiable, and each terminates
in a stable contract the next phase depends on. The Phase 3 test plan
mirrors an existing, working pattern (`merge-state-gate.test.sh`) and lands
in CI automatically via the existing `find ... -name '*.test.sh'`
auto-discovery loop in `.github/workflows/ci.yml`.

## Dimension Scoring

### Completeness — PASS

Every phase has an Overview, a "Changes Required" section with concrete file
paths and behavior, a runnable Bash sketch (Phase 1 includes the full
helper; Phase 3 includes the test-shim skeleton), and explicit success
criteria. The plan also includes Testing Strategy, Performance
Considerations, Migration Notes, and References sections — all populated
with relevant content, not boilerplate.

The only minor gap: Phase 2 shows the rewritten Step 4 body as a "sketch"
and defers final wording to implementation. This is acceptable because the
verdict tokens and case-arm semantics are fully specified; only prose
polish remains.

### Feasibility — PASS

Verified against the live tree on 2026-05-19:

- `plugin/ralph-hero/hooks/scripts/__tests__/merge-state-gate.test.sh`
  exists and matches the claimed structure (PASS counter, `assert_eq`
  helper, `mktemp -d` fixtures, `trap` cleanup).
- `plugin/ralph-hero/skills/finish/SKILL.md` lines 109-162 match the plan's
  description exactly — Step 4 begins at line 109, the depth-0 fan-out
  rationale is at lines 111-113, and the buried self-authorship fallback
  with `PR_AUTHOR == CURRENT_USER` checks is at lines 152-162.
- `.github/workflows/ci.yml` confirms the auto-discovery pattern: lines
  135-143 use `find plugin/ralph-hero/hooks/scripts/__tests__ \( -name
  '*.test.sh' -o -name 'test-*.sh' \) -type f -print0 | sort -z | xargs -0
  -n1 bash -c ...`. New test file will be picked up with no workflow edit.
- `plugin/ralph-hero/hooks/scripts/finish-review-verdict.sh` correctly does
  NOT exist yet (the plan creates it).
- The vendored code-review comment format relied on (`### Code review`
  prefix + `Found N issue(s):` / `No issues found.` body) is mentioned as
  stable; the plan's literal-string match strategy matches the current
  `finish/SKILL.md:155-162` logic verbatim, so behavior parity is preserved.

The proposed Bash uses `set -uo pipefail` (no `-e`) which is the right
choice for a script that wants to inspect command exit codes and emit
ERROR tokens rather than crash on a failed `gh` call.

### Clarity — PASS

Every phase uses the canonical checkbox format:

- `#### Automated Verification:` followed by `- [ ]` items that are runnable
  commands (e.g., `grep -c 'finish-review-verdict.sh' ... returns >= 3`).
- `#### Manual Verification:` followed by `- [ ]` items that a human can
  visually confirm (e.g., `chmod +x` set, no stderr leakage).

Phase 1's automated checks include the regression smoke test
(`bash ... 1315` should print `NEEDS_FIX`) which directly maps to the
failing case that motivated this plan — excellent.

Phase 2's automated checks use `grep -c` against `SKILL.md` to verify both
the presence of the new helper call (>= 3 sites) AND the absence of the
old buried-bullet logic (`grep -c 'startswith("### Code review")'` == 0,
`grep -c 'LAST_COMMENT'` == 0). This is a precise, mechanically-checkable
contract.

### Scope — PASS

The "What We're NOT Doing" section has five explicit, well-bounded
exclusions:

1. Not splitting `finish` into `finish-review` + `finish-merge` (correctly
   identified as a larger refactor — Option 3 from diagnosis).
2. Not adding hidden marker comments to the vendored code-review plugin.
3. Not changing `code-review:code-review` fan-out behavior or its depth-0
   invocation pattern.
4. Not touching `ralph-code-review` / `code-review-agent` (forked-context
   path).
5. Not increasing the fix-cycle cap beyond the existing max-1 in `finish`.

Each exclusion has a one-line rationale. None of these are accidental
gotchas waiting to bite later — they're conscious deferrals.

### Dispatchability — PASS (with caveat)

The three phases are atomic and self-contained:

- **Phase 1** (helper creation): single new file, no dependencies on other
  phases, fully verifiable by running the script.
- **Phase 2** (SKILL.md wiring): depends on Phase 1's contract (the four
  verdict tokens) but does not need to re-read Phase 1's implementation —
  the token grammar is the only contract.
- **Phase 3** (unit tests): pins Phase 1's contract; can be implemented in
  parallel with Phase 2 in principle, though the plan correctly notes
  "sequential order is required because Phase 2 imports Phase 1's contract,
  and Phase 3 pins that contract against regressions."

**Caveat**: The dispatchability table from `quality-standards.md` (fields:
files / tdd / complexity / depends_on / acceptance) is not rendered as a
literal table in the plan. Phase information is present in prose form (file
paths in "Changes Required", `tdd` implicit from "Manual Testing Steps",
complexity implicit from XS estimate, dependencies stated in Implementation
Approach, acceptance criteria in Success Criteria sections). This is the
ralph-hero house style for plans of this size and is acceptable here, but
note that a stricter dispatchability gate would flag this as a minor
deviation from the canonical schema.

For multi-issue group plans:
- Phase dependencies are explicit (Phase 1 -> Phase 2 -> Phase 3,
  rationale stated).
- Integration testing section ("Testing Strategy") covers replay against
  PR #1315 after all three phases land — this is the cross-phase
  integration check.

## Recommendation

Approve and proceed to implementation. The three sub-issues (GH-1323,
GH-1324, GH-1325) can be dispatched sequentially via the standard
`ralph-impl` flow. No iteration required.
