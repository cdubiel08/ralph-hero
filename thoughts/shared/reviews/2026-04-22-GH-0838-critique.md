# Plan Critique — GH-838: Refine ralph-hero:hello output budget

## Verdict

APPROVED (with one cosmetic nit on a verification grep; non-blocking).

## What the plan proposes

Four surgical edits to one file, `plugin/ralph-hero/skills/hello/SKILL.md`:

1. Step 1: change the `pipeline_dashboard` call from `includeMetrics: true` (no `issuesPerPhase`) to `includeMetrics: false, issuesPerPhase: 3`.
2. Step 2: insert a hard "Output budget" block forbidding raw tool-output echo, markdown tables, JSON blocks.
3. Step 5: rewrite the close-out block to forbid relaying dispatched `Agent()` return strings and require a ≤1-sentence dispatch summary.
4. Constraints section: append two bullets codifying rules 2 and 3.

All edits include exact old/new text. No TypeScript. No new tests.

## Assessment against quality dimensions

### Completeness
Strong. Each edit cites line numbers in the current file, quotes the exact current text, and gives the exact replacement. A careful implementer can apply all four with literal copy-paste. The "What we're NOT doing" section is explicit about five tempting extensions (removing Step 5 routing, changing dispatch mapping, altering tool defaults, introducing a shared fragment, adding a Stop hook) and rejects each with a reason.

### Feasibility
Verified:
- `pipeline_dashboard` accepts `issuesPerPhase` (default 10) and `includeMetrics` (default false). Both params are declared in `plugin/ralph-hero/mcp-server/src/tools/dashboard-tools.ts:319-330`. The plan's parameter additions are type-correct and defaults-aware — dropping `includeMetrics: true` is restoring the tool's own default, not a new override.
- The target file exists at the specified path and at the specified line numbers. I confirmed line 35 contains the current `pipeline_dashboard` call and lines 128-132 contain the `Session complete.` block quoted in the plan.
- The skill uses `context: inline` (confirmed at line 14 of SKILL.md), so every prose edit lands directly in the orchestrator prompt. The plan's core premise — that tightening prose here IS the fix — is correct.

### Clarity
Success criteria are concrete. Automated checks are greps for stable literal substrings ("Output budget (hard limit)", "Do not relay the dispatched agent", "Hard output budget", "summarize in ≤1 sentence"). Manual checks specify the line budget (≤~40 briefing, ≤3 post-dispatch) that will be behaviorally verified.

### Scope
Correctly single-phase and XS. Splitting this into multiple phases would be over-engineering: the four edits are tightly coupled (they all implement the same "no echo, hard budget" discipline), they touch one file, and there is no dependency ordering between them. Landing them in one PR is the right call. The plan's own implementation note says as much.

### Boundaries
The "What we're NOT doing" list is well-drawn. Notably, the plan avoids:
- Changing tool defaults (keeps the skill's call site as the only lever).
- Adding a Stop hook (correct — would be over-engineered and brittle).
- Removing Step 5 routing (orthogonal to the verbosity fix).
- Changing `context: inline` (required for the AskUserQuestion picker).

No scope creep risk evident.

## Issues found

### Minor (non-blocking): malformed grep sentinel

`success-criteria.automated[2]` in the plan (markdown line 155) reads:
```
grep -q "includeMetrics\`: false" plugin/ralph-hero/skills/hello/SKILL.md
```

The embedded `` \` `` is a shell-escaped backtick. The new text inserted by the plan is `includeMetrics: false` with no backtick — the escape is a leftover from backtick-quoting the identifier in prose. This grep will not match. Impact: the implementer will either notice and delete the `` \` ``, or will see a false-negative and fix it in seconds. The intended substring `includeMetrics: false` is correct and unambiguous.

Suggested correction:
```
grep -q "includeMetrics: false" plugin/ralph-hero/skills/hello/SKILL.md
```

This is a 1-character fix and does not require re-planning. Calling it out for the impl agent to patch on sight.

### Observations (not issues)

- The plan chose `≤~40 lines` and `≤3 lines` as soft budgets using "~" and the Unicode `≤`. This is fine for prose consumed by an LLM; it is not fine for an automated regex. Since the plan explicitly defers automated length enforcement ("Not adding automated output-length enforcement"), and the verification is behavioral, this is consistent.
- The manual verification step 9 ("temporarily rename `MEMORY.md` to confirm the memory-empty path still works") is a thoughtful regression check that catches the pre-existing rule from GH-480.
