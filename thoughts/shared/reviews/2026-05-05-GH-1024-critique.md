# GH-1024 Plan Critique - Trends query tool (metrics_trends + sparklines)

## Verdict: APPROVED

The plan is dispatchable, internally consistent, and well-bounded. Three tasks
each carry the required dispatchability fields (files, tdd, complexity,
depends_on, acceptance) with concrete, verifiable acceptance criteria.

## Dimension Assessment

### 1. Completeness — PASS
All three tasks define specific file paths with create/modify/read intent and
concrete acceptance lists. Phase Success Criteria splits Automated vs Manual
verification cleanly. Integration Testing section addresses cross-phase
interactions with siblings #1022/#1023.

### 2. Feasibility — PASS
All referenced files exist on disk:
- `plugin/ralph-hero/mcp-server/src/lib/date-math.ts` (exports `parseDateMath` at L17)
- `plugin/ralph-hero/mcp-server/src/lib/metrics.ts`
- `plugin/ralph-hero/mcp-server/src/types.ts` (exports `toolSuccess`/`toolError` at L266/L272)
- `plugin/ralph-hero/mcp-server/src/tools/activity-tools.ts` (registration pattern reference)

Plan correctly notes that `lib/snapshots.ts` and `tools/trends-tools.ts` are
created by Phase 1 (#1022) — Phase 3 consumes, does not create. The bucketing
formula `floor((v - min) / (max - min) * 7.999)` correctly maps to 0..7
inclusive. The `wipTotal` derivation is sound. The 24h/168h/720h delta windows
match the metric labels.

### 3. Clarity — PASS
Acceptance criteria are concrete and testable:
- Sparkline alphabet pinned to exact codepoints `▁▂▃▄▅▆▇█` (U+2581..U+2588).
- Specific test fixtures called out (`[1,2,3,4,5,6,7,8] -> "▁▂▃▄▅▆▇█"`).
- Null handling specified (`" "` placeholder, `n/a` in markdown).
- Default `since` window specified (30 days) and override mechanism (`parseDateMath`) named.
- ENOENT explicitly handled as "no snapshots yet", not surfaced as tool error.

### 4. Scope — PASS
"What We're NOT Doing" section is explicit and well-bounded: no `lib/snapshots.ts`
edits, no skill/scheduler (Phase 4), no docs (Phase 5), no extra metrics, no
24-bucket/color sparklines, no CLI. Estimate is "S" — appropriate for a single
pure module + one tool registration + tests.

### 5. Dispatchability — PASS
Each task is self-contained:

| Task | files | tdd | complexity | depends_on | acceptance |
|------|-------|-----|------------|------------|------------|
| 1.1 computeTrends | yes | true | medium | null | yes (6 tests) |
| 1.2 renderSparkline | yes | true | low | [1.1] | yes (8 cases) |
| 1.3 register tool | yes | true | medium | [1.1, 1.2] | yes (3 new test cases) |

Task 1.1 specifies the exact `TrendSeries` interface, ordering invariant
(`[velocity, riskScore, wipTotal, leadTimeP50Hours]`), and degradation behavior
for missing `cycleTime`. Task 1.3 names the exact Zod schema for params and the
exact env-var resolution pattern (`RALPH_GH_OWNER`, `RALPH_GH_PROJECT_NUMBER`).

## Minor Observations (non-blocking)

- The "single value or all-equal values renders middle bucket `▄`" rule (Task
  1.2) slightly diverges from the bucketing formula (which would divide by zero
  for all-equal input). The plan acknowledges this with the explicit early-out
  rule, so implementers will treat all-equal as a special case before the
  formula.
- The markdown null-render `n/a` and the sparkline null-render `" "` are
  different conventions, but both are explicit in the plan and consistent with
  their respective contexts (label vs glyph alignment).

None of these warrant iteration.

## Recommendation

APPROVED. Ready for `/ralph-impl 1024`.
