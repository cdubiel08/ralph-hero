`plugin/ralph-hero/scripts/ralph-delegate.sh` into a sourceable adapter at

## Dimension Scoring

### 1. Completeness — PASS

Three tasks (1.1 TDD scaffold, 1.2 adapter implementation, 1.3 wrapper
refactor) cover the full extraction. Each task specifies file paths with
create/modify/read tags, line-count expectations, and explicit acceptance
boxes. The plan correctly identifies that F2 introduces three new artifacts
(`lib/openai-compat.sh`, `__tests__/openai-compat.bats`, and refactor edits to
`ralph-delegate.sh`) and tracks all three.

### 2. Feasibility — PASS

Referenced files exist; tooling assumptions (bash, curl, jq, perl, python3,
bats) are already true in F1 and CI. The Python http.server stub pattern is
copy-of-prior-art from `ralph-delegate.bats`. The `BASH_SOURCE` sourcing-guard
idiom is standard bash. The `--validate-json-output` flag is a thin `jq -e .`
wrapper, trivially feasible.

One small acknowledged fidelity loss is called out and resolved in-plan
(Task 1.3 acceptance): on non-ok responses the wrapper will log `bytes_out: 0`
because the adapter only returns parsed content, not raw response bytes. The
plan explicitly notes this is deliberate and offers an alternative (2-line
stdout encoding) for reviewers who object. The trade-off is documented at the
point where the decision is enforced. PASS.

### 3. Clarity — PASS

Success criteria are split correctly into `Automated Verification` and
`Manual Verification` checkboxes. Each automated criterion is concretely
testable (exact bats invocations, exact `--help` exit code, exact CI job
names). The "Desired End State / Verification" section lists six adapter-CLI
smoke commands with exact URLs and expected exit codes (0, 127, 124, 1, 1).
The exit-code mapping in Task 1.2 is enumerated dimension-by-dimension.

### 4. Scope — PASS

"What We're NOT Doing" is unusually thorough — nine explicit exclusions
covering streaming, native Anthropic, CI smoke tests, audit-log location,
`--task`/`--health-check`/`--dry-run` semantics, skill wiring, and CI workflow
changes. The "Shared Constraints" section pulls inherited constraints from
the parent plan-of-plans and adds three feature-specific constraints
(adapter CLI is a strict subset of the wrapper CLI, refactor-friendly
boundary, manual smoke tests not CI). Scope is bounded crisply for an XS
estimate.

### 5. Dispatchability — PASS

Each of the three tasks includes all required fields:

|------|-------|-----|------------|------------|------------|
| 1.1  | yes (create) | true | medium | null | yes (8 explicit bats @test blocks listed) |

Task 1.1 includes the verbatim list of 8 `@test` titles and assertions, so a

Dependency chain (1.1 -> 1.2 -> 1.3) is sequential and explicit — required
for TDD-first execution.

strongest cross-feature signal and is enforced both as a bats command and as

## Risks Identified (Non-Blocking)

1. **bytes_out fidelity loss** — Acknowledged and documented in-plan. The
   adapter doesn't return raw response bytes, so the wrapper will log
   `bytes_out: 0` for non-ok cases. The plan offers a 2-line stdout fallback
   if reviewers reject the loss. Non-blocking; the decision is made and the
   alternative is captured.

2. **F1 bats hermetic-stub coupling** — Task 1.1 acceptance asks the adapter
   bats to mirror F1's Python http.server stub pattern. This creates two
   parallel copies of the stub helper. Not addressed in the plan, but
   acceptable for an XS extraction (extracting the helper itself would
   expand scope). Could be a small follow-up.

3. **Adapter `--url` required when standalone** — Constraint 9 says the
   adapter takes `--url` explicitly (no env fallback) when invoked
   standalone. This is intentional (separation of concerns) but slightly
   reduces the ergonomics of operator-direct smoke tests. The plan accepts
   this trade-off.

None of these risks block approval. All are documented or are
defensible scope choices.
