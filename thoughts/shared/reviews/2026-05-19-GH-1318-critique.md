# Critique: GH-1318 Plan — Author Scouts Team-Skill, SOUL, and scouts-agent

**Verdict: APPROVED**

This is one of the better atomic plans in the recent stream. It works backward from a fixed consumer contract (`ralph-merge/SKILL.md:213-276`), explicitly cites the watch-skill pattern at line-numbered anchors, distinguishes "this phase" work from sibling-phase work in three places (Shared Constraints 8-9, "What We're NOT Doing", and the dependency annotation `depends_on: [GH-1317]`), and uses grep-based acceptance criteria as a substitute for a real lint harness. Every reviewed claim was verified against the codebase. Approve and dispatch.

## Dimension scoring

### 1. Completeness — PASS

All four tasks are defined with specific file paths, create/modify intent, and individual acceptance criteria. Frontmatter requirements are enumerated (SessionStart hook order, `allowed-tools` minimum set, `argument-hint`, `context: inline`). The Scout Report shape is rendered inline in the plan, not referenced abstractly. Section-by-section structure mirrors a known-good plan template (Prior Work / Overview / Shared Constraints / Current State Analysis / Desired End State / What We're NOT Doing / Implementation Approach / Phase / Integration Testing / References).

One minor completeness note: Task 1.3 ("Verify SOUL integration") has the acceptance criterion "Capture the output and assert it is non-empty" but does not specify *where* the assertion lives (a script? a comment in the PR?). Impl-agent will likely interpret this as a one-shot bash check during validation, which is fine — but a more rigorous plan would either (a) say "run interactively, paste output into PR comment" or (b) commit an assertion script to `scripts/`. Not blocking; documented under Minor Notes below.

## Minor notes (non-blocking)

These do not change the verdict. Impl-agent can incorporate them at authoring time, or they can be left as-is.

1. **Task 1.3 assertion location is ambiguous.** "Capture the output and assert it is non-empty" — capture *where*? A comment? A script? Recommend impl-agent treat this as a one-shot bash check during validation and paste the first 5 lines into the PR comment as evidence.

2. **Verdict severity taxonomy referenced but not defined.** Line 157 says "Signal severity taxonomy is the same one SOUL.md references." If `SOUL.md` does not explicitly enumerate severities, impl-agent will have to coin one. Quick check during impl is sufficient.

3. **`RALPH_SCOUTS_MODEL` env var is mentioned in Task 1.2 criterion #3** but not documented elsewhere (e.g., `docs/model-tier-policy.md` or CLAUDE.md). Per Shared Constraint 8, that documentation is Phase 4's job (`GH-1320`), so this is correctly deferred — but worth noting in the agent body that the env-var contract is "live but not yet documented".

4. **Dispatch matrix conditional check #4** (`grep -q '"chromatic"\|"applitools"' package.json`) assumes `package.json` exists at repo root. For monorepos with multiple `package.json` files, this may need refinement. Acceptable for this phase since the plan defers visual-diff edge cases.

5. **Frontmatter `allowed-tools` for SKILL.md and `tools:` for agent must match** (Task 1.2 criterion #4 — "true superset of what the skill needs at runtime"). This is correct semantically (skill `allowed-tools` = pre-approval, agent `tools:` = runtime hard allowlist, per the wiki entry on allowlist-not-blacklist). Worth highlighting because new contributors often invert this.
