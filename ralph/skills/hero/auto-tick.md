# `--mode auto` + Auto tick

Full contract for hero's autonomous watcher, split out of `SKILL.md` (which stays limited to dispatch + step skeletons per `ralph/CLAUDE.md`'s ~200-line convention). `SKILL.md`'s `## --mode auto` heading points here.

## `--mode auto`

Autonomous **never-terminating adaptive watcher** via `/loop` dynamic mode. This mode does NOT drain-and-stop: it loops until the user deliberately cancels via `/tasks`. While the queue has actionable work it re-fires on a tight cadence; when the queue is idle it backs off to a 1h ceiling and keeps watching, so new issues, merged-PR fallout, or `trigger:*` labels are picked up within at most an hour. Opt-in enforced by `autopilot-enable-gate.sh` — if `RALPH_AUTOPILOT_ENABLE != true`, the `Skill("loop", …)` call exits 2 with a deterministic message.

**`--loop [duration]` does not apply here.** `--mode auto` always self-loops once dispatched — it never checks `$ARGUMENTS` for a `--loop` flag — and its cadence is adaptive (60-270s busy / 3600s flat when idle), not a fixed interval. Any `--loop <duration>` token the caller passes alongside `--mode auto` (or `--auto`) is silently ignored; there is no override knob. The `[duration]` form of `--loop` is meaningful only for `--mode watch` (see its own section in `SKILL.md`), which does read `$ARGUMENTS` for an interval override.

Emit `Skill("loop", args="Run /ralph:hero --tick on the next-most-important event on the project queue\n\n<continuation prompt from loop-wrapper.md § Continuation-prompt template, hero:auto manifest row>")`. Fill `{INNER_COMMAND}` = `Run /ralph:hero --tick on the next-most-important event on the project queue`, `{PROGRESS_SENTINELS}` = all three tick result lines — `result: Dispatched #NNN to <team> via <entrypoint>` (successful dispatch, step 6), `result: Queue empty.` (step 2), and `result: Dispatch failed for #NNN …` (step 5's failure path). There are **no terminal sentinels** — this loop never ends on its own.

**Continuation rules (LOAD-BEARING):**
- `result: Dispatched #NNN …` → busy/burst → `ScheduleWakeup` 60-270s (warm-cache continuation; drains as fast as the queue produces work). **Exceptions — the two step 5b cleanup-failure variants.** Both carry the same `Dispatched #` sentinel token and both use the **600s** failure-backoff bucket, not the 60-270s busy bucket; step 5c's marker check resumes each on the next tick WITHOUT re-dispatching.
  - `… — label consumption failed …`: the dispatch landed but the trigger label is still on the issue, so the queue did not move. Next tick resumes at step 5a (ii) and retries the label removal.
  - `… — clear-marker write failed …`: the dispatch landed AND the label was removed (the queue moved), but the paired `ralph-dispatch-cleared` comment did not get written. Next tick resumes at step 5a (iii) and retries that comment alone. Not a cosmetic failure: the unpaired `ralph-dispatch-recorded` marker suppresses a future legitimate re-add of the same trigger label until it is paired.
- `result: Queue empty.` → **idle, NOT terminal** → `ScheduleWakeup` **3600s flat** (the 1h ceiling), then re-check. Do NOT end the loop.
- `result: Dispatch failed for #NNN …` → **failed/refused/skipped, NOT terminal** → `ScheduleWakeup` **600s** (failure backoff: long enough not to hot-loop on a persistent gate refusal, short enough that a transient one clears within the tick budget). The failure path deliberately *preserves* the trigger label so the event is still owed; without a wakeup here that preservation is worthless — nothing re-reads the label, `/loop` reads the absent wakeup as "task complete", and the event is dropped exactly where the code was trying to save it.
- **Every tick MUST call `ScheduleWakeup`** — there is no clean self-exit, on ANY result line (the three below, and step 5b's `Dispatched … — label consumption failed …` variant, which the postcheck's `Dispatched #` pattern already covers). `autopilot-stop-gate.sh` (keyed to `RALPH_COMMAND=hero`, armed once `Skill("loop", …/ralph:hero --tick…)` is observed) blocks session exit with a loud message if a tick returns without a wakeup; `autopilot-director-postcheck.sh` marks the tick as owing one when it sees any of the three lines. Never 300s (`autopilot-wakeup-clear.sh` rejects it). Cancel only via `/tasks` → delete the pending wakeup.

Do not maintain an iteration counter — `/loop` and the `--tick` step own that.

> **Use the `hero:auto` row, NOT `hero:default`.** `--mode auto` wraps the internal `--tick` step, whose result lines are `result: Dispatched #NNN …`, `result: Queue empty.`, and `result: Dispatch failed for #NNN …` — not the `result: Hero complete …` / `result: Hero paused …` lines on the `hero:default` row. The `hero:auto` row treats ALL THREE tick result lines as re-fire signals (Dispatched → tight cadence, Queue empty → 1h idle backoff, Dispatch failed → 600s failure backoff) so the watcher never falls through to a terminal stop.

## Auto tick (internal — dispatched only by --mode auto's loop wrapper)

Director-only step: classify one event, dispatch the correct verb, stop. Not a public mode — `--tick` appears in no mode table or argument-hint in `SKILL.md`; it exists only as the inner command `--mode auto`'s `/loop` wrapper re-issues on every cadence. Full taxonomy in [../shared/event-taxonomy.md](../shared/event-taxonomy.md).

> **`ENTRYPOINT` is a bare skill name — never a skill name plus flags.** Step 4 passes it as the FIRST argument to `Skill()`, which resolves it as a literal skill identifier; `Skill("ralph:hero --mode watch", …)` matches no registered skill and dispatches nothing. Every mode flag belongs in `DISPATCH_ARG`, which step 4 passes as `args`. This applies to every tier that resolves a multi-token entrypoint — the `watchers` team and the `blocked:*` labels are the two live cases.
>
> **Issue-scoped `DISPATCH_ARG` must name the issue with `--issue NNN`, not a trailing bare `NNN`, whenever a mode flag is also present.** `SKILL.md`'s `## --mode watch` parser resolves the target from `--issue NNN` (or a bare number) **anywhere** in `$ARGUMENTS`, but the dispatcher must not depend on that tolerance: `--mode watch NNN` reads as "mode flag, then a positional" and was silently swallowed by the old prefix-only parse, dropping the target and running a board-wide heartbeat instead of the requested per-issue watch. The `watchers` tier therefore dispatches `--mode watch --issue NNN`. Tiers with no mode flag (builders, scouts, caretakers) keep the bare `"NNN"`.

1. **Parse + detect input source.** `--issue NNN` → `TARGET_ISSUE=NNN`, skip to step 3. `RemoteTrigger` tool input (deprecated) → extract `issue_number`+`team`, then **fully initialize the dispatch state before skipping ahead** (step 4 dispatches `Skill(ENTRYPOINT, args=…)` and has no other chance to set these): `TARGET_ISSUE=<issue_number>`, `DISPATCH_REASON=RemoteTrigger`, `CONSUMED_LABEL=none` (a RemoteTrigger carries no label to strip), and `ENTRYPOINT` + `DISPATCH_ARG` resolved from `<team>` via the **same team map step 3 uses**, splitting skill name from mode flags per the rule above — `builders`→`ENTRYPOINT=ralph:hero`, `DISPATCH_ARG="NNN"`; `watchers`→`ENTRYPOINT=ralph:hero`, `DISPATCH_ARG="--mode watch --issue NNN"`; `scouts`→the `ralph-playwright` skill name in `ENTRYPOINT`, `DISPATCH_ARG="NNN"`; `caretakers`→`ENTRYPOINT=ralph:caretake`, `DISPATCH_ARG="NNN"`; `memorykeepers`→unimplemented (emit the step-4 `needs input:` marker **and its failure result line** — see step 4 — then STOP). An unrecognized team is the same unimplemented case. Then skip to step 4. Otherwise → step 2.
2. **Read `next_actions({ audience: "agent" })`.** Empty queue → emit `result: Queue empty. No events to dispatch.` STOP. Pick top-ranked direction; resolve `TARGET_ISSUE` per [../shared/event-taxonomy.md](../shared/event-taxonomy.md) (kind rules). **Audience MUST be `agent` (not the `human` default):** this is the autonomous orchestrator path (and the engine of `--mode auto`), so it must get the XS/S estimate penalty (`audiencePenalty` in `directions.ts`) and the Backlog/null-state triage fallback (the agent-only `scored.length === 0` branch). With the human default, hero ranks XL like XS and idles on `Queue empty.` while Backlog has untriaged work. Sibling-file audit: `dispatch.md` and `watch-dispatch.md` have no other queue-read call sites.
3. **Fetch + classify.** `get_issue({ number: TARGET_ISSUE })`. Apply [../shared/event-taxonomy.md](../shared/event-taxonomy.md) priority order: `trigger:*` labels → **`blocked:*` labels (watcher routing)** → automation labels → `workflow_state`. Set `TEAM`, `ENTRYPOINT` (bare skill name), `DISPATCH_ARG`, `DISPATCH_REASON`, `CONSUMED_LABEL`. `DISPATCH_ARG` defaults to the bare issue number `"NNN"`; the two tiers that need mode flags set it explicitly. For the `trigger:watch` label / `watchers` team → `ENTRYPOINT=ralph:hero`, `DISPATCH_ARG="--mode watch --issue NNN"` (the `--issue` form is load-bearing — see the dispatch-contract note above). For the `blocked:*` tier: a label prefix-matching `blocked:pr-` → `TEAM=caretakers`, `ENTRYPOINT=ralph:caretake`, `DISPATCH_ARG="--mode watch --kind pr"`, `DISPATCH_REASON=blocked:pr`, `CONSUMED_LABEL=none`; exact `blocked:upstream` → `ENTRYPOINT=ralph:caretake`, `DISPATCH_ARG="--mode watch --kind upstream"`, `DISPATCH_REASON=blocked:upstream`, `CONSUMED_LABEL=none`.
4. **Dispatch.** Always `Skill(ENTRYPOINT, args=DISPATCH_ARG)` — one call shape for every tier, because `ENTRYPOINT` is always a bare skill name. Examples: `Skill("ralph:caretake", args="--mode watch --kind pr")` and `Skill("ralph:caretake", args="--mode watch --kind upstream")` for the `blocked:*` tier (a **board-wide watcher sweep** NOT scoped to `NNN` — the watcher mode ignores an issue arg); `Skill("ralph:hero", args="--mode watch --issue NNN")` for the watchers team; `Skill("ralph:hero", args="NNN")` for builders. Unimplemented team (memorykeepers) → emit `needs input: team <name> not yet implemented; skipping dispatch.` **followed by step 5's failure result line** (`result: Dispatch failed for #NNN (team <name> not implemented); no label consumed. Retrying next tick.`). A skipped dispatch is still a tick that must re-fire the loop — the `needs input:` marker alone matches none of the three continuation sentinels, so emitting it by itself ends the watcher.
5. **Dispatch failed → preserve the label, emit the failure line.** If step 4's `Skill(...)` errored, was refused by a gate hook, or never ran, **leave `CONSUMED_LABEL` in place** and emit `result: Dispatch failed for #NNN (<reason>); trigger label preserved for retry. Retrying next tick.` — the label is the only record that the event is still owed, so stripping it on a failed dispatch loses the event silently (nothing re-adds it, and `next_actions` has no other signal to re-surface it). The trailing `Retrying next tick.` is not decoration: `result: Dispatch failed …` is a **continuation sentinel** (§ `--mode auto` continuation rules, 600s backoff) recognized by `autopilot-director-postcheck.sh`, and it is what makes the preserved label actually reachable — a failure line outside that set ends the loop and the retry never happens. Tiers with `CONSUMED_LABEL=none` emit that same failure line with `no label consumed` in place of `trigger label preserved for retry` — they too must re-fire, so the `blocked:*` tier (the watcher owns that label's lifecycle), automation labels, and the `RemoteTrigger` path are **never** exempt from emitting a result line. What they skip is only the `save_issue` label-strip ACTION in step 5a, and only on a SUCCESSFUL dispatch — where step 6 emits their success line instead. Read the old wording literally and a failed `blocked:*`/automation/`RemoteTrigger` dispatch emitted no result line at all, which violates the every-tick-emits-one-of-three contract (line 17) and stalls the watcher on exactly that tier's failures. STOP here; steps 5a-6 are the success path.

5a. **Dispatch succeeded → record it durably, THEN consume the label.** Only reached when step 4's `Skill(...)` returned successfully. Nothing to do when `CONSUMED_LABEL=none` — go to step 6. Otherwise, in this order:

   i. `create_comment({ number: TARGET_ISSUE, body: "<!-- ralph-dispatch-recorded: <CONSUMED_LABEL> -->\nDispatched to <team> via <entrypoint> (reason: <DISPATCH_REASON>)." })` — the durable record that this event has ALREADY been dispatched.
   ii. `save_issue({ number: TARGET_ISSUE, labels: ISSUE_LABELS minus CONSUMED_LABEL })`.
   iii. On success, `create_comment({ number: TARGET_ISSUE, body: "<!-- ralph-dispatch-cleared: <CONSUMED_LABEL> -->" })` so the marker from (i) cannot suppress a *future*, legitimate re-add of the same trigger label.

   **The record comes first on purpose.** `save_issue` can fail on its own (rate limit, transient 5xx, a lock-guard conflict) *after* the dispatch already happened. Doing (ii) first and (i) never leaves the trigger label on the issue with no evidence the work was dispatched — the next tick re-classifies the same label and dispatches the SAME event again, forever.

   **(iii) is fallible too, and its failure is NOT cosmetic.** It is a `create_comment` on the same API that just failed for (ii) in step 5b, so it fails for the same reasons. If (iii) is treated as fire-and-forget, a tick where (ii) succeeded and (iii) failed leaves the (i) marker unpaired forever while the label is already gone — and step 5c's suppression rule keys on exactly that unpaired marker, so the next legitimate re-add of the same trigger label is silently swallowed and never dispatched. Worse, that tick emits step 6's clean success line and the loop moves on, so nothing ever retries. Handle it explicitly — see step 5b's second failure mode.

5b. **Label consumption failed → distinct path, distinct result line.** If (ii) fails, the dispatch is still a success and must **not** be retried. Do NOT abort the tick (that drops the wakeup) and do NOT emit step 5's `Dispatch failed …` line (that re-dispatches). Emit instead:

   ```text
   result: Dispatched #NNN to <team> via <entrypoint>. (reason: <DISPATCH_REASON>) — label consumption failed (<reason>); retrying label removal next tick.
   ```

   This line is a continuation sentinel by construction: it carries the `Dispatched #` token `autopilot-director-postcheck.sh` greps for, so the tick still owes (and schedules) a `ScheduleWakeup`. Treat it as the **600s failure backoff** bucket, not the 60-270s busy bucket — the queue did not move.

   If (i) ALSO failed, there is no durable record, so a naive retry *would* re-dispatch. In that case emit the same line with `(<reason>; dispatch NOT recorded — verify #NNN before the next tick)` and escalate the issue to `Human Needed` via `save_issue`; if that escalation also fails, the result line above is still emitted so the watcher survives to try again.

   **Second failure mode — (ii) succeeded but (iii) failed (clear-marker write).** The dispatch landed AND the label is gone, so the queue *did* move and this must never re-dispatch. What is owed is only the clear marker. Do NOT emit step 6's clean success line (it would report the tick as fully done and nothing would ever retry), and do NOT abort (that drops the wakeup). Emit instead:

   ```text
   result: Dispatched #NNN to <team> via <entrypoint>. (reason: <DISPATCH_REASON>) — clear-marker write failed (<reason>); retrying marker cleanup next tick.
   ```

   Same construction as the line above: it carries the `Dispatched #` token `autopilot-director-postcheck.sh` greps for, so the tick still owes and schedules a `ScheduleWakeup`. Use the **600s failure backoff** bucket — the dispatch succeeded, but an API that is refusing writes will refuse the retry on a 60s cadence too. The unpaired `ralph-dispatch-recorded` marker left on the issue IS the persistence: step 5c reads it on the next tick and retries the cleanup. No other state is needed.

5c. **Idempotent retry (consumed by step 3, next tick).** During step 3's classification, a `trigger:*` label counts as an actionable event ONLY if the issue does not carry a matching `<!-- ralph-dispatch-recorded: <label> -->` marker that is not followed by a later `<!-- ralph-dispatch-cleared: <label> -->` marker. When such an unpaired marker IS present, **skip step 4's dispatch entirely** — the event was already dispatched — and resolve what is still owed from whether the label is present:

   - **Label still on the issue** → step 5a (ii) never succeeded. Resume at (ii): retry the label removal, then (iii).
   - **Label absent** → (ii) succeeded and only (iii) is owed. Resume at (iii): retry the clear-marker `create_comment` alone. Never re-remove a label that is already gone, and never re-dispatch.

   Either way, emit step 6's success line once the owed work completes, or step 5b's matching line again on another failure. **This retry runs BEFORE any matching trigger can be dispatched** — the unpaired marker suppresses classification of that label by construction, so the cleanup is drained first and a future legitimate re-add is never swallowed by a marker the previous tick failed to pair. That is what makes the retry bounded in effect: the event is dispatched at most once, no matter how many ticks the label removal and its clear-marker take.

6. **Emit result marker — full-success path only.** `result: Dispatched #NNN to <team> via <entrypoint>. (reason: <DISPATCH_REASON>)`, emitted **only after step 4's `Skill(...)` returned successfully AND all of step 5a completed — the record (i), the label removal (ii), AND the clear marker (iii)** (or there was no label to consume). A dispatch that errored, was refused, or was skipped already emitted step 5's `result: Dispatch failed …` line; a dispatch whose label removal or clear-marker write failed already emitted the matching step 5b line. "Full success" includes (iii) deliberately: reporting a tick clean while the clear marker is still owed is what lets an unpaired marker suppress a future trigger with nothing left to retry it. Exactly one `result:` line per tick — the postcheck hook reads the last one to decide the wakeup cadence.
