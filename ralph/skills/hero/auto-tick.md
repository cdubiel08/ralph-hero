# `--mode auto` + Auto tick

Full contract for hero's autonomous watcher, split out of `SKILL.md` (which stays limited to dispatch + step skeletons per `ralph/CLAUDE.md`'s ~200-line convention). `SKILL.md`'s `## --mode auto` heading points here.

## `--mode auto`

Autonomous **never-terminating adaptive watcher** via `/loop` dynamic mode. This mode does NOT drain-and-stop: it loops until the user deliberately cancels via `/tasks`. While the queue has actionable work it re-fires on a tight cadence; when the queue is idle it backs off to a 1h ceiling and keeps watching, so new issues, merged-PR fallout, or `trigger:*` labels are picked up within at most an hour. Opt-in enforced by `autopilot-enable-gate.sh` — if `RALPH_AUTOPILOT_ENABLE != true`, the `Skill("loop", …)` call exits 2 with a deterministic message.

**`--loop [duration]` does not apply here.** `--mode auto` always self-loops once dispatched — it never checks `$ARGUMENTS` for a `--loop` flag — and its cadence is adaptive (60-270s busy / 3600s flat when idle), not a fixed interval. Any `--loop <duration>` token the caller passes alongside `--mode auto` (or `--auto`) is silently ignored; there is no override knob. The `[duration]` form of `--loop` is meaningful only for `--mode watch` (see its own section in `SKILL.md`), which does read `$ARGUMENTS` for an interval override.

Emit `Skill("loop", args="Run /ralph:hero --tick on the next-most-important event on the project queue\n\n<continuation prompt from loop-wrapper.md § Continuation-prompt template, hero:auto manifest row>")`. Fill `{INNER_COMMAND}` = `Run /ralph:hero --tick on the next-most-important event on the project queue`, `{PROGRESS_SENTINELS}` = all three tick result lines — `result: Dispatched #NNN to <team> via <entrypoint>` (successful dispatch, step 6), `result: Queue empty.` (step 2), and `result: Dispatch failed for #NNN …` (step 5's failure path). There are **no terminal sentinels** — this loop never ends on its own.

**Continuation rules (LOAD-BEARING):**
- `result: Dispatched #NNN …` → busy/burst → `ScheduleWakeup` 60-270s (warm-cache continuation; drains as fast as the queue produces work).
- `result: Queue empty.` → **idle, NOT terminal** → `ScheduleWakeup` **3600s flat** (the 1h ceiling), then re-check. Do NOT end the loop.
- `result: Dispatch failed for #NNN …` → **failed/refused/skipped, NOT terminal** → `ScheduleWakeup` **600s** (failure backoff: long enough not to hot-loop on a persistent gate refusal, short enough that a transient one clears within the tick budget). The failure path deliberately *preserves* the trigger label so the event is still owed; without a wakeup here that preservation is worthless — nothing re-reads the label, `/loop` reads the absent wakeup as "task complete", and the event is dropped exactly where the code was trying to save it.
- **Every tick MUST call `ScheduleWakeup`** — there is no clean self-exit, on ANY of the three result lines. `autopilot-stop-gate.sh` (keyed to `RALPH_COMMAND=hero`, armed once `Skill("loop", …/ralph:hero --tick…)` is observed) blocks session exit with a loud message if a tick returns without a wakeup; `autopilot-director-postcheck.sh` marks the tick as owing one when it sees any of the three lines. Never 300s (`autopilot-wakeup-clear.sh` rejects it). Cancel only via `/tasks` → delete the pending wakeup.

Do not maintain an iteration counter — `/loop` and the `--tick` step own that.

> **Use the `hero:auto` row, NOT `hero:default`.** `--mode auto` wraps the internal `--tick` step, whose result lines are `result: Dispatched #NNN …`, `result: Queue empty.`, and `result: Dispatch failed for #NNN …` — not the `result: Hero complete …` / `result: Hero paused …` lines on the `hero:default` row. The `hero:auto` row treats ALL THREE tick result lines as re-fire signals (Dispatched → tight cadence, Queue empty → 1h idle backoff, Dispatch failed → 600s failure backoff) so the watcher never falls through to a terminal stop.

## Auto tick (internal — dispatched only by --mode auto's loop wrapper)

Director-only step: classify one event, dispatch the correct verb, stop. Not a public mode — `--tick` appears in no mode table or argument-hint in `SKILL.md`; it exists only as the inner command `--mode auto`'s `/loop` wrapper re-issues on every cadence. Full taxonomy in [../shared/event-taxonomy.md](../shared/event-taxonomy.md).

> **`ENTRYPOINT` is a bare skill name — never a skill name plus flags.** Step 4 passes it as the FIRST argument to `Skill()`, which resolves it as a literal skill identifier; `Skill("ralph:hero --mode watch", …)` matches no registered skill and dispatches nothing. Every mode flag belongs in `DISPATCH_ARG`, which step 4 passes as `args`. This applies to every tier that resolves a multi-token entrypoint — the `watchers` team and the `blocked:*` labels are the two live cases.

> **Issue-scoped `DISPATCH_ARG` must name the issue with `--issue NNN`, not a trailing bare `NNN`, whenever a mode flag is also present.** `SKILL.md`'s `## --mode watch` parser resolves the target from `--issue NNN` (or a bare number) **anywhere** in `$ARGUMENTS`, but the dispatcher must not depend on that tolerance: `--mode watch NNN` reads as "mode flag, then a positional" and was silently swallowed by the old prefix-only parse, dropping the target and running a board-wide heartbeat instead of the requested per-issue watch. The `watchers` tier therefore dispatches `--mode watch --issue NNN`. Tiers with no mode flag (builders, scouts, caretakers) keep the bare `"NNN"`.

1. **Parse + detect input source.** `--issue NNN` → `TARGET_ISSUE=NNN`, skip to step 3. `RemoteTrigger` tool input (deprecated) → extract `issue_number`+`team`, then **fully initialize the dispatch state before skipping ahead** (step 4 dispatches `Skill(ENTRYPOINT, args=…)` and has no other chance to set these): `TARGET_ISSUE=<issue_number>`, `DISPATCH_REASON=RemoteTrigger`, `CONSUMED_LABEL=none` (a RemoteTrigger carries no label to strip), and `ENTRYPOINT` + `DISPATCH_ARG` resolved from `<team>` via the **same team map step 3 uses**, splitting skill name from mode flags per the rule above — `builders`→`ENTRYPOINT=ralph:hero`, `DISPATCH_ARG="NNN"`; `watchers`→`ENTRYPOINT=ralph:hero`, `DISPATCH_ARG="--mode watch --issue NNN"`; `scouts`→the `ralph-playwright` skill name in `ENTRYPOINT`, `DISPATCH_ARG="NNN"`; `caretakers`→`ENTRYPOINT=ralph:caretake`, `DISPATCH_ARG="NNN"`; `memorykeepers`→unimplemented (emit the step-4 `needs input:` marker **and its failure result line** — see step 4 — then STOP). An unrecognized team is the same unimplemented case. Then skip to step 4. Otherwise → step 2.
2. **Read `next_actions({ audience: "agent" })`.** Empty queue → emit `result: Queue empty. No events to dispatch.` STOP. Pick top-ranked direction; resolve `TARGET_ISSUE` per [../shared/event-taxonomy.md](../shared/event-taxonomy.md) (kind rules). **Audience MUST be `agent` (not the `human` default):** this is the autonomous orchestrator path (and the engine of `--mode auto`), so it must get the XS/S estimate penalty (`audiencePenalty` in `directions.ts`) and the Backlog/null-state triage fallback (the agent-only `scored.length === 0` branch). With the human default, hero ranks XL like XS and idles on `Queue empty.` while Backlog has untriaged work. Sibling-file audit: `dispatch.md` and `watch-dispatch.md` have no other queue-read call sites.
3. **Fetch + classify.** `get_issue({ number: TARGET_ISSUE })`. Apply [../shared/event-taxonomy.md](../shared/event-taxonomy.md) priority order: `trigger:*` labels → **`blocked:*` labels (watcher routing)** → automation labels → `workflow_state`. Set `TEAM`, `ENTRYPOINT` (bare skill name), `DISPATCH_ARG`, `DISPATCH_REASON`, `CONSUMED_LABEL`. `DISPATCH_ARG` defaults to the bare issue number `"NNN"`; the two tiers that need mode flags set it explicitly. For the `trigger:watch` label / `watchers` team → `ENTRYPOINT=ralph:hero`, `DISPATCH_ARG="--mode watch --issue NNN"` (the `--issue` form is load-bearing — see the dispatch-contract note above). For the `blocked:*` tier: a label prefix-matching `blocked:pr-` → `TEAM=caretakers`, `ENTRYPOINT=ralph:caretake`, `DISPATCH_ARG="--mode watch --kind pr"`, `DISPATCH_REASON=blocked:pr`, `CONSUMED_LABEL=none`; exact `blocked:upstream` → `ENTRYPOINT=ralph:caretake`, `DISPATCH_ARG="--mode watch --kind upstream"`, `DISPATCH_REASON=blocked:upstream`, `CONSUMED_LABEL=none`.
4. **Dispatch.** Always `Skill(ENTRYPOINT, args=DISPATCH_ARG)` — one call shape for every tier, because `ENTRYPOINT` is always a bare skill name. Examples: `Skill("ralph:caretake", args="--mode watch --kind pr")` and `Skill("ralph:caretake", args="--mode watch --kind upstream")` for the `blocked:*` tier (a **board-wide watcher sweep** NOT scoped to `NNN` — the watcher mode ignores an issue arg); `Skill("ralph:hero", args="--mode watch --issue NNN")` for the watchers team; `Skill("ralph:hero", args="NNN")` for builders. Unimplemented team (memorykeepers) → emit `needs input: team <name> not yet implemented; skipping dispatch.` **followed by step 5's failure result line** (`result: Dispatch failed for #NNN (team <name> not implemented); no label consumed. Retrying next tick.`). A skipped dispatch is still a tick that must re-fire the loop — the `needs input:` marker alone matches none of the three continuation sentinels, so emitting it by itself ends the watcher.
5. **Consume label — only after the dispatch succeeded.** If `CONSUMED_LABEL` is set (only the `trigger:*` tier sets it) **AND step 4's `Skill(...)` returned successfully**: `save_issue({ number: TARGET_ISSUE, labels: ISSUE_LABELS minus CONSUMED_LABEL })`. If the dispatch errored, was refused by a gate hook, or never ran, **leave the label in place** and emit `result: Dispatch failed for #NNN (<reason>); trigger label preserved for retry. Retrying next tick.` — the label is the only record that the event is still owed, so stripping it on a failed dispatch loses the event silently (nothing re-adds it, and `next_actions` has no other signal to re-surface it). The trailing `Retrying next tick.` is not decoration: `result: Dispatch failed …` is a **continuation sentinel** (§ `--mode auto` continuation rules, 600s backoff) recognized by `autopilot-director-postcheck.sh`, and it is what makes the preserved label actually reachable — a failure line outside that set ends the loop and the retry never happens. Tiers with `CONSUMED_LABEL=none` emit that same failure line with `no label consumed` in place of `trigger label preserved for retry` — they too must re-fire, so the `blocked:*` tier (the watcher owns that label's lifecycle), automation labels, and the `RemoteTrigger` path are **never** exempt from emitting a result line. What they skip is only the `save_issue` label-strip ACTION above, and only on a SUCCESSFUL dispatch — where step 6 emits their success line instead. Read the old wording literally and a failed `blocked:*`/automation/`RemoteTrigger` dispatch emitted no result line at all, which violates the every-tick-emits-one-of-three contract (line 17) and stalls the watcher on exactly that tier's failures.
6. **Emit result marker — success path only.** `result: Dispatched #NNN to <team> via <entrypoint>. (reason: <DISPATCH_REASON>)`, emitted **only after step 4's `Skill(...)` returned successfully**. A dispatch that errored, was refused, or was skipped already emitted step 5's `result: Dispatch failed …` line and must NOT also emit this one: exactly one `result:` line per tick, and the postcheck hook reads the last one to decide the wakeup cadence.
